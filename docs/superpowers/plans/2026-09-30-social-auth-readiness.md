# 소셜 인증 활성화 전 앱 준비

기준: 2026-09-30, `feature/bank-state-transitions` / `10ec214` 위의 기존 미커밋 작업. 사용자 승인: 앱 개발·검증은 진행하고 공급자 키 입력·활성화는 사용자가 추후 수행한다.

## 목표와 경계

기존 BFF → Supabase Auth 연결을 유지한다. Google/Kakao는 기본 공급자, Naver는 `custom:naver`이며 실제 호환성은 아직 미검증이다. Nest Passport, 추가 인증 저장소, 새로운 의존성은 넣지 않는다. 운영 DB·실제 자격 증명·외부 공급자 설정은 변경하지 않는다.

## 대안과 결정

- 화면만 버튼 숨김: 작지만 직접 API 호출을 막지 못한다.
- 서버 허용 목록과 화면 안내를 함께 연결(선택): 설정을 한 곳에서 관리하고 기본 비활성을 보장한다. 공개되는 값은 공급자 이름뿐이다.
- 공급자별 별도 Passport 구현: 인증·세션 체계가 갈라지고 현재 합의 범위를 벗어나므로 제외한다.

이메일 비밀번호 경로는 인증된 이메일을 계속 요구한다. 이메일 없는 소셜 로그인은 Supabase 서버 응답의 사용자 ID·소셜 identity·OAuth 인증 방식이 확인될 때에만 허용하며, 이메일을 만들어내거나 `emailVerified=true`로 위장하지 않는다. 사용자 편집 가능 metadata를 권한 근거로 삼지 않는다. 이메일이 있는 미인증 계정은 계속 거부한다.

## 파일 지도·예상 규모

| 경로 | 작업 |
| --- | --- |
| `apps/web/src/server/auth/` | 공급자 설정 파서 추가, Supabase 응답의 이메일 없는 OAuth 처리와 해당 회귀 테스트 |
| `apps/web/src/server/container.ts` | 허용 목록 주입 |
| `apps/web/src/server/http/auth-controller.ts` | start/continue/callback 비활성 공급자 거부 |
| `apps/web/src/app/api/auth/providers/` | 비밀값 없는 공개 상태 조회 |
| `apps/web/src/queries/`, `components/auth/`, `(auth)/` | ky + React Query 상태 조회, 준비 중/실패 안내 |
| `packages/contracts/src/auth.ts` | 공개 공급자 상태 계약 |
| `tests/e2e/` | 기존 합성 인증 환경의 명시적 공급자 설정, Playwright 회귀 |
| `docs/guides/`, `docs/status/`, Notion 인증 카드 | 사용자 설정 절차, 검증 결과, 실제 공급자 미검증과 다음 작업 |

예상 20~30개 파일, 제품 코드 약 250~400줄, 테스트·문서 약 400~700줄. 기존 큰 컨트롤러는 필요한 분기만 수정하고 새 정책은 별도 작은 파일로 분리한다. 자동 생성 lockfile 변경 없음.

## 순서와 완료 조건

1. 기존 일반 테스트 기준선 확인.
2. 비활성/잘못된 설정, 직접 API 우회, 이메일 없는 OAuth와 이메일 경로 거부, UI 준비 중 테스트를 먼저 실패시킨다.
3. 최소 구현 후 관련 테스트, 전체 일반 테스트, lint/typecheck/build를 실행한다.
4. PC 로그인/가입 화면의 준비 중·정상 활성화·오류 복귀를 실제 Playwright로 확인한다. 실제 Google/Kakao/Naver 계정을 사용한 검증으로 간주하지 않는다.
5. 한국어 설명·설정 체크리스트와 Notion 기능별 현황 갱신. 공급자 키·쿠키·토큰·실제 사용자 데이터는 기록하지 않는다.
6. 다음 우선순위인 거래 조회/입력 API와 PC 화면의 기존 스키마·멱등성·버전 정책을 확인해 착수 범위를 기록한다.

공급자 허용 목록에서 제거하는 것은 새 로그인 차단이지 기존 세션 즉시 폐기가 아니다. 실제 공급자 응답이 문서/테스트와 다르면 해당 공급자를 비활성으로 유지하고 수정·재검증한다. 이번에는 커밋·푸시·배포를 수행하지 않는다.
