## Phase 1 — CEO: 목표·범위·운영 검토

### 0A–0F: 왜 지금 이 작업인가

**0A 전제:** 무료 유지와 공개 가능은 사용자 선택이다. 공개가 실계좌 API 이용 자격이나 앱 출시를 해결한다는 전제는 채택하지 않는다. PR 연관성만으로 병합 경로를 증명한다는 종전 가정은 폐기한다. 1인 운영에서 본인 최종 확인은 절차적 통제이며 서버가 타인의 독립 승인을 강제하는 것과 다르다.

**0B 기존 코드 재사용:** `.github/settings/main-protection.json`은 목표 설정 골격, workflow는 PR 품질·main 사후 검사, `merge-evidence.mjs`는 PR/커밋 연관성, `github-merge-evidence.mjs`는 제한된 읽기 조회, workflow 정책 테스트는 의도치 않은 설정 변경 탐지, 기존 운영 문서는 오류 복구 절차를 제공한다. 새 승인 서버·서명키·의존성은 만들지 않는다.

**0C 지향점:**

```text
현재: private + 우회 가능한 로컬 hook + 사후 CI
  -> 이번: 공개 안전성 확인 + 서버 PR/검사 조건 + 본인 SHA 확인
  -> 12개월: 협업자 발생 시 독립 리뷰, 검증된 배포·운영 경계
```

이번 단계로 모바일·은행 API·금융 DB가 완성되지는 않는다. CI 차단 요소를 명확히 종결하고 10-A2 은행 연결 DB 단계로 돌아가는 것이 가치다.

**0C-bis 대안:**

| 대안 | 규모·장점 | 단점·위험 | 판단 |
| --- | --- | --- | --- |
| 기존 저장소 공개 + classic 보호 | 중간, 기존 설정·CI 재사용, 추가 요금·서버 없음 | 전체 과거 노출 검토, 공개 회수 불가 | 사용자 방향 유지 |
| 정제된 현재 소스만 새 공개 저장소 | 중간~큼, 공개 이력을 축소 가능 | PR·링크·CI 이전, 현재 소스도 재검토 필요 | 기존 이력 안전성 해결 불가 때만 별도 승인 비교 |
| private + 로컬/사후 통제 유지 | 작음, 공개 위험 없음 | 서버 사전 차단 목표 불충족 | 전환 보류 중 상태일 뿐 완료 대안 아님 |

유료 전환은 무료 요구에 어긋나므로 다시 제안하지 않는다. 좋은 패턴은 네이티브 보호 재사용, 설정 적용 후 재조회, 무민감 fixture 검증이다. 피할 패턴은 사후 CI를 사전 차단으로 소개하기와 해시를 바꾸는 것만으로 검사 변경을 승인하기다.

**0D 확장 5건:** (1) 공개 자료 목록+변경분 확인 수용, (2) SHA 기반 본인 확인 수용, (3) 오류별 대응 표 재사용, (4) 별도 정책 서버 제외, (5) 자동 공개·복구 도구 제외. 수용 항목은 기존 운영 문서 안에서 해결한다. 외부 리소스 생성은 포함하지 않는다.

**0E 시간순 확인:** 첫 구간은 원격 SHA·규칙·실제 체크 확인, 다음은 설정/테스트 작성, 이후는 문서·로컬 회귀, 마지막은 공개 대상 감사와 사용자 확인이다. 1~6시간이라는 고정 소요를 보장하지 않는다. 전체 이력·첨부 검토와 외부 권한 문제가 일정의 가장 큰 변수다.

**0F 모드:** SELECTIVE EXPANSION을 유지하되 인접한 운영 빈틈만 보완한다. 은행 연결을 빨리 시작하려고 공개 점검을 생략하지 않고, 반대로 이번에 전 제품 보안 체계를 다시 만들지도 않는다.

### 1. 구조

서버 보호는 main 갱신 전 조건을 검사하고, 기존 main-provenance는 갱신 후 연관성을 확인한다. 둘을 하나의 증명으로 합치지 않는다. 소유자는 규칙 변경 권한이 있어 신뢰 경계 밖의 절대 차단 대상이 될 수 없다.

```text
feature -> PR 후보 head H + base B -> security-gate(check SHA C, app A)
               |                                  |
               +-> 본인 diff/CI 최종 확인 ----------+
                                                  v
                                  GitHub 서버 보호 -> main M
                                                       -> 사후 CI
우회 가능 경계: 관리자 규칙 변경 / 신뢰된 작성자의 검사 코드 축소
```

### 2. 오류·복구

원격 읽기 실패·검사 불일치를 성공으로 간주하지 않는다. 보호 미적용 상태에서는 병합하지 않는다. 사후 검사 실패 시 main을 강제 되돌리지 않고 조사 후 수정 PR을 사용한다. 아래 레지스트리에 오류와 사용자 행동을 연결했다.

### 3. 보안

**C1 P1:** 같은 Actions 앱·체크 이름은 승인된 workflow 내용까지 보증하지 않는다. 같은 PR에서 workflow와 digest 테스트를 함께 바꿀 수 있으므로 소유자의 최종 diff 확인이 필요하다. **C2 P1:** 공개 검토 후 새 커밋·댓글·로그가 생길 수 있다. 최종 목록 확정 시 동결을 시작하고 전환 직전 변경분을 재검사한다. 둘 다 계획으로 수용하며 아직 운영상 해결된 것은 아니다.

### 4. 데이터·상호작용

**C3 P1:** 본인 확인은 최종 head H, base B, 체크 실행 ID·검사 SHA C에 결합한다. head/base/검사 내용이 바뀌면 이전 확인은 재사용하지 않는다. PR 검사가 merge ref를 검사하는 경우 C가 H와 항상 같지는 않으므로 실행 이벤트·head/base 연결까지 확인해야 한다. 원본 금융 데이터와 비밀값은 증거 파일에 넣지 않는다.

### 5. 코드 품질

**C4 P2:** 종전 무료/private 경고와 새 public 보호 완료 표시가 혼재할 수 있다. 문서를 삭제하는 대신 날짜·상태를 분리한다. source digest 테스트는 실수 방어이고 신뢰된 변경자의 악의까지 막는 장치가 아니라는 설명을 추가한다.

### 6. 테스트

현재 연관성 단위 테스트와 workflow 구조 테스트는 재사용한다. 서버 보호 활성화·취소/실패 차단·출처 고정은 로컬 테스트로 증명할 수 없어 별도 원격 증거가 필요하다. 간접 병합은 허용될 수 있다는 한계 테스트를 추가하고 이것을 취약점 해결 테스트로 오해하지 않게 한다. 세부 지도는 Eng 단계에서 작성한다.

### 7. 성능

앱 요청·DB·FCP 경로 변경은 없어 사용자 화면 지연에 직접 영향은 없다. 전체 이력 감사 비용과 strict 검사 재실행은 증가할 수 있다. 기존 blob 중복 제거와 조회 한도를 유지하며 속도를 이유로 이력·필수 단계를 생략하지 않는다. 시간 수치는 미측정이다.

### 8. 관측성

**C5 P2:** 자료 점검·원격 read-back·체크 실행·본인 확인을 대상 SHA와 시각별로 남긴다. 분기 보호 종료와 secret protection 종료를 별도 행으로 기록한다. 활성화 여부를 확인하지 않은 통제를 완료 처리하지 않는다. 토큰·응답 원문 대신 안전한 코드·ID만 기록한다.

### 9. 적용·복구

```text
자료 목록 확정/동결 -> 전체 점검 -> 변경분 재검사 -> 공개 최종 승인
 -> 공개 -> 보호 적용/재조회 -> 무민감 검증 -> 정상 PR -> 사후 확인
실패 -> 추가 쓰기·병합·배포 중단 -> 상태/증거 보고 -> 별도 복구 승인
```

공개 후 private 복귀가 복제본 회수를 의미하지 않는다. 전환은 원자적이지 않으므로 노출과 보호 적용 사이의 상태를 보고한다. 자동 공개 반복·force push·보호 완화는 없다.

### 10. 장기 영향

설정 변경은 되돌릴 수 있지만 공개 이력은 완전 회수가 불가능하다(가역성 1/5). 설정·문서만의 가역성은 4/5다. 협업자가 생기면 required approval 1 이상과 신뢰된 CI 정책을 재설계한다. 지금 별도 승인 인프라를 추가하지 않는다.

### 11. 디자인

제품 UI·접근성·레이아웃을 바꾸지 않으므로 제외한다. 개발자 안내 문구·오류 가독성은 DX 검토 대상이다.

### 오류·실패 레지스트리

새 런타임 메서드를 추가하지 않는다. 아래 `계획 코드`는 운영 체크리스트의 분류이며 이미 구현된 예외 클래스라고 주장하지 않는다.

| 경로 | 오류/실패 | 복구·사용자가 보는 결과 | 기존 검증/남은 검증 |
| --- | --- | --- | --- |
| 공개 자료 점검 | 자료 누락·접근 불가(계획: EXPOSURE_REVIEW_INCOMPLETE) | 미검증 목록 표시, 공개 중단 | 전체 감사 미실행 |
| 최종 공개 | 검토 후 자료 변경(계획: EXPOSURE_DRIFT) | 변경분 재검사·재확인 | 수동 시나리오 필요 |
| 보호 적용 | 권한 부족·충돌·값 불일치(계획: PROTECTION_MISMATCH) | 중단, 원격 실제 상태 보고 | 원격 read-back 필요 |
| 체크 선택 | 앱 ID/실행 SHA 불명(계획: CHECK_IDENTITY_UNKNOWN) | any-source로 완화하지 않음 | 원격 체크 증거 필요 |

## Phase 3 — Eng: 실제 코드와 검증 계획

### 0. 범위·재사용 판단

현재 `workflow-policy.test.mjs`는 562줄로 이미 길다. 새로운 보호 JSON 정책 테스트를 이 파일에 더 붙이지 않고 독립 `branch-protection-policy.test.mjs`로 나눈다. 런타임 추상화·새 패키지는 추가하지 않는다. 기존 workflow는 PR에서 의도된 provenance skipped를 검사한 뒤 품질 단계를 실행하므로 근거 없이 분리·재작성하지 않는다. 후보 파일 수가 8개를 넘는 이유는 정책 전환 문서와 테스트 때문이며 신규 서비스 증가는 0이다.

### 1. 아키텍처: E1/E2

- **E1 [P1, 신뢰도 10/10]** `.github/settings/main-protection.json:2`의 `"required_status_checks": null`은 필수 검사 목표와 다르다. `:11`의 `"required_linear_history": true`도 일반 merge 지원과 충돌한다. strict + 실제 체크 context/app ID, linear=false로 계획한다. `required_pull_request_reviews`는 null이 아닌 객체·approval=0 유지. app ID는 조회 전 임의 상수로 쓰지 않는다.
- **E2 [P1, 신뢰도 9/10]** `.github/workflows/security-gate.yml:48`의 `name: security-gate`와 `workflow-policy.test.mjs:274`의 `assert.equal(canonicalWorkflowDigest(source), reviewedWorkflowSha256);`는 같은 변경에서 교체 가능하다. digest는 독립된 승인 근거가 아니다. workflow·검증 스크립트·package script의 후보 diff와 실제 job 단계 결과를 소유자가 확인한다. 서버 보호 목표의 전제는 신뢰된 소유자와 검토된 검사 정의다.

```text
목표 JSON --[신규 설정 정책 테스트]--> 검토된 설정
PR workflow --[기존 구조/digest 테스트]--> 변경 실수 탐지
      |-- PR: provenance skipped -> guard -> 필수 품질 단계
      |-- main push: 연관성 조회 success -> guard -> 필수 품질 단계
      |                                failure -> 품질 중단 -> 조사/재실행
원격 보호 API <- 승인된 관리자 적용 -> GET read-back + 원격 시나리오
```

보호 API 결과는 로컬 파일과 별개다. 403/404를 보호 없음이라고 단정하지 않고 권한·플랜·대상 식별을 확인한다. 기존 규칙/ruleset 충돌이면 자동 덮어쓰지 않는다. 공개 여부와 보호 여부, 비밀정보 보호 여부를 각자 기록한다.

### 2. 품질·유지보수: E3/E4

- **E3 [P2, 신뢰도 10/10]** `.github/pull_request_template.md:10`의 `PR head SHA와 CI가 검사한 SHA가 같다.`는 PR 기본 checkout이 임시 병합 ref를 사용하는 경우와 맞지 않는다. H=head, B=base, C=실제 테스트 SHA, run URL/event를 별도 필드로 바꾼다. `workflow-policy.test.mjs:550`의 대응 assertion도 함께 고친다. 원본 head 범위 secret scan과 병합 결과 품질 테스트를 혼동하지 않는다.
- **E4 [P2, 신뢰도 10/10]** 같은 템플릿 `:21`은 무료에서 보호가 강제되지 않는다고 고정한다. 전환 전/후 실제 read-back 상태를 기록하는 문구로 교체한다. 과거 문서는 역사로 보존하고 상단의 현재 상태만 교정한다. 기존 코드의 PR 연관성 함수명을 대규모 변경하는 일은 편익보다 파급이 커서 제외한다.

### 3. 테스트 지도

범례: EXISTING=소스에서 확인한 테스트, GAP=새 계획, LIVE=승인된 원격 검증 필요. 기존 테스트 존재와 이번 실행 성공은 별개다.

```text
설정 JSON [GAP: 신규 node:test]
  required_status_checks null/누락 -> 실패
  strict false, context 누락/중복/잘못된 이름 -> 실패
  app_id 누락/-1/0/문자열 -> 실패 (실제 값은 원격 증거로 검증)
  PR 객체 null, approval !=0, enforce_admins false -> 실패
  linear true, force/delete true -> 실패
  승인된 목표 설정 -> 통과
workflow [EXISTING: workflow-policy.test.mjs]
  권한/secret/Action SHA/full history/필수 단계/순서/digest
  PR + 의도된 skipped -> 품질 단계 실행
  main + failure/cancelled/skipped/누락 -> 고정 오류
  [GAP] 새 보호 정책과 PR 템플릿의 H/B/C 증거 문구
PR 연관성 [EXISTING: merge-evidence.test.mjs]
  정상 merge/single-result, 불일치 PR/부모/SHA, malformed -> 판정
  [GAP] 간접 병합 1부모/2부모가 연관성 검사를 만족할 수 있음을 고정
GitHub HTTP [EXISTING: github-merge-evidence.test.mjs]
  고정호스트, redirect, timeout, 1MiB, 3page, 후보0/복수, 취소
원격 사용자 흐름 [LIVE, 미실행]
  PR 실패/취소/미실행 -> 병합 차단
  stale base -> 업데이트/재검사
  정상 후보 + source/app 확인 + 본인 확인 -> 허용 -> main 사후 검사
  skipped/neutral/동명 대체 -> GitHub의 한계 기록 + 소유자 병합 금지
  보호 조건 미충족 push -> 승인된 무민감 fixture에서 거부 증거
```

새 단위 테스트는 RED→GREEN→회귀 순서로 작성한다. 간접 병합 테스트는 새 구현으로 거부시키려는 테스트가 아니라 보장 한계를 보존하는 회귀다. skipped/neutral 또는 동일 앱 대체 job을 GitHub가 반드시 거부한다고 기대하지 않는다. 정상 승인된 workflow에서는 필수 job/단계가 실제 실행되는지 검사하고, 조작된 정의는 본인 검토로 거부하는 잔여 경계다.

검증 계획은 [별도 테스트 계획](2026-09-28-public-repository-test-plan.md)에 저장한다. 앱 라우트/E2E 확대나 LLM eval은 신규 제품 경로가 없어 불필요하다. 기존 전체 verify·인증 coverage·폐기 DB/브라우저 회귀는 후속 코드 변경 뒤 유지한다.

### 4. 성능·실패 결합: E5

**E5 [P2, 신뢰도 10/10]** workflow `:76`의 `Require the expected provenance result`가 실패하면 뒤 품질 단계가 실행되지 않는다. 조회기는 전체 10초·응답 1MiB·최대 3페이지 제한이다. 둘 다 확인했다. 대안은 품질을 독립 실행하고 최종 job을 합치는 구조지만 job·필수 체크·정책 테스트의 변경 범위가 커진다.

**이번 선택:** 현재 결합을 유지하고 조회 장애를 분류한 뒤 동일 SHA·이벤트를 재실행한다. 품질 테스트 미실행을 통과로 표시하지 않는다. 반복 장애가 실제 관측될 때 분리 계획을 별도 제시한다. 새 캐시·자동 재시도·N+1 DB 쿼리는 도입하지 않는다. 10배 PR 부하에서는 CI 대기/strict 재실행이 병목이며, 100배는 현재 1인 운영의 범위를 넘어 실행 정책을 재검토해야 한다. 앱 FCP 개선 수치를 만들지 않는다.

## Phase 3.5 — DX: 초급 개발자 운영 경험

### 사용자와 처음 읽는 사람의 관점

대상은 Windows/PowerShell을 사용하는 한국어 1인 개발자이며, 개발 흐름을 배우면서 보안 설정을 관리한다. 제품 유형은 개발 운영 문서+기존 CLI/플랫폼이다. 전체 가계부 API/SDK 디자인 리뷰가 아니다. 기다릴 수 있는 시간은 측정하지 않았으며, 첫 안전한 확인을 5분 안에 끝내도록 안내하는 것을 목표로 둔다.

아래는 실제 명령을 처음부터 실행한 사용자 실험이 아니라 현재 문서를 읽고 구성한 1인칭 사용성 분석이다.

> 나는 README에서 인증은 구현됐지만 실제 장부는 아직 없다는 설명을 먼저 읽는다. 무엇을 테스트할 수 있는지는 이해된다. 하지만 저장소 보호 작업을 시작하려면 문서 전체 지도, 보안 운영 문서, 별도 설계 기록을 차례로 찾아야 한다. 어떤 문서가 현재 정책인지 바로 알기 어렵다. 문서 지도는 9월 9일 기준인데 이번 설계는 9월 24일이고, 무료 플랜 문서는 여전히 비공개 상태를 설명한다. 과거 기록인 것인지 지금도 적용되는 것인지 다시 묻게 된다.
>
> 운영 문서에서 pnpm setup:hooks를 발견한다. 그전에 Node와 pnpm을 설치해야 하는지는 다른 가이드에서 확인한다. 테스트가 성공하면 서버 보호도 켜진 것인지 헷갈린다. 목표 설정 JSON은 있지만 그 파일을 저장하는 것과 GitHub 서버에 적용하는 것은 다르다는 안내가 중요하다. PR 템플릿에서는 head SHA와 검사 SHA가 같아야 한다고 쓰여 있다. GitHub에 다른 SHA가 보이면 잘못 실행한 것인지 판단할 수 없다. 성공 표시가 있어도 건너뛴 단계가 있는지, 어떤 실행을 승인해야 하는지도 알고 싶다.
>
> 오류가 나면 안전하게 멈추고 싶다. 나는 토큰을 복사해 질문하는 대신 오류 코드와 실행 링크만 전달하고 싶다. 공개 전환과 테스트 명령이 같은 블록에 섞여 있으면 실수할 수 있다. 읽기 확인부터 시작해서 결과가 정상인지 확인한 뒤 다음 단계로 가는 짧은 안내가 필요하다. 마지막에는 지금 가능한 일과 내가 아직 승인하지 않은 일이 명확히 보였으면 한다.

### 비교 근거와 첫 성공 경험

| 비교 대상 | 참고할 경험 | 시간 근거 |
| --- | --- | --- |
| GitHub 보호 브랜치 안내 | 설정별 효과·예외를 분리 | 공식 문서에 이 프로젝트 TTHW 측정 없음 |
| gh pr checks | pass/fail/pending/skipping/cancel 구분 | 공식 CLI 문서, 준비 시간 미측정 |
| GitHub 외부 PR 실행 승인 | 실행 승인과 병합 승인 분리 | 공식 운영 안내, 시간 미측정 |
| 이번 저장소 | 기존 명령+짧은 한국어 결과 해설 | 아래 목표값만 제안, 실측 아님 |

새 playground 대신 읽기 전용 첫 확인을 제공한다. 사전에 GitHub CLI 로그인과 저장소 접근이 준비됐을 때 다음 명령으로 공개 상태를 읽고, `false`이면 아직 비공개임을 이해하는 것이 첫 성공 경험이다. 명령은 상태를 바꾸지 않는다.

```powershell
gh api repos/jawon0407/account-book --jq '{private: .private, default_branch: .default_branch}'
git rev-parse HEAD
```

이는 보호 확인 명령이 아니다. 이어 실제 보호 read-back은 별도 절에서 다루며 403/404는 진단이 필요하다고 설명한다. 설치/인증/전체 CI/공개 감사까지 5분에 된다고 약속하지 않는다. 로컬 테스트는 별도 단계로 기존 `pnpm test:security-gate`를 사용한다.

### 오류 3가지: 현재 안내와 보완

1. `MAIN_MERGE_EVIDENCE_UNAVAILABLE`: 기존 코드/문서에 이미 확인 불가와 재실행 안내가 있다. 여기에 “main 품질 단계도 실행되지 않았을 수 있음”과 run/SHA 확인 위치를 연결한다.
2. 보호 조회 403/404: 권한 부족·플랜·대상 오류 가능성을 분리하고 “필수 검사 없음”으로 해석하지 않는다. 관리자 권한 확대나 유료 전환은 자동 제안/실행하지 않는다.
3. PR H≠테스트 C: 오류로 단정하는 기존 체크박스를 없애고 merge-ref C가 승인된 H/B에서 생성됐는지 확인하도록 한다. 무관한 과거 성공 실행이면 중단한다.

## Implementation Tasks — 수동 통합 실행 후보

jq가 없어 스킬의 자동 JSONL 집계는 실행하지 않았다. 설치는 하지 않았으며 아래가 중복 제거한 수동 목록이다. 자동 집계가 필요하면 jq 설치를 별도 결정한다. 공수는 코드·문서 작업의 거친 예측이고 외부 대기·감사 범위는 제외한다.

1. **T1 / P1 — 목표 보호 설정과 RED/GREEN 테스트.** E1에서 도출. 실제 check 앱 식별자 조회 후 JSON 정책 테스트→설정 수정. 기존 workflow는 읽기 검토만 하며 근거 없는 수정 없음. 사람 약 2~4시간 / AI 보조 약 1~2시간 예상, 검증 지연 별도.
2. **T2 / P1 — 검사 신뢰와 후보 증거 정합성.** C1/C3, E2/E3/E4, D4에서 도출. PR 양식·정책 테스트·간접 병합 한계 테스트를 수정하고 최종 후보 본인 확인을 명시. 사람 약 2~4시간 / AI 보조 약 1~2시간 예상.

4. **T4 / P1 — 로컬 회귀·독립 리뷰.** 위 테스트 계획에 따라 집중 검사→verify→coverage; DB/브라우저는 명시적 폐기 환경에서만. 시간은 환경·실행 결과에 따라 측정. 여기까지는 로컬 보완 묶음이다.
5. **T5 / P1 — 공개 대상 전수 점검과 최종 승인 자료.** C2에서 도출. refs/이력뿐 아니라 PR·댓글·로그·첨부·권리·연결된 공개 자료를 목록화. 미검증이 있으면 공개 보류. 공수는 자료 목록 확인 전 미정.
6. **T6 / P1 — 별도 승인 후 공개·보호 적용·원격 검증.** 현재 자동 실행 승인 없음. 원격 read-back, 정상/거부 fixture, 본인 확인 후 정상 PR, main 사후 검증과 독립 확인이 있어야 P1 종결. 원격 자원·push/merge 권한은 그때 따로 확인한다.

추천 순서는 T1→T2→T3→T4→T5→공개 최종 승인→T6→10-A2다. T5가 실패해도 T1~T4 작업은 비공개로 보존하며 공개하지 않는다. 공개 전 검증 완료를 빨리 보고하려고 T5를 생략하지 않는다.
