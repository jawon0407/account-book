# 개인 알림 가계부 요구사항과 선택형 자동 분류 설계

최초 작성: 2026-10-07. 최신화: 2026-10-13, 한국시간. 대상: 사용자, 초급 개발자, 로컬·클라우드 개발 담당자.

최신 상태·데이터 책임·보관·집계·검증 기준은 [통합 설계서](2026-10-13-notification-ledger-data-flow-design.md)를 함께 읽는다. 아래는 제품 요구사항 요약이며, 코드·실제 DB 적용 완료 보고서가 아니다.

**자동 분류 규칙은 선택 기능이다. 가입·계좌 지정·알림 기록·수기 입력·조회에 규칙 생성을 강제하지 않는다.** 규칙이 없어도 명확한 입출금은 미분류 거래로 기록하고 입출금 합계에 포함한다. 사용자가 직접 분류하거나, 원할 때만 이후 거래의 자동 분류를 설정한다.

## 1. 문서 상태와 우선순위

- 사용자 확정: 개인 장부 우선, 실계좌 API 제외, 알림과 수기 기록, PC 기존 거래 조회·수정·삭제·30일 복구, 조회 필터 원칙, 미분류 합계 포함·알림, 사용자 선택형 분류 규칙.
- 사용자 확정: 거주 기준 시간대 고정, 거래 시각 우선순위, 정확 일치·명시 별칭·금액/시간 경계, 단계형 설정·판독 실패 구분. 시간 조건 규칙의 수신 시각 대체는 기본 꺼짐·규칙별 선택이다. 원장 자체는 시각을 모르면 최초 수신 시각을 추정 표시해 기록할 수 있다.
- 아래 DB 이름·열, 처리 모듈, 세부 UI는 **구현 전 설계 후보**다. SQL/API 구현·실제 DB 적용 완료를 뜻하지 않는다.
- 보관·환불·이체·실패 대응의 승인 정책은 통합 설계에 반영했다. 모바일 인증·실제 DDL·오류/동시 처리·자료별 보관 계약과 파일별 실행 계획은 후속이다. autoplan 전체 검토 완료나 54개 엣지케이스 검증 완료를 주장하지 않는다.
- 충돌할 때 10/13 통합 설계와 이 요구사항의 최신화 내용을 이전 개인/공동 장부·은행 연결 문서보다 우선한다. 이후 명시적 사용자 결정은 날짜와 함께 반영한다. 보안 기준을 자동으로 낮추는 문서가 아니다.
- 관련: [클라우드 인수인계](../../status/2026-10-07-personal-notification-ledger-handoff.ko.md), [문서 지도](../../README.md).

## 2. 제품 범위

### 이번 목표

1. 별도 Android 앱에서 사용자가 선택한 금융 앱·카카오톡·문자 앱의 새 금융 알림을 판독해 실제 계좌 입출금을 기록한다. 과거 대화·문자함은 조회하지 않는다.
2. PC 웹과 모바일은 같은 계정의 서버 장부를 공유한다. PWA로 대체하지 않는다.
3. 앱이 놓쳤거나 해석하지 못한 거래는 모바일 수기 입력으로 보완한다.
4. PC는 기존 기록의 조회·필터·수정·삭제·복구 중심으로 전환한다. 신규 거래 작성은 모바일이며 기존 PC 작성 자료는 보존한다.
5. 사용자 정의 계좌·카테고리, 선택형 자동 분류, 미분류 안내를 제공한다.

### 후속 또는 별도 설계

- 공동 장부·운영진 초대·총무 검토·라온 연동.
- AI 소비패턴 분석. 사용자 규칙 실행을 AI 학습으로 표현하지 않는다.
- 실계좌 연결·잔액 조회·송금 API. 기존 은행 관련 코드와 미완성 작업을 임의 삭제하지 않는다.
- iOS의 알림 수집 방식. Android와 동일하게 동작한다고 약속하지 않는다.
- 현금 이동 없는 카드 승인·청구 예정은 기록하지 않는다. 실제 체크카드 출금은 기록 대상이다. 출처 불명 합산 카드대금의 구매별 분해는 보류한다.
- 환불 N:M·같은 구매 묶음 삭제/복구·이체 원금/수수료 구분은 승인 정책이다. 저장·집계·관계 무결성의 상세 계약은 통합 설계에서 구분한다.

채택한 A안은 Next.js 웹, NestJS/Node.js API, Supabase PostgreSQL과 공용 TS 계약을 재사용하고 React Native/Expo 앱 및 Android 네이티브 수집 모듈을 추가하는 방식이다. 화면은 TS/TSX, HTTP는 ky, 서버 상태는 TanStack Query를 사용한다.

## 3. 혼동하지 말아야 할 개념

| 개념 | 설명용 예시 | 의미 |
| --- | --- | --- |
| 장부 계좌 | 토스뱅크 생활비 | 사용자가 지정한 기록 묶음. 은행 소유 인증 완료가 아님 |
| 알림 출처 | 금융 앱과 알림 유형 | 어떤 앱의 어떤 종류 알림에서 읽었는가 |
| 거래 대상 | 거래 상대 A, KG이니시스 | 알림에 표시된 받는 쪽 또는 보내는 쪽 |
| 대상 유형 | 개인, 업체·기관, 미확인 | 사용자 지정 정보. 이름만으로 신원을 증명하지 않음 |
| 실제 이용처 | 예시 체육관 | 거래 대상과 다를 수 있는 선택적 사용처 |
| 카테고리 | 체육관 입장비, 장보기, 회식 정산 | 이번 거래 목적. 사용자가 정의 |
| 자동 기록 | 명확한 알림을 거래로 저장 | 카테고리 자동 분류와 독립된 기능 |
| 자동 분류 규칙 | 조건에 맞으면 체육관 입장비 | 사용자가 선택·활성화한 경우에만 실행 |

이 문서의 이름·금액·요일·시각은 설명용 합성 사례이며 실제 거래 자료가 아니다. 기본 거래 분류와 조회의 복수 선택은 거래에 여러 태그를 붙이는 기능과 다르다. 이체 수수료·환불 배분의 세부 금액과 카테고리 필터 관계는 통합 설계의 후속 집계 계약에서 확정한다.

## 4. 기본 기록과 분류 흐름

```text
동의한 금융 알림 수집 → 해석·계좌 확인·재전송/중복 후보 검사
  ├─ 금융 거래 여부조차 판단 불가/비대상 → 거래 생성 안 함, 원문 보관 안 함
  ├─ 계좌·금액·방향 불명확 또는 중복 의심 → 확인대기, 추가 금액 미반영
  └─ 장부 기록 가능 → 거래 한 건 저장, 입출금 합계 반영
       ├─ 사용자가 활성화한 분류 규칙이 명확히 일치 → 자동 분류
       └─ 규칙 없음/꺼짐/불일치/충돌/매번 확인 → 미분류, 사용자 안내
```

### 4.1 내 계좌 확인

- 로그인·거주 시간대 선택 후 수기 이용부터 가능하다. 자동 기록 동의·OS 접근·수집 앱·서비스 연결은 별도 확인한다. 처음부터 모든 계좌/규칙 설정을 강제하지 않는다.
- 사용자별로 금융 앱·알림 유형·제공된 부분 계좌 식별값을 장부 계좌와 연결한다.
- 알림 출처 앱과 실제 은행을 구분한다. 중계 앱이 다른 은행 알림을 제공할 수 있으므로 앱 이름만으로 계좌를 선택하지 않는다.
- 식별값이 없는 알림은 사용자가 해당 알림 유형의 기본 계좌를 명시적으로 지정할 수 있다.
- 계좌가 미지정이면 기존 계좌 연결, 새 장부 계좌 등록, 나중에 설정, 수집 제외를 안내한다.
- 계좌 뒷자리 충돌이나 여러 규칙의 불일치는 추측으로 해결하지 않는다.
- 알림만으로 본인 명의 계좌인지 검증하지 않는다. 계좌 지정과 카테고리 규칙 생성은 별개다.
- 권한 거부·수집 중지·미지원 형식이어도 기존 장부와 서버에 연결 가능한 상태의 수기 입력을 유지한다. 알림이 없다는 사실을 은행 거래 없음으로 표현하지 않는다.

### 4.2 처음 보는 거래 대상

1. 장부 기록 가능 조건이 충족되면 미분류로 먼저 저장한다.
2. 사용자가 분류 화면을 열었을 때 대상 유형과 이번 거래의 카테고리를 지정한다.
3. 실제 이용처·메모는 필요할 때 입력한다. 처음 보는 대상의 확인 때문에 기록 자체를 막지 않는다.
4. 카테고리 선택만으로 자동 분류 규칙을 만들거나 활성화하지 않는다.
5. 업체·기관은 원할 때만 '다음부터 자동 분류'를 선택한다. 선택하지 않으면 이후에도 직접 확인한다.

개인 상대는 같은 이름이라도 목적이 달라질 수 있으므로 이전 분류 후보를 보여주고 매번 선택하는 흐름을 기본으로 한다. 이름만으로 동일인을 확정하거나 다른 사용자의 분류를 가져오지 않는다.

### 4.3 다시 만난 거래 대상

- 이전에 장보기로 분류한 상대에게 다시 출금되어도 같은 목적이라고 단정하지 않는다.
- 직접 확인 모드에서는 이전 분류 사용, 다른 분류 선택, 나중에 분류를 제공한다.
- 날짜·금액·원래 거래 대상명은 새 거래 값이다. 이전 거래 전체를 복사하지 않는다.
- 이번 건만 수정과 앞으로의 규칙 수정은 별도 동작이다. 과거 거래는 자동 일괄 변경하지 않는다.

입금도 계좌 확인 → 대상 확인 → 입금 목적 분류 → 선택적 규칙 순서로 처리한다. 입금/출금 방향만으로 소득/소비·환불·내 계좌 간 이체까지 확정하지 않는다.

## 5. 미분류와 확인대기

| 상태 | 원장·합계 | 사용자 처리 |
| --- | --- | --- |
| 분류 완료 | 거래와 입출금 합계에 포함 | 필요하면 수정 |
| 목적만 미분류 | 거래와 입출금 합계에 포함, 카테고리는 미분류 | 직접 분류 또는 선택적 규칙 설정 |
| 금융 후보이나 계좌·금액·방향 불명확 | 최소 추출값의 확인대기, 확정 전 합계 제외 | 누락 정보 확인 |
| 중복 의심 | 불확실한 추가 건은 합계 제외, 기존 확정 건 유지 | 기존 건 연결 또는 별개 거래 확인 |
| 광고·OTP 등 비대상 | 거래로 만들지 않음 | 기록 대상에서 제외 |
| 본문 숨김·미지원으로 금융 여부조차 판독 불가 | 거래로 만들지 않음, 원문 보관하지 않음 | 판독 한계·수기 경로 안내 |

미분류를 장보기로 바꾸면 전체 입출금 합계는 그대로이며 카테고리별 집계만 이동한다. 전체 검색에는 미분류도 포함하고 특정 카테고리 검색에서는 그 선택 조건을 따른다. 합계는 현재 내려받은 한 페이지가 아니라 조건에 맞는 전체 거래를 기준으로 계산한다.

### 미분류 알림

- 새 미분류 거래가 생기면 사용자에게 알린다. 알림을 누르면 미분류 목록으로 이동한다.
- 첫 새 확인 사항부터 고정 60초 동안 묶어 '분류가 필요한 거래 3건'처럼 안내한다. 새 건으로 창을 연장하거나 원장 저장을 지연시키지 않는다. 앱 안에서도 현재 건수를 표시한다.
- 이미 분류한 건을 계속 재알림하거나 동일 접수 재시도로 알림을 중복 발송하지 않는다.
- 자동 분류 완료 거래에는 미분류 알림을 보내지 않는다.
- 잠금화면 안내는 기본적으로 상세 계좌·상대·금액을 숨긴다. OS 알림 권한이 없으면 앱 내부에서 안내한다.
- 우리 앱이 만든 안내 알림을 금융 거래로 다시 수집하지 않는다.
- 발송 전 해결한 건은 제외하고 전부 해결되면 취소한다. 같은 사유의 반복·일일 독촉은 하지 않는다. 기존 거래에 새 사유가 생기면 그 사유에 대해 한 번 안내할 수 있다.
- 60초는 논리적 묶음 기준이지 OS 배달 보장이 아니다. 다중 기기·경계 동시 처리의 세부 계약은 후속이다. 안내 클릭/삭제만으로 거래의 확인 사유를 해결하지 않는다.

## 6. 선택형 자동 분류 규칙

### 6.1 기본값과 조건

**기본은 규칙 없음/자동 분류 꺼짐이다.** 앱 사용을 시작하기 위해 규칙을 만들 필요가 없다. 규칙 사용에 동의한 경우에만 다음 조건을 저장한다.

| 조건 | 초기 설계 |
| --- | --- |
| 소유 사용자 | 서버 인증 문맥으로 결정. 다른 사용자에게 공유하지 않음 |
| 대상 장부 계좌 | 해당 사용자의 계좌를 명시. 모든 계좌로 암묵 확대하지 않음 |
| 알림 출처·거래 대상 | 사용자 확인한 앱/유형 및 거래 대상 정확 일치·명시 별칭 |
| 방향 | 입금 또는 출금 규칙을 분리 |
| 적용 카테고리 | 사용자 소유·사용 가능한 해당 방향의 카테고리 |
| 요일 | 선택 사항. 선택한 요일 중 하나면 충족 |
| 시간대 | 선택 사항. 거주 기준에서 시작 포함·종료 제외, 자정 넘김은 시작 요일 |
| 금액 | 선택 사항. 정확 금액 또는 양 끝 포함 범위, 최소>최대는 거부 |
| 시각 대체 허용 | 기본 꺼짐. 거래 시각이 없을 때 기기 알림 수신 시각을 쓰도록 별도 선택 |

조건 항목 사이는 AND다. 예를 들어 화요일 또는 목요일이면서 계좌·방향·대상·선택한 시간대가 모두 맞아야 한다. 요일/시간/금액을 선택하지 않은 것은 해당 조건 제한이 없다는 뜻이다. 이 규칙의 요일 복수 선택과 거래 조회 화면의 단일 기간 선택은 서로 다른 설정이다.

저장 화면은 기본 항목과 '조건 추가'로 나누고 적용 범위를 문장으로 확인시킨다. 알림에 없는 이용처·거래번호·위치를 알고 있다고 가정하지 않는다. 자동 분류를 위해 GPS 등 새 권한을 요구하지 않는다.

부분/유사 이름 일치는 하지 않는다. 앞뒤 공백 등 최소 정리를 넘어 지점·숫자·내부 공백·마스킹을 임의 삭제해 대상을 합치지 않는다. 별칭은 사용자가 해당 범위에서 지정하며 과거 기록을 자동 일괄 변경하지 않는다.

### 6.2 합성 예시와 한계

> 생활비 계좌에서 화·목요일 18:00 이상 20:00 미만에 KG이니시스로 출금되면 체육관 입장비로 분류한다.

- 목요일 18:35, 나머지 조건 일치: 자동 분류.
- 목요일 21:00 또는 일요일 18:35: 이 규칙은 적용하지 않음.
- 같은 시각의 입금이나 다른 계좌: 이 출금 규칙은 적용하지 않음.
- 적용 가능한 규칙이 없다면 미분류로 기록·합계 반영·알림.
- 서로 다른 카테고리 규칙이 충돌하면 임의 우선순위로 확정하지 않고 미분류로 안내.

KG이니시스는 결제대행사이므로 표시 대상과 실제 이용처가 다를 수 있다. 같은 계좌·대상·금액·요일·시각 조건에 다른 구매까지 들어오면 알림 정보만으로 구별할 수 없다. 자동 분류는 사용자 규칙의 결과이지 실제 이용처를 검증한 결과가 아니다.

원래 거래 대상명은 보존하고 분류 출처를 '사용자 규칙'으로 표시한다. 이번 거래만 정정하거나 규칙을 수정·비활성화할 수 있어야 한다. 본인이 고친 거래를 재수집·규칙 재실행으로 덮어쓰지 않는다.

### 6.3 거래 시각과 알림 시각

1. 사용자 확인 시각 → 본문 거래 시각 → 같은 거래로 확인된 알림의 최초 기기 수신 시각(추정) 순서다. 사용자 정정은 늦은 알림으로 덮어쓰지 않는다.
2. 원장에 추정 시각을 표시해 기록·합계 반영하는 것과 시간 조건 규칙에 그 값을 쓰는 것은 별개다. 규칙은 기본적으로 추정 시각을 사용하지 않는다.
3. 해당 규칙에서 대체를 허용한 경우에만 추정 수신 시각을 시간 조건 판단에 사용한다. 서버 업로드 시각은 대체값으로 사용하지 않는다.
4. 거래 시각/수신 시각·정밀도·추정 근거를 구분한다. 본문 시각끼리 충돌하면 확인 대상으로 두고 날짜만 아는 과거 기록에 시각을 만들어 넣지 않는다.
5. 시각 조건이 없는 규칙은 시각이 없다는 이유만으로 실패시키지 않는다.

처음 선택한 거주 지역의 IANA 시간대로 조회·집계·규칙 기준을 고정한다. 여행·휴대폰 시간대 변경으로 기준이나 과거 기록을 바꾸지 않는다. 출처 시간대를 알 때만 정확히 환산하며 이미 거주 기준인 시각을 이중 환산하지 않는다. 실제 거주지 변경 정책은 별도다. 경계는 '18:00 이상 20:00 미만', '금요일 23:00~다음 날 01:00'은 금요일 시작으로 해석한다. 같은 시작/종료 시각을 임의 24시간으로 해석하지 않으며 판단할 정밀도가 없으면 억지로 일치시키지 않는다.

## 7. 조회 필터와 PC 역할

- 기본값은 모든 필터 미선택이며 전체 기간·계좌·카테고리를 조회한다.
- 계좌와 카테고리는 각각 복수 선택 가능. 각 묶음 안은 OR, 묶음 사이는 AND다.
- '전체'는 개별 선택과 동시 선택하지 않고 해당 필터 해제와 같은 뜻이다.
- 기간은 특정 일/주/월/년 또는 직접 날짜 범위 중 최대 한 가지 방식이다.
- 직접 날짜 범위는 계좌·카테고리와 결합할 수 있지만 다른 기간 방식과 함께 적용하지 않는다.
- 특정 주는 월~일 달력 기준, 직접 범위는 시작일·종료일 모두 포함한다. 내부 비교는 거주 시간대의 시작일 이상·종료 다음 날 미만이며 DST를 고려한다.
- 최신 날짜·시각 우선이며 시간 미상을 표시한다. 동일 시각은 안정적인 ID 보조 정렬을 사용하되 실제 은행 처리 순서를 증명하는 값으로 설명하지 않는다.
- 전체 기간은 무제한 일괄 다운로드가 아니다. 서버 페이지 조회와 전체 조건 합계를 구분한다.
- 필터 변경 시 커서를 초기화하고, 거래 편집으로 검색 결과에서 제외되면 이유를 안내한다.

PC는 조회·필터·기존 거래 수정·삭제·30일 복구를 허용하고 새 거래 작성은 모바일 담당이다. 같은 구매로 엮인 지출/환불 삭제·복구는 범위를 보여주고 함께 처리한다. 계좌/카테고리 생성·규칙 관리 등의 기기별 세부 허용은 후속 권한표에서 확정한다. 버튼만 숨기거나 자칭 모바일 헤더만 믿는 접근 제어는 금지한다.

## 8. DB 확장 후보와 저장 책임

아래는 새 테이블 생성 완료 목록이 아니라 설계 후보다. 현 DB를 삭제·재생성하지 않고 추가형 migration을 설계한다.

| 기존 테이블 | 유지·보강 방향 |
| --- | --- |
| `user.users`, `user.roles`, `user.role_history` | 기존 사용자·권한 이력 유지. 금융 알림의 이름을 로그인 사용자 신원으로 사용하지 않음 |
| `finance.accounts` | 장부 계좌 유지, 금융기관/부분 표시 등 필요한 식별 정보 확장 검토 |
| `finance.transaction_categories` | 사용자별 입금/출금 미분류를 시스템 코드로 구별. 이름 충돌·중복 초기화·보관 방지 |
| `finance.transaction_history` | 발생 시각·정밀도·기록/분류 출처·거래 대상/이용처 관계 확장 검토 |
| `finance.account_transfers` | 기존 내 계좌 간 이동 유지. 알림 한쪽만으로 반대편 거래 생성 금지 |
| `finance.request_deduplication` | 같은 생성 요청 재시도 방지. 실제 거래 동일성 판정과 구별 |

| 신규 후보 | 책임 |
| --- | --- |
| `user.devices` | 수집 기기와 사용자 연결·철회. IMEI나 평문 인증 토큰을 저장하지 않음 |
| `notification.account_rules` | 금융 알림을 어느 장부 계좌에 연결할지 관리 |
| `notification.received_notifications` | 원문 없는 최소 추출 정보·시각 근거·해석 버전·처리 상태·장부 거래 연결 |
| `notification.review_history` | 불확실한 알림을 기존 거래에 연결/별개 거래로 확정/제외한 이력 |
| `finance.counterparties` | 사용자별 거래 대상 유형·표시 이름. 같은 이름을 전역 동일인으로 묶지 않음 |
| `finance.classification_rules` | 선택형 카테고리 조건·활성 상태·version·시각 대체 정책 |
| `finance.transaction_change_history` | 일반 거래의 사용자 수정과 분류 변경 이력. 알림 검토 이력과 구별 |

원장의 적용 규칙 ID/버전과 분류 출처를 추적하는 방안을 검토한다. 구매 묶음·환불 N:M 배분·세부 금액·삭제/복구 묶음·최소 실패 표식의 책임은 통합 설계에 추가했다. 이 표의 물리 이름은 후보이며 즉시 생성 지시가 아니다. 별칭 저장 방식·필드별 제한·감사 이력 수명은 상세 DB 명세에서 확정한다. 모든 관계의 같은 사용자 소유를 서버와 DB에서 검증한다.

기존 수입/지출은 DB CHECK에서 카테고리를 필수로 요구한다. `category_id` 열의 NULL 허용 여부만 보고 NULL로 미분류를 저장하면 안 된다. 초기안은 기존 제약을 유지하고 서버 관리 미분류 카테고리를 참조한다. 사용자별 기본 분류가 없을 때의 생성 경쟁도 검증한다.

시각·분류 열을 추가할 때 SQL trigger, 열별 GRANT, 공용 계약, 저장소 매핑, Drizzle 선언을 함께 검토한다. 과거 적용 migration은 수정하지 않는다. 이전 적용 도구와 Supabase CLI migration history가 같다고 가정해 무조건 `db push` 하지 않는다.

## 9. 보안과 오류 처리 원칙

- 새 사용자 테이블에도 사용자 소유 조건, 복합 외래키, RLS/FORCE RLS와 최소 권한을 설계한다. RLS는 DB가 행별 접근을 제한하는 기능이다.
- 금융·알림 데이터를 브라우저용 Data API에 노출하지 않는다. 모바일에 DB 비밀번호·서버 서명 비밀키를 넣지 않는다.
- 금융 앱 허용 목록과 알림 유형을 제한하고 OTP·일반 알림·불필요한 원문을 서버 전송/로그에서 제외한다.
- 앱이 올린 알림은 은행 검증 자료가 아니다. 서버가 사용자·계좌·분류·금액·요청 크기·빈도·재시도를 검증한다.
- 원문은 메모리에서 분석 후 폐기하며 DB·파일·오류 로그에 별도 보관하지 않는다. 추출한 금융 정보도 개인정보이며 최소 범위만 저장한다.
- 미전송 금융 payload의 장기 대기열·자동 재전송은 초기 범위에서 제외한다. 최소 요청/실패 표식은 최초 실패부터 최대 30일 보관하며 금액·상대·본문을 담지 않는다.
- 결과 불명이면 원래 요청의 서버 저장 결과를 확인한 뒤 미반영이 확인된 건만 모바일 수기 보완한다. 늦은 원래 요청과 수기 보완의 경쟁은 별도 원자적 계약으로 막는다.
- A 계정의 최소 표식은 A 재인증 때만 확인하고 B의 화면·건수·캐시에 노출하지 않는다. 일시 중지는 새 수집만 멈추며 동의 철회·탈퇴·삭제와 구분한다.
- 알림 누락·권한 해제·재부팅·앱 종료를 고려한다. 수집 상태 안내는 특정 거래가 누락되지 않았다는 증명이 아니다.
- 같은 분·금액·이름의 정상 반복 거래를 자동 병합하지 않는다. 알림 갱신·묶음 요약·여러 앱의 같은 거래·늦은 수신·수기 입력 중복을 별도로 검증한다.
- 알림창에서 알림을 지워도 장부를 삭제하지 않는다. 사용자가 삭제/제외한 거래를 재접수로 부활시키지 않는다.
- 사용자 수정은 버전 충돌로 보호하고 자동 분류 재실행이 덮어쓰지 않게 한다. 이미 보관된 계좌·분류의 과거 기록도 보존한다.
- 이체는 실제 두 원장 기록을 연결하고 원금을 소비에서 제외한다. 합산 출금의 수수료는 내부 세부 금액이며 부모 거래와 이중 집계하지 않는다. 없는 반대편 거래를 만들지 않는다.
- 환불은 사용자 지정 같은 구매 안의 N:M이며 각 실제 발생일을 유지한다. 초과 보상 연결과 원지출 없는 실제 환불 기록을 허용하되 실제 입금 초과 배분·관계 금액 이중 집계를 금지한다.
- 일반 삭제는 즉시 집계에서 제외하되 30일 복구용 데이터를 보호해 남긴다. 영구 삭제·백업·재접수 표식의 수명은 상세 계약과 운영 검증이 남아 있다.
- 계좌 보관은 수집 중지가 아니다. 유효한 연결·동의가 있으면 계속 기록한다. 카테고리 보관은 관련 규칙을 비활성화하고 복원 시 자동 활성화하지 않는다.
- 잔액을 표시한다면 '장부 기준'이라고 알린다. 시작 잔액 미설정을 0원으로 표시하지 않는다.

## 10. 필수 검증 시나리오

다음은 구현 시 수행할 인수 기준이며 이 문서 작성으로 통과한 테스트가 아니다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 규칙을 한 개도 만들지 않고 시작 | 알림/수기 기록·조회 사용 가능, 규칙 강요 없음 |
| 계좌·금액·방향은 명확하고 목적만 미분류 | 한 건 저장, 입출금 합계 포함, 미분류 안내 |
| 미분류를 사용자가 분류 | 총액 유지, 카테고리 집계만 변경, 자동 규칙은 생성 안 됨 |
| 같은 상대와 다른 목적의 새 거래 | 이전 후보를 제시하고 이번 거래만 선택 가능 |
| 선택·활성화한 규칙 없음/비활성 | 과거 분류가 있어도 무단 자동 적용 안 함 |
| 선택형 규칙의 모든 조건 일치 | 해당 사용자 카테고리로 분류, 규칙 근거 추적 |
| 요일만 일치/시간만 일치/다른 방향/다른 계좌 | 전체 조건이 충족되지 않으면 해당 규칙 미적용 |
| 18:00 이상 20:00 미만 | 18:00 포함, 20:00 제외 |
| 금요일 23:00~다음 날 01:00 | 토요일 00:30 포함, 01:00 제외 |
| 거래 시각 미상, 대체 꺼짐/켜짐 | 시간 조건 미적용 또는 수신 시각 사용 근거 표시 |
| 서버 전송이 수시간 지연 | 서버 도착 시각으로 요일·시간 분류하지 않음 |
| 서로 다른 카테고리 규칙 충돌 | 미분류·이유 안내, 임의 첫 규칙 선택 금지 |
| 같은 거래 재전송 | 원장 금액과 미분류 안내가 중복 증가하지 않음 |
| 서로 다른 정상 거래의 내용이 동일 | 단순 지문 중복으로 실제 거래를 잃지 않음 |
| 수기 입력 뒤 늦은 알림 | 중복 후보 연결/별개 거래 판단, 무조건 두 번 집계하지 않음 |
| 자동 분류 정정·규칙 변경 | 이번 건/이후 규칙 분리, 과거 일괄 덮어쓰기 없음 |
| A/B 사용자·계정 전환·기기 철회 | 타인 원장/규칙/최소 표식·건수 노출 및 잘못된 계정 전송 차단 |
| 다중 필터와 직접 기간 | OR/AND·기간 배타성·날짜 경계·페이지/전체 합계 일치 |
| PC와 모바일 동시 편집 | 버전 충돌 처리, 조용한 덮어쓰기 없음 |
| 미분류 여러 건/이미 분류/우리 앱 알림 | 묶음 안내·오래된 안내 정리·자기 알림 재수집 방지 |

공용 계약·API·폐기용 PostgreSQL에서 자동 검증하고, PC 변경은 Playwright로 확인한다. Android 수집은 합성 알림 테스트와 실제 기기 권한/백그라운드 검증을 분리한다. 사용자 실제 금융정보를 공개 테스트 fixture·스크린샷·로그에 넣지 않는다.

추가된 실패 경쟁·거주 시간대/DST·환불/삭제·보관 정책을 포함한 검증 묶음은 [통합 설계 §11](2026-10-13-notification-ledger-data-flow-design.md#11-구현-후-반드시-검증할-사례)에 있다. 문서 갱신은 테스트 실행이 아니다.

## 11. 대안과 다음 순서

이름만으로 항상 자동 분류하면 편하지만 결제대행사·동명이인 오분류가 생긴다. 모든 거래를 먼저 확인하게 하면 정확성을 관리하기 쉽지만 자동 기록 목적과 맞지 않는다. 선택한 방향은 **기록은 자동, 목적 미상은 미분류, 분류 자동화는 사용자가 선택**하는 조합이다.

다음은 통합 설계 검토 → 첫 하위 과제의 상세 계약·실행 계획 → DB/공용 계약·모바일 인증 → 기본 수기·계좌·분류·조회 → Android 수집/원장 반영 → 선택형 분류·안내 → 관계 집계·PC 편집/교차 검증 순서다. 단계마다 필요한 PC 표시와 테스트를 수행한다. 선택형 기능은 사용자에게 필수가 아니라는 뜻이지 개발 제외가 아니다.

남은 계약은 통합 설계 §12에 모았다. 승인한 원문 미보관·최소 실패 표식 30일·정확 일치·환불/이체 정책을 다시 묻지 않고 실제 필드·오류·동시 처리·보관 수명으로 구체화한다. 시작 잔액은 조건부 A안이며 파일·공수·검증 규모 보고 후 적용을 확인하고 부담이 크면 B안을 검토한다. 미확정 상세 항목을 클라우드 담당자가 임의로 '승인 완료'로 바꾸지 않는다.
