# 반응형 동기화 가계부 앱 설계

작성일: 2026-07-16

상태: 사용자 승인 완료

제품명: 구현 전까지 `Account Book`을 작업명으로 사용한다.

## 1. 목표

PC와 모바일에서 동일한 개인 재무 데이터를 안전하게 사용할 수 있는 로그인 기반 반응형 PWA를 만든다. 사용자는 어느 기기에서든 10초 안에 거래를 기록하고, 월간 예산과 전체 자산 흐름을 한눈에 파악할 수 있어야 한다.

첫 버전은 개인 사용에 집중한다. 가족·커플 공유는 후속 범위이며, OCR과 금융기관 자동 연동은 별도 단계로 구현한다.

## 2. 단계별 범위

### 1단계: 실사용 가능한 개인 가계부

- 이메일과 비밀번호 회원가입·로그인
- Google, Kakao, Naver 소셜 로그인
- 이메일 인증과 비밀번호 재설정
- 수입, 지출, 계좌 간 이체 기록
- 카테고리와 태그
- 월별 전체·카테고리 예산
- 반복 거래와 다음 생성일 관리
- 계좌와 자산의 수동 관리
- 월별·카테고리별·계좌별 통계
- CSV 가져오기와 내보내기
- 오프라인 입력과 재연결 동기화
- PC·태블릿·모바일 반응형 화면
- PWA 설치와 정적 앱 셸 캐시

### 2단계: 영수증 OCR

- 영수증 이미지 업로드와 안전한 저장
- OCR 추출 결과의 사용자 검수
- 가맹점, 날짜, 금액, 카테고리 후보 제안
- 확정된 결과만 거래로 저장

### 3단계: 금융기관 자동 연동

- 은행·카드 연동 제공자 선정과 계약 검토
- 계좌·카드 거래 수집과 중복 판정
- 수동 거래와 자동 수집 거래의 병합 흐름
- 동의, 철회, 보관 기간과 감사 기록

OCR과 금융기관 자동 연동은 1단계 UI에 비활성 메뉴나 예고 카드로 노출하지 않는다. 로드맵 문서에서만 관리한다.

## 3. 기술 아키텍처

### 3.1 구성

- 프런트엔드: Next.js 기반 반응형 PWA
- 백엔드: Node.js, NestJS, Fastify 어댑터
- 데이터베이스: Supabase 관리형 PostgreSQL
- 데이터 접근: Drizzle ORM과 명시적 SQL
- 인증: Supabase Auth
- 파일 저장: Supabase Storage
- 오프라인 저장: 브라우저 IndexedDB
- 계약과 검증: 공유 TypeScript 타입과 런타임 검증 스키마
- API 문서: OpenAPI

### 3.2 책임 경계

프런트엔드는 금융 테이블을 직접 수정하지 않는다. Supabase Auth에서 인증을 수행하고 발급받은 JWT를 Node API에 전달한다. Node API는 JWT, 데이터 소유권, 입력값, 버전을 검증한 뒤 PostgreSQL을 변경한다.

서비스 키와 데이터베이스 접속 정보는 서버에만 둔다. 금융 테이블은 비공개 스키마에 배치한다. 클라이언트 직접 조회가 필요한 표면을 추가하는 경우에만 공개 스키마와 RLS 정책을 별도로 설계한다.

Redis, 메시지 큐, 읽기 복제본, 테이블 파티셔닝은 초기 구성에 넣지 않는다. 측정된 병목이 생기면 요약 테이블, Materialized View, 캐시, 읽기 복제본, 날짜 파티셔닝 순으로 검토한다.

### 3.3 논리 흐름

```text
Next.js PWA
  ├─ Supabase Auth: 로그인과 JWT 갱신
  ├─ IndexedDB: 오프라인 데이터와 변경 대기열
  └─ Node API: 모든 금융 데이터 명령과 조회
       ├─ PostgreSQL: 관계형 데이터와 통계
       └─ Storage: 영수증 파일과 제한된 접근 URL
```

```text

│  └─ api/                 # NestJS + Fastify API

│  ├─ database/            # Drizzle 스키마와 데이터 접근 코드

├─ docs/
│  ├─ architecture/
```

각 파일은 하나의 명확한 책임을 가진다. 기능 코드는 `web`, `api`, `contracts`, `database` 경계를 통해 통신하며 서로의 내부 구현을 직접 참조하지 않는다.

## 5. 인증과 계정

### 5.1 지원 방식

- 이메일과 비밀번호
- Google OAuth
- Kakao OAuth
- Naver Custom OAuth2 Provider

이메일 가입은 이메일 인증을 요구한다. 비밀번호 재설정 링크는 일회성·만료형으로 처리한다. 소셜 로그인 공급자가 이메일을 주지 않거나 신뢰할 수 없는 경우 자동 계정 병합을 하지 않는다.

### 5.2 계정 연결

동일 이메일이라는 이유만으로 계정을 묵시적으로 병합하지 않는다. 로그인된 사용자가 재인증을 완료한 뒤 설정 화면에서 공급자를 연결한다. 연결 해제 시 남은 로그인 수단이 하나 이상인지 검증한다.

### 5.3 사용자 범위

첫 버전은 개인 가계부만 지원한다. 모든 사용자 데이터는 `user_id`로 소유권을 구분하고 API와 데이터베이스 제약으로 격리한다.

## 6. 화면과 상호작용

### 6.1 화면 구성

- 로그인·가입·이메일 인증·비밀번호 재설정
- 초기 설정: 월 시작일, 기본 예산, 카테고리, 계좌
- 홈 대시보드
- 모바일 빠른 입력
- 거래 목록·검색·필터·상세·수정·삭제·복제
- 월간 달력
- 예산과 사용률
- 반복 거래
- 계좌와 자산
- 통계와 이전 기간 비교
- CSV 가져오기·오류 검토·내보내기
- 프로필·연결 로그인·접근성·모션·탈퇴 설정

### 6.2 반응형 역할

승인된 A·B·C 화면을 역할별로 함께 사용한다.

- A 균형형 대시보드: PC와 태블릿의 기본 홈
- B 달력 중심형: 날짜별 거래와 반복 지출 확인
- C 모바일 우선형: 남은 예산과 빠른 입력 중심의 모바일 홈

PC는 사이드바와 다열 레이아웃을 사용한다. 모바일은 하단 탭과 전체 화면 입력 흐름을 사용한다. 반응형 처리는 단순 축소가 아니라 정보 우선순위와 탐색 구조의 재배치다.

### 6.3 디자인 방향

Impeccable의 제품 UI 원칙과 `PRODUCT.md`, `DESIGN.md`를 따른다.

- 성격: 전문적, 분석적, 명확함
- Creative North Star: The Financial Instrument Panel
- 참고: Toss, Stripe Dashboard, Linear
- 색상: 중성 표면과 제한된 인디고 계열 강조색
- 글꼴: UI용 산세리프와 숫자용 모노스페이스
- 숫자: `tabular-nums`로 자릿수 정렬 유지
- 강조색: 행동, 선택, 상태, 데이터 구분에만 사용
- 깊이: 기본은 평면, 실제로 떠 있는 요소에만 그림자 사용

### 6.4 모션

다음 모션은 제품 상태를 설명하기 때문에 포함한다.

- 숫자 값의 변화
- 그래프 데이터 갱신
- 탭과 화면 상태 전환
- 데이터 조회·저장·동기화 진행
- 성공·오류 피드백

일반 전환은 150~250ms의 ease-out 계열을 사용한다. 콘텐츠를 처음부터 숨겨 애니메이션 완료에 의존하지 않는다. `prefers-reduced-motion` 환경에서는 교차 페이드 또는 즉시 전환으로 축소한다.

## 7. 데이터 모델

### 7.1 공통 원칙

- KRW 금액은 원 단위 `BIGINT`로 저장한다.
- 사용자가 입력한 거래일은 `DATE`로 저장한다.
- 서버 이벤트 시각은 UTC `TIMESTAMPTZ`로 저장한다.
- 식별자는 클라이언트에서도 생성 가능한 UUID를 사용한다.
- 동기화 대상 데이터는 `version`, `created_at`, `updated_at`, `deleted_at`을 갖는다.
- 삭제는 동기화가 끝날 때까지 소프트 삭제로 유지한다.

### 7.2 핵심 테이블

- `profiles`: 시간대, 월 시작일, 사용자 설정
- `accounts`: 현금·은행·카드·투자 계좌
- `categories`: 수입·지출 분류와 정렬 순서
- `transactions`: 금액, 거래일, 계좌, 카테고리, 메모, 출처
- `transfer_groups`: 이체 출금·입금 두 행의 연결
- `budgets`: 월별 전체·카테고리 예산
- `recurring_rules`: 반복 주기, 다음 생성일, 종료 조건
- `asset_snapshots`: 특정 시점의 자산 평가액
- `import_jobs`: CSV 처리 상태와 오류 요약
- `sync_operations`: 기기 변경 요청과 중복 방지 키

### 7.3 제약과 인덱스

- 모든 조회는 사용자 소유권을 포함한다.
- 거래 목록 기본 인덱스는 `(user_id, occurred_on, id)`다.
- 반복 거래 생성은 `(rule_id, scheduled_on)` 고유 제약으로 중복을 방지한다.
- 이체 두 행은 같은 `transfer_group_id`로 연결하고 수입·지출 통계에서 제외한다.
- 계좌 잔액 요약값은 거래 합계로 재검증 가능해야 한다.

## 8. 오프라인 동기화

### 8.1 쓰기 흐름

1. 클라이언트가 UUID와 `idempotency_key`를 생성한다.
2. IndexedDB에 변경과 기준 `version`을 저장한다.
3. UI에 즉시 반영하고 `동기화 대기` 상태를 표시한다.
4. 연결 복구 후 변경 묶음을 `POST /sync/push`로 전송한다.
5. API가 인증, 소유권, 스키마, 버전을 검증한다.
6. 검증된 변경을 하나의 PostgreSQL 트랜잭션으로 적용한다.
7. 성공한 변경만 로컬 대기열에서 제거한다.

### 8.2 읽기 흐름

클라이언트는 `GET /sync/pull?cursor=...`로 변경과 삭제 tombstone을 증분 수신한다. 커서는 정렬 가능한 서버 변경 순서를 나타내며 클라이언트 시각에 의존하지 않는다.

### 8.3 충돌 원칙

동일한 레코드의 서버 `version`이 클라이언트 기준 버전과 다르면 조용히 덮어쓰지 않는다. 서버는 최신 값과 로컬 변경을 함께 충돌 응답으로 반환한다. 클라이언트는 사용자가 유지할 값을 선택하도록 한다. 중복 전송은 `idempotency_key`로 동일 결과를 반환한다.

## 9. API 조회 전략

- 거래 목록은 `(occurred_on, id)` 커서 페이지네이션을 사용한다.
- 홈 대시보드는 여러 네트워크 호출 대신 전용 집계 응답 하나를 제공한다.
- 월별·카테고리별·계좌별 통계는 PostgreSQL 집계와 윈도 함수를 사용한다.
- CSV 가져오기는 비동기 작업 상태를 제공하고 정상 행과 오류 행을 분리한다.
- 느린 조회는 `EXPLAIN ANALYZE`로 확인한 뒤 인덱스나 요약 구조를 추가한다.
- Redis 캐시는 실제 반복 조회와 지연이 측정되기 전에는 추가하지 않는다.

## 10. 오류 처리

모든 API 오류는 다음 필드를 포함한다.

```json
{
  "code": "TRANSACTION_VERSION_CONFLICT",
  "message": "다른 기기에서 변경된 거래입니다.",
  "requestId": "req_example",
  "retryable": false,
  "fieldErrors": []
}
```

- 입력 오류는 필드 단위로 반환한다.
- 네트워크·일시적 서버 오류만 제한된 지수 백오프로 자동 재시도한다.
- 인증, 권한, 검증, 충돌 오류는 자동 재시도하지 않는다.
- DB 변경은 트랜잭션으로 묶어 일부 성공을 방지한다.
- 로딩, 빈 상태, 오프라인, 동기화 대기, 충돌, 성공, 오류를 서로 다른 상태로 표현한다.
- CSV는 전체 실패 대신 오류 행을 검토할 수 있게 한다.

## 11. 보안과 개인정보

- JWT 검증 후 모든 요청에 사용자 소유권을 강제한다.
- 서비스 키와 DB 자격 증명은 서버 환경 변수에만 둔다.
- CORS는 허용된 배포 도메인으로 제한한다.
- 로그인, 비밀번호 재설정, OAuth 콜백, 가져오기 API에 속도 제한을 적용한다.
- 로그에서 비밀번호, 토큰, 전체 계좌번호, 거래 메모 원문을 제거하거나 마스킹한다.
- 사용자 추적에는 개인정보 대신 `requestId`와 내부 오류 코드를 사용한다.
- 탈퇴는 인증 계정, 금융 데이터, 저장 파일을 순서대로 삭제하고 결과를 기록한다.
- 마이그레이션 전에 백업과 롤백 가능 여부를 확인한다.
- CI에서 의존성 취약점과 비밀정보 커밋을 검사한다.

## 12. 접근성

WCAG 2.2 AA를 목표로 한다.

- 모든 핵심 기능은 키보드로 조작 가능해야 한다.
- 입력, 버튼, 내비게이션, 그래프에는 스크린 리더 레이블을 제공한다.
- 일반 본문 대비는 최소 4.5:1, 큰 텍스트는 최소 3:1을 유지한다.
- 그래프와 상태는 색상만으로 구분하지 않고 레이블, 패턴, 아이콘, 수치를 함께 사용한다.
- 포커스 표시를 제거하지 않는다.
- 터치 대상은 모바일에서 충분한 크기와 간격을 갖는다.
- 축소 모션 환경에서 기능 정보가 사라지지 않아야 한다.

## 13. 코드 주석과 개발 문서

### 13.1 코드 주석

- 공개 함수, 클래스, DTO, 서비스, 훅에는 TSDoc을 작성한다.
- TSDoc에는 목적, 행동 원리, `@param`, `@returns`, `@throws`를 포함한다.
- 동기화 충돌, 금액 계산, 권한, 반복 생성, 복잡한 SQL에는 결정 이유와 전제를 주석으로 기록한다.
- API DTO와 컨트롤러에는 OpenAPI 설명과 요청·응답 예시를 제공한다.
- 코드가 그대로 말해 주는 문법을 주석으로 반복하지 않는다.
- 코드 변경 시 관련 주석과 문서도 같은 커밋에서 갱신한다.

### 13.2 문서 구조

- `README.md`: 소개, 실행, 환경 변수, 주요 명령
- `docs/architecture/`: 시스템 구조와 ADR
- `docs/database/`: ERD, 테이블, 인덱스, 동기화 규칙
- `docs/api/`: OpenAPI, 인증, 오류 코드
- `docs/guides/`: 개발, 테스트, 배포, 사용자 안내
- `docs/roadmap/`: 1단계, OCR, 금융 연동
- `CHANGELOG.md`: 버전별 변경
- `PRODUCT.md`: 제품 목적과 원칙
- `DESIGN.md`: Impeccable 디자인 시스템

## 14. 테스트와 품질 게이트

### 14.1 테스트 계층

- 단위: 금액, 예산, 반복 거래, 이체, 충돌 판정
- DB 통합: 제약, 롤백, 격리, 마이그레이션
- API 계약: 인증, 권한, 오류, 페이지네이션, 스키마
- UI 컴포넌트: 입력, 로딩, 빈 상태, 오류, 키보드
- 동기화: 오프라인 생성, 중복 전송, 역순 요청, 두 기기 충돌
- E2E: 가입부터 거래 입력, 예산 확인, CSV 내보내기까지
- 반응형: PC, 태블릿, 모바일 주요 화면
- 접근성: 자동 검사와 핵심 수동 시나리오
- 성능: 대시보드 쿼리와 대량 거래 목록 기준값

### 14.2 CI 순서

```text
format → lint → typecheck → unit → integration → build → E2E smoke
```

필수 검증을 통과하지 않은 변경은 `main`에 병합하지 않는다.

### 14.3 구현 마일스톤

1단계 범위는 다음 순서의 독립 검증 가능한 마일스톤으로 나눈다.

1. 저장소 구조, 공통 설정, 인증 골격
2. 거래·카테고리·계좌와 기본 대시보드
3. 예산·반복 거래·자산·통계
4. IndexedDB 오프라인 대기열과 양방향 동기화
5. CSV 입출력, PWA, 접근성, 운영 문서와 릴리스 품질 게이트

각 마일스톤은 실패하는 테스트, 최소 구현, 전체 검증, 관련 문서 갱신의 순서로 완료한다. 뒤 마일스톤은 앞 마일스톤의 공개 인터페이스에만 의존한다.

## 15. Git과 GitHub 전략

### 15.1 브랜치

- `main`: 항상 배포 가능한 보호 브랜치
- `feature/{기능명}`: 기능 개발용 단기 브랜치
- `maintenance-branch`: 유지보수 작업용 장기 브랜치
- `hotfix/{픽스명}`: 운영 장애와 긴급 보안 수정용 단기 브랜치

`develop` 브랜치는 사용하지 않는다. 기능명과 수정명은 영문 소문자 `kebab-case`를 사용한다.

### 15.2 흐름

1. 문서와 프로젝트 구조를 `main`의 초기 커밋으로 만든다.
2. GitHub에 비공개 `account-book` 저장소를 생성하고 `main`을 푸시한다. 비공개는 초기 보안 기본값이며 공개가 필요하면 저장소 생성 전에 사용자가 변경한다.
3. `maintenance-branch`를 생성하고 원격에 푸시한다.
4. 기능은 최신 `main`에서 `feature/{기능명}`으로 분기한다.
5. 긴급 수정은 최신 `main`에서 `hotfix/{픽스명}`으로 분기한다.
6. PR과 CI를 통과한 뒤 `main`에 병합한다.
7. 병합된 기능·핫픽스 브랜치는 삭제한다.
8. 핫픽스 병합 후 `maintenance-branch`와 관련 작업 브랜치에 변경을 반영한다.

### 15.3 병합과 커밋

- 최초 원격 푸시 직후 `main` 브랜치 보호를 활성화하고, 그 이후 직접 푸시를 금지한다.
- 기능 PR은 squash merge를 기본으로 한다.
- Conventional Commits 형식을 사용한다.
- PR에는 기능, 테스트, 문서, 마이그레이션, 보안 영향을 기록한다.
- 릴리스는 Semantic Versioning과 `vX.Y.Z` 태그를 사용한다.

## 16. 완료 기준

1단계는 다음 조건을 모두 만족할 때 완료다.

- PC와 모바일에서 가입, 로그인, 거래 기록, 예산, 계좌, 통계가 동작한다.
- 이메일, Google, Kakao, Naver 로그인 흐름이 검증된다.
- 오프라인 거래가 재연결 후 중복 없이 동기화된다.
- 사용자 간 데이터 격리 테스트가 통과한다.
- CSV 가져오기와 내보내기가 오류 검토 흐름과 함께 동작한다.
- WCAG 2.2 AA 자동 검사와 핵심 수동 접근성 시나리오가 통과한다.
- 전체 CI 품질 게이트가 통과한다.
- README, 아키텍처, ERD, API, 테스트, 배포, 사용자 안내, 로드맵, 변경 기록이 최신 상태다.
