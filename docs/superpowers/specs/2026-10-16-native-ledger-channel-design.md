# Android 장부 연결·PC 편집 권한 설계

## 의도와 범위

승인된 제품은 Android에서 수기/알림으로 기록하고 PC에서는 같은 기록을 조회·편집·삭제하며 계좌·카테고리·향후 규칙을 관리하는 개인 장부다. 이번 단위는 현재 구현된 이메일 앱 인증과 기존 원장 API 사이를 연결한다. Android 앱 화면·알림 수집·iOS·새 집계/환불 기능까지 완료했다고 표시하지 않는다.

기존 사용자 지시대로 일반 구현 결정을 매번 승인받지 않고 명세·계획·검증 결과를 기록하며 진행한다. 실제 DB 이관·배포·원격 전송·사용자 정책 변경은 별개다. 기존 미커밋 작업은 보존한다.

## 선택과 대안

채택: 기존 BFF 위임 JWT에 필수 `chn=web|android`를 넣는다. BFF는 인증된 서버 세션에서만 값을 얻고 NestJS는 서명·기존 요청 결합·재사용 방어를 통과한 클레임만 신뢰한다. 클라이언트의 channel/userId 헤더나 본문을 권한으로 쓰지 않는다.

대안인 Android 전용 새 scope만 추가하면 앞으로 추가되는 채널 정책마다 scope가 늘고 기존 쓰기 scope를 통한 우회 검토도 분산된다. 모바일이 공급자 토큰으로 NestJS에 직접 접근하면 현재 서버 세션 철회·단일 요청 JWT 경계를 이중 구현해야 한다. 기존 위임 경계 확장이 더 일관된다.

채널은 인증 경로의 구분이며 정식 앱/하드웨어 증명이 아니다. 유효한 자격 증명을 가진 별도 HTTP 클라이언트의 Android 경로 호출까지 차단한다고 주장하지 않는다. 은행 계좌 소유 검증도 아니다.

## 흐름과 권한

```text
PC 쿠키 → 웹 BFF 검사 → web 서버 세션 ───────┐
                                          ├→ 단일 요청 ES256 JWT(chn 포함) → NestJS → 같은 원장
Android Bearer → native 검사 → android 세션 ┘
```

| 작업 | web | android |
| --- | --- | --- |
| 프로필/계좌/카테고리 기존 조회·관리 | 허용 | 허용 |
| 거래 조회·수정·삭제 | 허용 | 허용 |
| 새로운 수기 거래 생성 | 거절 | 허용 |
| 신규 알림 수집 | 이번에 없음 | 수집 기기/접수 계약 후 구현 |

`chn` 누락/잘못된 값은 기본 web으로 추정하지 않고 인증 거절한다. 현재 사용 중인 30초 JWT에는 반드시 새 클레임이 필요하다. 일반 서버 세션/쿠키는 유지한다. 새 API와 새 BFF를 함께 배포해야 하며, 구 BFF가 남으면 요청이 거절될 수 있으므로 배포 조합을 사전에 검증한다. 이번에는 배포하지 않는다.

NestJS의 `POST /v1/transactions`는 Android 전용 채널 메타데이터를 요구한다. 나머지 기존 경로는 유효한 web/android를 받되 기존 scope·행 소유권은 그대로 강제한다. 유효한 web 토큰으로 생성하면 403 고정 오류이며 저장소를 호출하지 않는다. 누락/변조 JWT는 401이다.

## BFF 연결

`/api/native/profile`, `/accounts`, `/accounts/:id`, `/accounts/:id/archive`, `/categories`, `/categories/:id`, `/categories/:id/archive`, `/transactions`, `/transactions/:id`의 9개 라우트 파일로 기존 14개 작업을 제공한다. 경로마다 메서드/작업을 고정한다. 임의 목적지·scope·사용자는 입력받지 않는다.

기존 CoreController/작업표/응답 스키마를 재사용하고 채널별 인증 검사를 작은 모듈로 분리한다. Android는 HTTPS·정확한 origin·고정 경로·허용 쿼리·Bearer 하나·Cookie/Origin/Sec-Fetch 거절을 적용한다. 16KiB/3초 본문 제한, 응답 1MiB, no-store, 리다이렉트/자동 mutation 재전송 금지는 유지한다. 갱신 임박이면 명시적 갱신 요구 401을 반환한다.

앱 요청의 추가 사용자 일치 조건도 유지한다. 계정 전환 뒤 A의 요청을 B에 쓰지 않는다. 웹 세션을 native에, Android 세션을 웹에 쓰면 거절한다. 서명할 채널은 항상 해석된 세션과 해당 컨트롤러의 고정 채널이 일치해야 한다.

인증된 native 장부 접근 제한은 기존 DB 제한기를 확장해 작업을 분리한다. `ledgerRead` 전역 분당1,200/사용자+설치60, `ledgerWrite` 전역600/사용자+설치30. 저장 종류는 기존 `native_auth`를 재사용하되 operation을 HMAC 구분에 포함한다. DB 장애는 503, 초과는429다. 이메일 로그인/갱신 예산과 분리한다. 새 테이블/권한/이관은 필요 없다.

## PC UX와 시험 데이터

거래 추가 버튼·생성 폼 연결을 제거하고 '새 거래는 Android 앱에서 기록하고 PC에서는 조회·편집합니다'로 안내한다. 아직 Android APK가 없다는 현재 상태도 숨기지 않는다. 빈 목록에서 PC 작성을 권하지 않는다. 계좌·카테고리 관리는 유지한다.

PC 회귀 시험의 거래 준비는 Android HTTP 생성으로 바꾼다. 실제 UI로 PC 편집·삭제·409 충돌·응답 유실·계정 전환을 계속 검증한다. PC 생성 성공을 테스트 통과 조건으로 남기지 않는다.

## 실패와 검증

| 실패 | 기대 결과/검증 |
| --- | --- |
| 서명된 chn 누락·null·미허용 값 / payload 변조 | 실제 JOSE 서명 테스트에서401, 권한 처리 전 거절 |
| 웹 JWT로 신규 거래 생성 | 실제 Nest 경로403, DB 원장/멱등 결과 추가 없음 |
| native 경로에 웹 쿠키·웹 세션·자칭 Android 헤더 | BFF 거절, 위임 호출 없음 |
| 잘못된 경로/쿼리/본문/응답 ID | 고정 오류, 잘못된 자원 쓰기/응답 노출 없음 |
| 요청 제한 DB 오류·상한 | 503/429, 원장 호출 없음 |
| Android 생성 후 PC 조회/수정 | 동일 ID/금액 보존, 버전 충돌 보호 |
| 기존 앱 인증·PC 관리 회귀 | 전체 단위/타입/coverage와 실제 DB·Playwright 실행 |

공급자 실제 네트워크/호스팅 프록시·실 Android 안전 저장소/실기기·활성 수집 기기 교체는 아직 검증 대상이 아니다. 이 범위를 전체 보안 감사나 PR 전체 승인으로 확대하지 않는다.
