# 접근성 우선 뉴모피즘 인증 화면 설계

- 작성일: 2026-08-25
- 상태: 승인됨
- 대상: `apps/web` 인증 화면
- 디자인 방향: B안 `Accessible Instrument Neumorphism`
- 구현 방식: 토큰 우선 적용

## 1. 목적

PC 웹과 모바일 화면에서 동일한 계정 경험을 제공하면서 로그인, 회원가입, 이메일 인증, 비밀번호 재설정 화면에 절제된 뉴모피즘을 적용한다. 금융 서비스의 명확성, 접근성, 보안 상태 전달을 장식보다 우선한다.

이번 변경은 인증 화면의 시각 체계만 다룬다. 인증 요청 흐름, BFF 경계, 세션 처리, OAuth 검증 및 오류 코드 매핑은 변경하지 않는다.

## 2. 브레인스토밍 결론

뉴모피즘은 동일하거나 유사한 색상의 배경과 표면에 밝고 어두운 그림자를 함께 사용해 얕은 높낮이를 표현하는 시각 언어다. 금융 앱에서는 차분하고 정교한 인상을 줄 수 있지만, 그림자 대비가 지나치면 장식성이 커지고 대비가 약하면 컨트롤의 경계와 상태를 인지하기 어렵다.

따라서 다음 원칙을 고정한다.

1. 그림자는 표면의 계층만 설명한다.
2. 클릭 가능 여부, 포커스, 오류, 성공, 비활성 상태를 그림자 하나로 전달하지 않는다.
3. 금융 금액, 거래 목록, 표, 차트는 평면적인 정보 레이어로 유지한다.
4. 중요한 상태는 색상과 테두리, 텍스트 또는 아이콘 중 최소 두 가지 신호로 표현한다.
5. 과도한 돌출과 함몰 표현을 피하고 표면이 배경에서 살짝 분리되는 정도만 사용한다.

## 3. 적용 범위

### 3.1 뉴모피즘 적용 대상

- 인증 페이지의 주요 패널
- 이메일 및 비밀번호 입력창
- 기본 행동 버튼과 소셜 로그인 버튼
- 상태 메시지를 담는 표면

### 3.2 평면형 유지 대상

- 이후 구현될 거래 목록과 데이터 테이블
- 금액과 집계 숫자
- 그래프의 축, 레이블, 범례 및 데이터 표시
- 보안·오류 안내 문구

### 3.3 변경하지 않는 영역

- 인증 컴포넌트의 이벤트와 데이터 흐름
- Zod 입력 검증 규칙
- React Query 및 API 통신 경계
- Supabase, BFF, API 및 세션 보안 로직
- 안전한 공개 오류 코드 매핑

## 4. 색상 체계

사용자가 선택한 메인 배경은 `중립 오프화이트`다. 푸른 기운이나 강한 아이보리 색조를 사용하지 않는다.

| 역할 | 기준 색상 | 용도 |
| --- | --- | --- |
| Canvas | `#F7F7F5` | 페이지 전체 배경 |
| Surface | `#FAFAF8` | 뉴모피즘 패널과 컨트롤 |
| Paper | `#FFFFFF` | 금융 데이터와 높은 판독성이 필요한 평면 레이어 |
| Ink | `#1D2330` 계열 | 주요 텍스트 |
| Muted | `#626875` 계열 | 보조 설명 |
| Brand | `#4F46E5` 계열 | 기본 행동과 포커스 |
| Danger | 명도 대비를 통과하는 적색 | 오류 테두리, 텍스트, 아이콘 |
| Success | 명도 대비를 통과하는 녹색 | 성공 텍스트와 아이콘 |

구현에서는 기존 OKLCH 토큰 체계를 유지할 수 있다. 위 HEX 값은 시각 기준이며 실제 OKLCH 값은 브라우저 대비 검증을 통해 확정한다.

본문 텍스트는 일반 텍스트 대비 4.5:1 이상을 목표로 한다. 주요 컨트롤 경계와 상태 표시는 인접 색상 대비 3:1 이상을 목표로 한다.

## 5. 표면과 그림자

그림자는 기존 예시보다 거리와 불투명도를 절반 이하로 낮춘다.

- 주요 패널: 양방향 그림자를 사용하되 이동 거리는 약 4px, 흐림은 약 10~12px 수준으로 제한한다.
- 입력창: 약 2px의 얕은 내부 그림자만 허용한다.
- 버튼: 기본 상태의 그림자는 패널보다 약하게 사용한다.
- 눌림 상태: 최대 1px 이동 또는 매우 얕은 내부 그림자를 사용한다.
- 오류와 포커스: 그림자를 덮어쓰는 대신 명시적인 테두리와 외부 포커스 링을 추가한다.

정확한 값은 CSS 사용자 정의 속성으로 중앙 관리한다. 컴포넌트별 임의 그림자 값은 추가하지 않는다.

## 6. 타이포그래피와 숫자

- 기존 시스템 글꼴 스택을 유지해 추가 웹폰트 요청과 렌더링 지연을 만들지 않는다.
- 제목은 짧고 명확하게 유지하고 과도한 굵기 단계는 사용하지 않는다.
- 금액과 집계 숫자에는 `font-variant-numeric: tabular-nums`를 유지한다.
- 금융 데이터는 우측 정렬을 기본으로 하되 문맥에 따라 명시적으로 결정한다.
- 상태 메시지는 색상만 사용하지 않고 의미를 설명하는 한국어 문구를 함께 제공한다.

## 7. 반응형 구조

승인된 인증 콘텐츠 너비 규칙을 유지한다.

| 뷰포트 | 인증 콘텐츠 규칙 |
| --- | --- |
| 320px 이상 모바일 | 안전 여백을 둔 단일 열 |
| 태블릿 및 소형 데스크톱 | 공간이 충분할 때 설명 패널과 인증 패널을 2열로 전환 |
| 1080~1920px | 뷰포트의 `60vw` |
| 1921px 이상 | 최대 `1080px` |

모바일 터치 대상은 최소 44px 높이를 유지한다. 소프트 키보드가 표시돼도 주요 입력과 제출 버튼에 접근할 수 있어야 한다. 장식적인 고정 높이는 사용하지 않는다.

PC 웹과 향후 네이티브 모바일 앱은 같은 계정과 데이터베이스를 공유하지만, CSS와 네이티브 UI 코드를 직접 공유하지 않는다. 대신 색상 역할, 표면 계층, 상태 표현, 모션 원칙을 공통 디자인 규약으로 공유한다.

## 8. 모션 원칙

모션은 데이터 변화와 시스템 상태를 설명할 때만 사용한다.

| 대상 | 동작 | 권장 시간 |
| --- | --- | --- |
| 금액 변화 | 이전 값에서 최종 값으로 짧게 보간 | 300~500ms |
| 그래프 출력 | 축과 레이블을 먼저 표시하고 데이터만 한 번 전개 | 400ms 이내 |
| 화면 전환 | 짧은 페이드와 최대 4px 이동 | 160~220ms |
| 데이터 로딩 | 200ms 이상 지연될 때 스켈레톤 또는 진행 상태 표시 | 요청 시간에 따름 |
| 버튼 상호작용 | 색상·테두리 변화와 최대 1px 눌림 | 약 180ms |

`prefers-reduced-motion: reduce` 환경에서는 숫자 보간, 이동, 그래프 전개를 제거하고 최종 상태를 즉시 표시한다. 로딩 상태 자체는 제거하지 않고 정적인 안내로 대체한다.

## 9. 컴포넌트 적용 구조

현재 단계에서는 공통 UI 라이브러리를 새로 만들지 않는다. 토큰을 먼저 적용하고 기존 의미 중심 인증 컴포넌트를 유지한다.

- `apps/web/src/app/globals.css`
  - 색상, 표면, 그림자, 포커스, 모션 토큰
  - 인증 패널, 입력창, 버튼, 상태 스타일
  - 반응형 및 움직임 축소 규칙
- `apps/web/src/components/auth/auth-shell.tsx`
  - 기존 DOM과 접근 가능한 제목 구조 유지
  - 스타일 적용에 꼭 필요한 경우에만 클래스 조정
- `auth-form.tsx`, `provider-buttons.tsx`, `auth-status.tsx`
  - 데이터 흐름과 오류 처리 유지
  - 시각 상태에 필요한 접근성 속성이 부족한 경우에만 보강

`Surface`, `Button`, `Input` 같은 공통 컴포넌트는 대시보드 구현 과정에서 같은 패턴이 두 번 이상 반복될 때 추출한다. 인증 화면만을 위해 선제적으로 추상화하지 않는다.

## 10. 상태와 오류 처리

- 입력 오류는 `aria-invalid`, 오류 테두리, 오류 문구를 함께 사용한다.
- 오류 문구는 기존 `aria-describedby` 연결을 유지한다.
- 검증 실패 시 첫 번째 오류 입력으로 포커스를 이동하는 기존 동작을 유지한다.
- 제출 중에는 중복 제출을 방지하고 텍스트 상태를 함께 표시한다.
- 소셜 로그인 이동 중에도 제공자 이름과 진행 상태를 문장으로 알린다.
- 원시 서버 오류, 식별자, 공급자 URL 및 민감 정보는 UI에 출력하지 않는다.
- 시각 변경으로 보안 오류 메시지 매핑과 실패 동작이 달라지지 않아야 한다.

## 11. 구현 방식 비교와 결정

### 선택: 토큰 우선 적용

기존 컴포넌트와 의미 구조를 보존하면서 CSS 토큰과 스타일을 최소 수정한다. 현재 구현 범위에 가장 작은 변경으로 승인된 디자인을 반영할 수 있고 회귀 위험이 낮다.

### 보류: 공통 UI 컴포넌트 선제 구축

장기적인 일관성은 높지만 아직 인증 화면 외 반복 사례가 부족하다. 대시보드 구현 이후 실제 중복을 기준으로 재검토한다.

### 제외: 외부 UI 라이브러리 테마

새 의존성과 번들 크기, 업데이트 부담이 생기며 승인된 낮은 깊이와 상태 규칙을 세밀하게 유지하기 어렵다.

## 12. TDD 및 검증 계획

### RED

구현 전에 다음 기대를 실패하는 테스트로 먼저 추가한다.

- Canvas가 푸른색이 아닌 승인된 중립 오프화이트인지 검증
- 1080, 1920, 1921px 인증 셸 너비 회귀 검증
- 320, 390, 768px에서 수평 스크롤이 없고 주요 컨트롤이 표시되는지 검증
- 입력 오류와 포커스에 명시적인 경계가 존재하는지 검증
- 버튼과 입력의 터치 높이가 44px 이상인지 검증
- 움직임 축소 설정에서 모션 시간이 사실상 제거되는지 검증

### GREEN

CSS 토큰과 필요한 최소 마크업만 수정해 RED 테스트를 통과시킨다. 테스트 통과를 위해 인증 로직이나 보안 경계를 완화하지 않는다.

### 최종 검증

1. Vitest 인증 컴포넌트 테스트
2. Playwright 인증 흐름 및 레이아웃 테스트
3. 설치된 `@axe-core/playwright` 기반 접근성 검사
4. 320, 390, 768, 1080, 1920, 1921px 브라우저 검증
5. 로그인, 회원가입, 비밀번호 재설정의 PC·모바일 스크린샷 확인
6. ESLint
7. TypeScript 타입 검사
8. 전체 워크스페이스 테스트
9. 프로덕션 빌드

## 13. 완료 조건

- 승인된 중립 오프화이트 배경과 낮은 그림자 강도가 모든 인증 페이지에 일관되게 적용된다.
- 포커스, 오류, 성공, 로딩 상태가 그림자나 색상 하나에 의존하지 않는다.
- 기존 인증 흐름과 보안 테스트가 모두 통과한다.
- 승인된 데스크톱 너비와 모바일 단일 열 구조가 유지된다.
- 움직임 축소 설정에서 불필요한 모션이 제거된다.
- Axe 자동 검사에 중대한 접근성 위반이 없다.
- 린트, 타입 검사, 테스트 및 빌드가 통과한다.
