# Android 수기 입력 선행: 거래 시각 계약

상태: 승인된 통합 설계 §8의 하위 구현 단위. Android 우선이며 iOS는 시작하지 않는다.

## 이번 단위와 범위

현재 API/DB의 `occurredOn`/`occurred_on`은 날짜뿐이다. 시각을 폼에 먼저 추가하면 저장되지 않는 입력을 제공하게 된다. 먼저 순수 TypeScript 계약과 시간대 선택 함수를 만들고, 다음 단위에서 DB/서버 저장·PC 표시·Android 입력을 연결한다. 이번에는 기존 거래 계약·API·DB·화면을 변경하지 않는다.

## 고정 정책

- DATE 기록은 `precision: day`, `occurredAt: null`, `source: legacy_date`로 보존한다. 자정이나 현재 시각을 만들어 넣지 않는다.
- 시각이 있는 기록은 UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, 정밀도(minute/second/millisecond), 근거(user/notification/device_received), 출처 시간대(nullable), 적용 장부 시간대, 장부 날짜를 함께 가진다.
- 분 단위는 UTC 초/밀리초 0, 초 단위는 밀리초 0인 구간 시작으로 표현한다. UI에서 0초를 실제 관측한 초라고 표시하지 않는다. 수신 시각은 추정 근거이지 은행 거래 발생 시각의 증명이 아니다.
- 장부 날짜는 명시한 시간대로 계산한다. OS 기본 시간대나 현재 시각은 읽지 않는다. IANA 지역/이름과 UTC를 사용하고 `+09:00`, `KST` 같은 임의 오프셋·약어는 설정값으로 받지 않는다.
- 거주 이력은 첫 기준(`effectiveFrom: null`)과 오름차순 변경 시각으로 구성한다. 전환 시각 포함부터 새 기준, 그 전은 이전 기준이다. 저장 시점이 아닌 발생 시각으로 선택한다.
- 정밀도 구간 안에 거주 변경이 있거나, 변경 이력이 있는 상태에서 수신 시각만 아는 경우는 `confirmation_required`를 반환한다. 조용히 한 시간대를 확정하지 않는다.
- 실제 시각→현지 날짜 변환만 한다. DST의 중복/존재하지 않는 현지 시각을 UTC로 추측하는 역변환은 하지 않는다. Android 입력 UI에서 별도 처리해야 한다.
- 새 계약은 저장 전 검증용이다. DB에 이미 확정 저장된 과거 날짜를 매 조회 때 재계산하는 용도로 쓰지 않는다. 서버가 인증 소유자의 이력을 읽어 적용해야 하며 클라이언트가 보낸 시간대로 권한/역사를 결정하지 않는다.

## 경계·검증

윤년, UTC/서울/로스앤젤레스 날짜 경계, 뉴욕 DST, 45분 오프셋, 날짜만 있는 과거 기록, 잘못된 시간대/정밀도, 전환 경계와 늦은 접수, 추정 시각을 시험한다. 입력 객체는 strict이고 이력은 한 번에 최대 256개까지 검증한다(초과 시 실패, 잘라내지 않음). 이 상한은 제품의 이사 횟수 제한이 아니라 내부 호출의 자원 경계다.

UTC는 서기 1~9999년의 유효한 날짜만 허용한다. 변환 결과가 같은 지원 범위를 벗어나면 실패한다. 구 DATE 보존은 기존 LocalDate 계약을 그대로 따른다. 새 의존성·환경변수·원문 금융 알림 저장은 없다.

## 다음 저장 단위에서 반드시 닫을 것

거주 이력의 소유권/RLS·원자적 변경, 거래별 시간대 snapshot, 추가형 migration과 과거 DATE 이관, 시간 정정 시 version/멱등성/장부 날짜 갱신, 실제 시각 정렬·cursor, 추정/확인 사유 UI. 이 계약 단위 통과를 수기 작성 또는 시간대 기능 전체 완료로 표시하지 않는다.

기술 근거: [ECMA-402 Intl.DateTimeFormat](https://tc39.es/ecma402/#sec-intl-datetimeformat-constructor). 명시적 `timeZone`, ISO 달력, 라틴 숫자를 사용한다. 런타임별 IANA 데이터 차이는 실제 Android 테스트에서 추가 확인한다.
