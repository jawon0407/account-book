# 개인 알림 가계부 통합 설계 — 데이터 흐름·상태·검증 기준

최초 작성: 2026-10-13. 최신 반영: 2026-10-15, 한국시간. 대상: 사용자, 초급 개발자, 로컬·클라우드 개발 담당자.

**이 문서는 승인된 제품 정책을 통합한 설계 검토본이다. 앱 구현·DB 적용·실기기 검증 완료 문서가 아니다.** 전체를 한 번에 구현하지 않고 §13의 하위 과제로 나눈다. 각 과제의 상세 계약과 파일별 실행 계획은 별도 검토한다.

## 1. 목표와 읽는 순서

목표는 **사용자가 동의한 새 금융 알림에서 실제 계좌 입출금을 기록하고, 놓친 거래는 모바일에서 수기로 보완하며, 같은 계정의 PC에서 조회·편집하는 개인 장부**다. 금융기관의 원장이나 실제 잔액을 검증하는 서비스는 아니다.

- 제품 요구: [개인 알림 가계부 요구사항](2026-10-07-personal-notification-ledger-design.md).
- 결정 근거: [Notion 엣지케이스 점검 현황](https://app.notion.com/p/3f5323168ba6816e9578c5151182018e) §10.1~10.47 및 2026-10-15 사용자 승인. 이 문서에는 실제 이름·계좌·알림 원문 대신 합성 사례만 사용한다.
- 재개 위치: [클라우드 인수인계](../../status/2026-10-07-personal-notification-ledger-handoff.ko.md).

표시를 구분한다. **승인 정책**은 사용자와 정한 기대 동작, **설계 제안**은 이를 구현하기 위한 책임·데이터 구분, **현재 코드**는 읽어서 확인한 사실이다. 기술 제안을 사용자 승인이나 실제 구현으로 바꾸어 읽지 않는다. Notion의 54개 시나리오와 기존 상태표는 검토 이력이며 테스트 수나 현재 완성도가 아니다. 최신 승인으로 이전 설명이 바뀐 경우 아래 기준과 해당 후속 결정절을 우선한다.

이번에 남아 있던 사용자 선택 2건은 결정 완료다. 영구 거주지 변경은 과거 기록 유지·변경 이후 발생 거래부터 새 기준을 적용한다. 시작 잔액은 계좌별 선택 설정 A안을 유지하되, 구현 전 공수 보고와 부담이 큰 경우 B안 전환 검토 조건도 유지한다. 기술 계약 6개와 구현·검증까지 완료했다는 뜻은 아니다.

| 실제 이사 때 시간대 처리 미정 | 과거 장부 날짜·집계 유지, 변경 이후 발생 거래부터 새 시간대 적용 |

| 문자열·금액·시간 조건은 미정 | 정확 일치·사용자 별칭, 금액 양 끝 포함, 시간 시작 포함·종료 제외 승인 |
| 환불·이체·개인정보 정책을 처음부터 다시 선택 | 승인 정책 유지. 저장·동시 처리·집계의 세부 계약만 후속으로 구체화 |

### 포함·제외 범위

Android 별도 앱, 수기 입력, 사용자 계좌 지정, 알림 기록, 선택형 규칙, 조회·편집·알림 안내가 초기 목표다. 화면은 TS/TSX, HTTP는 ky, 서버 상태는 TanStack Query, 앱은 React Native/Expo와 Android 네이티브 수집 모듈 방향을 유지한다. 패키지 버전·빌드 설정은 아직 확정한 것이 아니다.

실계좌 API·송금, 공동 장부·라온 연동, AI 분석, iOS의 동일 수집 기능, 외화 자동 환산, 과거 문자함·대화 조회는 이번 구현 범위 밖이다. 해외 거주 시간대 지원이 해외 금융 앱 판독 지원을 의미하지 않는다. 기존 은행 코드는 보존한다. 출처 불명 카드대금의 구매별 자동 분해도 보류한다.

## 3. 구성 요소와 신뢰 경계

```text
사용자가 선택한 앱의 새 알림
  → Android 수집 경계: 동의·권한·로그인·기기·일시 중지 확인
  → 기기 메모리: 금융 여부 판독 / 최소 거래 정보 추출 / 원문 폐기
  → 모바일 인증 경계(상세 계약 후 구현)
  → NestJS API: 소유권·입력·중복 접수 검증
  → 실제 이동이 명확하면 원장 기록(계좌·분류 미지정 허용)
     / 핵심 정보 불명확·중복 의심은 후보 검토 / 선택형 분류
  → 같은 서버 장부 ← Next.js BFF ← PC 브라우저
  → 새 확인 사항의 60초 묶음 안내 + 앱 내 확인 목록
```

수집기는 알림을 받는 역할, 판독기는 알려진 형식을 해석하는 역할, API는 권한·저장 무결성을 지키는 역할이다. 판독 결과가 은행 검증을 대신하지 않는다. Android의 `NotificationListenerService`는 게시된 알림과 출처 정보를 제공하는 경로이지 은행 거래 조회 API가 아니다. 알림이 게시되지 않으면 이 경로에서 그 거래를 알 수 없다는 한계가 있다. [Android 공식 문서](https://developer.android.com/reference/android/service/notification/NotificationListenerService)

기존 웹 BFF 위임 토큰을 모바일에서 직접 발급하게 하지 않는다. 서버 서명키·DB 비밀번호·관리자 키를 앱에 넣지 않는다. 모바일 로그인·세션 회전·철회·기기 교체 및 API 연결 방식은 §12의 선행 계약이다. 사용자 ID는 인증 결과에서 결정하며 요청 본문의 소유자나 자칭 `mobile` 헤더를 믿지 않는다. PC 신규 작성 제한도 화면 버튼만으로 끝내지 않는다.

**승인된 기기·채널 범위:** 여러 기기에서 같은 계정으로 로그인할 수 있지만 자동 수집은 계정당 최대 1대다. 수집 기기를 교체하면 서버에서 활성 권한을 전환하고 이전 기기의 새 접수를 차단한다. 전환과 처리 중 요청의 경계는 인증·접수 계약으로 검증한다. PC는 기존 거래 조회·수정·삭제·복구와 장부 계좌·카테고리·자동분류 규칙 관리를 제공한다. 새 수기 거래 작성과 기기 고유 수집 설정은 모바일에서 한다.

DB의 SQL 권한과 행 소유권 검사는 함께 필요하다. 기존 최소 권한 런타임 역할·RLS/FORCE RLS·소유자 복합 참조를 유지하고 새 관계에도 적용한다. Supabase 관리자 키는 RLS를 우회할 수 있고 수정 가능한 사용자 메타데이터는 권한 근거로 삼으면 안 된다. 다만 현재 API의 DB 역할/요청 문맥과 Supabase Data API의 `auth.uid()`를 동일하다고 가정하지 않는다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 4. 첫 사용과 판독 실패

1. 로그인하고 거주 기준 시간대를 선택한다. 수기 입력·조회부터 이용할 수 있다.
2. 자동 기록을 원하면 수집 동의, OS 알림 접근, 수집 앱 선택, 앱 내부 수집 켜짐을 각각 확인한다. 서비스 연결 여부도 별도로 표시한다.
3. 모든 계좌를 처음부터 등록할 필요는 없다. 실제 입출금·금액·방향이 명확한 알림은 계좌 미지정 상태로 먼저 기록한다. 기존 계좌 지정 / 새 장부 계좌 / 나중에 / 제외를 제공하며, 나중에 지정해도 같은 거래 ID를 유지한다.
4. 알림 출처 앱·유형·제공된 계좌 식별값을 사용자의 장부 계좌와 연결한다. 이는 은행 계좌 등록·명의 확인이 아니다.
5. 계좌·카테고리·거래 상대명만 모르면 원장 기록·전체 입출금 집계를 유지한다. 금액·방향이 불명확하거나 기존 거래와 중복 의심이면 확인 후보로 두며, 금융 거래인지조차 모르면 거래를 만들지 않는다.

토스 앱이 다른 은행 계좌 알림을 전달할 수 있으므로 패키지 이름을 은행명으로 치환하지 않는다. 계좌 뒷자리는 전역 고유값이 아니다. 계좌 식별값이 없는 형식은 사용자가 명시적으로 지정한 모호하지 않은 기본 연결만 사용한다. 여러 계좌가 가능하면 다시 확인한다.

토스 알림의 ‘상대 A → 내 토스뱅크 통장’은 입금 상대와 본인 계좌 단서를 구분해 읽는다. 문자열 하나로 명의 확인이나 카드 사용을 확정하지 않는다. 출처가 모호하면 ‘거래를 기록했어요. 어느 계좌의 거래인지 지정해 주세요.’로 안내하며 다른 사람 계좌라고 단정하지 않는다.

**판독 지원은 순차 활성화한다.** 검증 가능한 KB 한 형식으로 전체 흐름을 검증한 뒤 카카오뱅크·토스 유형과 금융 카카오톡·문자 형식을 추가한다. 은행 이용 강제나 문자/카카오톡 제외가 아니다. 지원은 은행명 전체가 아니라 출처 앱·형식·기기/앱 버전별로 명시하며 실제 지원표는 합성·실기기 시험 근거로 작성한다.

권한 거부·본문 숨김·미지원 형식에서도 기존 장부와 연결 가능한 상태의 수기 입력을 유지한다. 일반 대화·OTP를 판독 실패 금융 거래로 쌓지 않는다. ‘수집 준비됨’은 모든 거래 수집 성공이 아니다. 빈 목록을 실제 거래 없음으로 표시하지 않는다. 신규 수기 저장은 서버 연결이 필요하며 오프라인 금융 초안 보관 기능은 포함하지 않는다.

우리 앱의 안내 알림 표시 권한과 다른 앱 알림 접근 권한은 별개다. 안내 알림을 허용하지 않아도 앱 안의 미분류·확인대기 목록은 유지한다. [Android 알림 표시 권한](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

## 5. 상태와 합계 — 하나의 상태값에 모두 섞지 않기

다음은 논리적 상태 제안이다. 실제 enum·API 오류 코드 이름은 하위 명세에서 정한다.

| 구분 | 상태/전이 | 합계와 사용자 동작 |
| --- | --- | --- |
| 수집 후보 | 핵심 정보 부족 → 사용자 확인 → 원장 반영 또는 제외 | 확정 전 추가 금액 0. 확인 후 한 번만 반영 |
| 중복 후보 | 기존 기록 유지 → 같은 거래 연결 또는 별개 거래 확정 | 후보만으로 추가 합산하지 않음 |
| 원장 기록 | 정상 → 사용자 수정 → 삭제 → 기한 내 복구 | 정상 기록만 집계. 수정은 version 검증 |
| 계좌 지정 | 미지정(NULL) ↔ 본인 장부 계좌 지정 | 미지정도 전체 합계 포함. 특정 계좌 필터에서는 제외되며 지정 후 그 계좌에만 반영 |
| 분류 | 미분류 ↔ 사용자 분류 / 선택형 규칙 분류 | 분류 변경으로 실제 입출금 총액이 바뀌지 않음 |
| 확인 사유 | 계좌 미지정·상대 미상·시각 충돌 등 발생 → 확인/정정 | 원장 존재와 별개. 계좌/목적/상대 미상은 합계 포함 |
| 전송 결과 | 저장됨 / 미반영 확인 / 결과 불명 | 결과 불명에서 수기 중복 생성을 먼저 하지 않음 |
| 수집 설정 | 켜짐 / 일시 중지 / 동의 철회 / 기기 철회 | 기존 원장의 삭제 상태와 별개 |

거래가 ‘분류 완료’이면서 ‘시각 확인 필요’일 수 있다. 카테고리를 선택했다고 다른 확인 사유까지 닫지 않는다. 알림창에서 안내를 지우거나 클릭한 것도 해결 완료가 아니다. 사용자 정정은 규칙 재실행·늦은 알림보다 우선한다.

## 6. DB에 무엇을 나누어 저장하는가

현재 `user.users/roles/role_history`, `finance.accounts/transaction_categories/transaction_history/account_transfers/request_deduplication`을 보존한다. 아래 추가 책임은 **테이블·열의 논리 설계 제안이지 생성 완료 목록이나 확정 DDL이 아니다.** 같은 사용자 소유 관계를 API와 DB 모두 검증하고 과거 migration은 수정하지 않는다.

| 저장 책임 | 최소 내용·관계 | 보관하지 않거나 혼동하면 안 되는 것 |
| --- | --- | --- |
| 사용자/수집 기기 | 사용자, 서버 발급 기기 식별, 동의/철회 상태, 활성 수집 기기, 거주 시간대 변경 이력 | 은행 알림의 이름을 로그인 신원으로 쓰지 않음 |
| 계좌 연결 규칙 | 소유자, 출처 앱/유형, 부분 식별 또는 명시 기본 연결, 장부 계좌 | 전체 계좌번호·은행 소유 인증 상태를 임의 생성하지 않음 |
| 수집 접수·후보 | 소유자/기기/이벤트 ID, 판독 버전, 필요한 추출값·시각 근거, 원장/후보 연결 | 전체 알림 원문·스크린샷·OTP·일반 대화 |
| 원장 | 실제 금액·방향, nullable 계좌/카테고리, 거래 상대명, 날짜/시각 근거·정밀도·적용 시간대, 수정 version | 알림 개수만큼 같은 실제 거래를 복제하지 않음 |
| 계좌별 시작 잔액 | 소유자·계좌, 선택 설정 금액과 기준 시점, 수정 version·이력 | 장부 전체 공통값·새 수입·은행 검증 잔액이 아님 |
| 거래 대상/분류 규칙 | 사용자별 표기·유형, 명시 별칭, 조건·카테고리·version | 이름을 전역 인물 ID나 실제 가맹점 증명으로 사용하지 않음 |
| 이체/세부 금액 | 실제 출금·입금 연결, 원금·수수료 구성, 사용자 확인 | 이체 연결만으로 반대편 실제 거래를 만들지 않음 |
| 구매 묶음/환불 배분 | 사용자 지정 구매, 관련 지출·실제 입금, N:M 배분 금액 | 관계 행을 입출금으로 다시 합산하지 않음 |
| 수정/검토 이력 | 대상·사용자·변경 근거·version·시각 | 원문·비밀값을 감사 로그에 복제하지 않음 |
| 삭제 묶음/복구 | 삭제 범위·원래 ID·관계·기한·충돌 검증 | 다른 구매로 무제한 연쇄 삭제하지 않음 |
| 최소 실패 표식/안내 | 계정 격리된 불투명 요청 ID·상태·최초 실패 시각, 안내 사유 식별 | 미전송 금액·상대·본문을 대기열에 저장하지 않음 |

예: 사용자 U의 알림에서 상대 ‘상점 A’에게 20,000원 출금이 확인되면 원장 T1 한 건을 만든다. 처음에는 `account_id = NULL`, `category_id = NULL`, `counterparty_name = '상점 A'`일 수 있다. 전체 출금 합계에는 바로 20,000원을 포함한다. 사용자가 생활비 계좌와 ‘운동용품’을 선택하면 T1의 관계와 변경 근거만 바뀐다. 새 거래를 만들거나 전체 합계에 다시 더하지 않는다. ‘다음부터 자동 분류’를 따로 선택한 경우에만 규칙을 만든다.

### 거래 필드의 의미와 수정 보호

- **거래 상대명:** `counterparty_name` 하나로 통일한다. 출금이면 돈을 받는 상대, 입금이면 보내는 상대의 알림 표기다. 예를 들어 ‘사용자 → 상대 A 출금’은 ‘상대 A’를 저장한다. 기관명·사람 이름·장소 표기일 수 있으며 이름만으로 같은 실재 인물을 확정하지 않는다. 누락은 NULL이며 빈 값을 동일인 근거로 쓰지 않는다.
- **소비 목적:** 사용자가 선택한 대/소분류와 상세 메모다. 거래 상대명과 별개이며 상대명을 바꾸었다고 소비 분류를 자동 변경하지 않는다. 계층형 카테고리의 실제 열·부모/자식 제약은 DB 계약에서 정한다.
- **출처:** 알림/수기라는 기록 출처와 사용자/규칙/미분류라는 분류 출처를 분리한다. `자동분류 여부` 하나로 수집 방식까지 표현하지 않는다.
- **환불 연결:** 원장에 단일 환불 ID나 불리언을 넣어 N:M을 표현하지 않는다. 같은 구매 묶음 안에서 지출·실제 환불 입금과 배분 금액을 연결하는 별도 관계로 관리한다.
- **동시 수정:** 거래 `version`과 요청의 `expectedVersion`을 비교한다. 오래된 값은 409 충돌로 반환하고, 짧은 DB 트랜잭션 안에서 소유권·삭제 상태·버전 검증과 수정을 함께 수행한다. 화면을 열어 둔 동안 잠그지 않는다.
- **관계 수정:** 환불 연결 추가/수정/해제는 구매 묶음과 관련 거래 버전을 검사하고 배분 합계를 다시 검증한다. 연결 변경도 묶음 버전을 증가시킨다. 실제 환불 금액 수정·삭제와의 잠금 순서는 상세 계약에 명시한다. `version`은 전체 수정 이력·복구 사본·멱등성 키를 대신하지 않는다.
- **NULL 수정:** 수정 요청에서 필드를 생략하면 유지, 명시적 NULL이면 미지정/미분류로 변경한다. 다른 사용자 소유 계좌·카테고리로 연결하는 것은 API와 DB에서 모두 금지한다.

기존 DATE 기록은 DATE로 보존하고 실제 시각을 00:00으로 꾸며 넣지 않는다. 정확한 순간을 알 때만 UTC 시각과 원래 시각 기준·정밀도를 함께 다룬다. 실제 열 구성, 기존 데이터 이관, trigger/열별 GRANT/Drizzle/공용 계약의 동시 변경은 DB 하위 명세에서 검증한다.

## 7. 실제 돈·중복·이체·환불의 불변 조건

### 기록 대상과 중복

- ‘결제’라는 단어만으로 기록하지 않는다. 알려진 형식에서 실제 계좌 출금이 확인된 체크카드 결제는 기록하며, 현금 이동 없는 신용카드 승인·청구 예정은 별도 거래를 만들지 않는다. 취소 안내만으로 입금을 만들지 않는다.
- 제목/본문의 반복 금액, 잔액, 누적액을 거래 금액과 구별한다. 통화·단위가 불명확한 금액을 원화로 추측하지 않는다. 기존 원화 계약의 범위를 외화로 조용히 확대하지 않는다.
- 같은 접수 ID는 멱등 처리한다. 다른 알림이 비슷한 것은 ‘같은 요청’이 아니라 ‘같은 거래일 가능성’이다. 아래 자동 연결 조건에 해당하지 않는 의심 후보는 기존 기록을 유지하고 사용자 확인 후 연결하거나 별개 거래로 만든다.
- 같은 분·금액·이름의 정상 거래가 반복될 수 있다. 단순 본문 해시 UNIQUE로 폐기하지 않는다. 알림 키 재사용·갱신·그룹 요약도 은행 거래 ID로 간주하지 않는다.
- 수기 입력 뒤 늦은 알림, 동시 후보 확정, 삭제 후 재접수는 별도 검증한다. 알림을 같은 거래에 연결해도 사용자 수정은 덮어쓰지 않는다.

### 은행·토스 알림의 자동 연결과 지연 후보

은행 앱만 오면 그것만 처리하고 토스 알림을 기다리지 않는다. 토스만 오면 실제 계좌 이동 판독과 출처 단서를 확인해 기록한다. 은행과 토스가 같은 거래를 알린 경우 원장 한 건에 여러 최소 추출 근거를 연결한다. 출금/입금 방향이 다르면 중복이 아니라 이체 관계 검토 대상이다.

**자동 연결은 아래 조건을 모두 만족하는 경우에만 한다.**

1. 같은 사용자·같은 활성 수집 기기의 은행 앱/토스 알림 쌍이다.
2. 최초 기기 수신 간격이 **5,000ms 이내(경계 포함)**다. 서버 도착 시각이나 화면에 같은 분으로 표시되는지를 대신 사용하지 않는다.
3. 실제 계좌 이동으로 판독되고, 결측이 아닌 거래 상대명·방향·금액이 일치한다. 알려진 계좌 단서와 본문 거래 시각에 모순이 없어야 한다.
4. 서로의 비교 후보가 유일한 1:1 쌍이다. 복수 후보·NULL 상대·시각/계좌 충돌·수신 간격 신뢰 불가이면 자동 연결하지 않는다. 토스가 먼저 와도 조건은 같다.
5. 같은 거래에 연결한 뒤 합계를 한 번만 반영한다. 근거·판단 사유와 연결 해제/별개 거래 정정 경로를 제공하고, 기존 사용자 편집을 덮어쓰지 않는다. 전체 원문 보관은 하지 않는다.

5초 초과 건은 자동 연결하지 않는다. 믿을 만한 실제 거래 날짜·시각이 있으면 그것을 우선 비교하며, **그 시각을 알 수 없는 경우 새 알림의 기기 수신 시점 기준 최근 24시간**의 거래/근거를 비교한다. 서버 접수가 지연됐다는 이유로 검색 기준을 이동하지 않는다. 같은 사용자·상대명·방향·금액 및 알려진 계좌의 모순 여부를 비교하고 의심 후보의 추가 금액은 확인 전 합산하지 않는다.

24시간 밖 자료도 수동 검색·연결할 수 있다. 후보가 없다는 것만으로 별개 거래임이 입증되는 것은 아니므로 이후 사용자 정정이 가능해야 한다. 24시간은 후보 검색 범위이지 보관/삭제 기한이 아니며, 5초도 은행 앱 수신 시간의 실측 보장이 아닌 승인된 초기 제품 기준이다.

재부팅·시계 보정·기기 교체·알림 갱신으로 간격을 신뢰할 수 없으면 자동 연결을 보류한다. 부분 거래 시각, 재접수 ID, 검색 경계/상한/정렬, 늦게 발견된 충돌 근거, 연결·분리·수기 편집의 동시 처리 계약은 §12에 남긴다. 이름/금액/시간은 금융기관 거래 고유번호가 아니므로 오연결 가능성을 사용자 정정 경로로 다룬다.

### 입출금 집계와 소비 집계

입출금 합계는 선택 조건에 맞는 실제 현금 이동이다. 소비 집계는 그중 이체 원금 등을 구별해 보여주는 해석이다. 원장 금액을 바꾸지 않고 별도 표시한다.

| 합성 사례 | 저장/연결 | 표시 원칙 |
| --- | --- | --- |
| 같은 출금 19,800원을 은행 앱·토스가 알림 | 5초 이내·안전 조건 충족 시 자동 연결, 그 외 의심 후보는 사용자 확인 | 실제 지출 19,800원 한 번 |
| 내 A 계좌 출금 100,000원, 내 B 계좌 입금 100,000원 | 실제 2건 + 내 계좌 이체 관계 | 전체 입출금에는 각각 표시, 소비에는 원금 제외 |
| 실제 출금 100,500원 = 이체 원금 100,000원 + 수수료 500원 | 출금 1건 안의 세부 금액 | 총 출금 100,500원, 비용 500원. 부모+세부 금액 중복 합산 금지 |
| 비용이 별도 실제 출금으로 도착 | 별도 원장 1건 | 앞 출금에 다시 같은 수수료를 더하지 않음 |
| 지난달 지출 100,000원, 이번 달 실제 환불 97,000원 | 각 날짜의 실제 2건 + 환불 연결 | 이번 달 입금은 97,000원. 가상의 입금 100,000원/출금 3,000원 생성 금지 |

계좌 하나만 선택하면 그 계좌의 실제 이동만 표시한다. 이체 원금은 선택 계좌 수와 무관하게 소비에서 제외하되 연결 미확정은 임의로 이체 확정하지 않는다. 양쪽 날짜가 다르면 일/주/월 순변동을 억지로 0으로 만들지 않는다. 불완전한 알림에서 없는 반대편 입출금을 만들지 않는다.

환불은 **사용자가 정한 같은 구매 묶음 안의 N:M**이다. 여러 지출을 한 번에 돌려받거나 여러 번 나누어 돌려받을 수 있다. 배분은 실제 입금 안에서만 하며 같은 입금을 중복 배분하지 않는다. 보상 때문에 지출보다 환불액이 클 수 있고 사용자 확인 후 연결 가능하다. 원금/보상 상세 구분은 선택이다. 다른 구매의 집계·삭제에 영향을 주지 않는다.

원지출을 아직 기록하지 않았어도 실제 환불 입금은 남긴다. 필요할 때 모바일에서 원지출을 수기로 추가해 연결한다. 환불 공제액은 사용자가 선택적으로 설명할 수 있지만 차액을 무조건 수수료로 추측하지 않는다. 할부·분할 납부도 사용자 지정이며 예정 금액을 실제 지출로 미리 만들지 않는다.

## 8. 날짜·시간·필터

시각 우선순위는 **사용자 확인 → 알림 본문 거래 시각 → 같은 거래로 확인된 알림의 최초 기기 수신 시각(추정)**이다. 서버 도착 시각은 거래 날짜로 쓰지 않는다. 본문끼리 충돌하면 확인 사유를 남기고 특정 은행을 무조건 우선하지 않는다. 더 정확한 근거가 오면 추정값을 보완할 수 있지만 사용자 확인값은 덮어쓰지 않는다.

추정 시각이어도 실제 이동·금액·방향이 명확한 기록은 기간 합계에 포함한다. 계좌 미지정만으로 제외하지 않는다. 목록과 합계에서 추정값 포함 여부를 알린다. 이것은 시간 조건 규칙의 사용 허용과 별개다. 분 단위 알림을 초 단위 정확도로 표시하거나 날짜만 있는 과거 기록에 실제 시각을 만들어 넣지 않는다.

처음 선택한 거주 도시/지역의 IANA 시간대를 장부 기준으로 사용한다. 해외 거래 시각의 출처 시간대와 장부 표시 기준을 분리하고 이미 거주 기준으로 온 시각을 다시 환산하지 않는다. 출처의 시간대를 알 수 없으면 확정 시각으로 위장하지 않는다. 여행·휴대폰 시간대 변경은 장부 기준을 바꾸지 않는다.

### 영구 거주지 변경 — A안 승인(2026-10-15)

- 실제 이사로 장부 기준을 바꾸면 **과거 거래의 장부 날짜와 기존 일/주/월 집계를 유지하고, 변경 이후 발생한 거래부터 새 시간대를 적용**한다. 이전 기록을 새 시간대로 일괄 환산하는 B안은 채택하지 않는다.
- ‘이후’는 저장/수신 시점이 아니라 실제 거래 발생 시점 기준이다. 변경 뒤 도착한 이전 거래도 당시 기준을 적용한다. 시각이 추정이거나 DATE만 있어 전환 전후를 단정할 수 없으면 정밀도를 유지하고 확인 사유를 남긴다. 날짜 이동을 숨기거나 가짜 시각을 만들지 않는다.
- 설계 책임은 시간대 변경 이력(이전/새 IANA 값·적용 시점), 거래에 적용된 기준과 장부 날짜, 실제 시각 근거를 구분하는 것이다. 구체 열·전환 경계·사용자 시각 정정 시 재계산은 DB/조회 계약에서 검증한다.
- 예: 11월 1일에 거주 기준을 바꾸어도 10월 거래의 날짜·월별 합계를 다시 쓰지 않는다. 10월 거래 알림이 11월에 늦게 도착하면 수신일이 아니라 확인된 거래일과 당시 기준으로 기록한다.
- 설정 변경 전 과거 기록 유지와 이후 적용을 안내하고, 상세에서는 해당 거래의 적용 시간대를 볼 수 있게 한다. 여러 기준이 섞인 조회는 이를 표시하며 조회할 때마다 모든 과거 자료를 현재 시간대로 재해석하지 않는다.
- 선택형 규칙도 시간대 기준을 명시한다. 영구 변경 시 기존 규칙의 적용 기준·영향 안내와 이력은 규칙 계약에 포함하며 과거 분류를 자동 재실행하지 않는다. 이번 승인은 시간대 기능의 구현·DST 검증 완료가 아니다.

### 기간·계좌·카테고리 조회

- 계좌·카테고리 각각 복수 선택: 묶음 안 OR, 묶음 사이는 AND. 전체는 필터 해제이며 특정 값과 함께 선택하지 않는다.
- 기간은 일/주/월/년/직접 범위 중 최대 하나. 기본 미선택은 전체 기간이다.
- 주는 월요일~일요일 달력 기준. 직접 범위는 양쪽 장부 날짜 포함이다. 시간 범위로 조회하는 구간은 해당 구간에 적용된 기준의 시작일 이상·종료 다음 날 미만이며 DST 때문에 무조건 24시간을 더하지 않는다. 거주 기준 변경을 가로지르면 정책 구간별로 해석해 과거 장부 날짜를 유지한다.
- 최신 날짜·시각 우선, 동률은 안정적인 보조 ID로 정렬한다. ID 순서를 실제 은행 처리 순서로 설명하지 않는다. 시각 미상 기록은 그 사실을 표시한다.
- 필터 변경은 커서를 초기화한다. 전체 조건 합계는 내려받은 페이지 합계와 구별한다. 커서와 소유자·필터·정렬 기준의 결속은 조회 계약에서 명세화한다.
- 세부 금액/환불 배분의 카테고리 필터가 부모 거래와 어떤 관계로 집계되는지는 §12에서 먼저 닫는다. 한 금액을 부모와 세부 항목 양쪽에서 더하는 방식은 금지한다.

### 계좌별 시작 잔액 — 조건부 A안 승인(2026-10-15)

**사용자가 지정한 각 장부 계좌마다 시작 잔액 금액과 기준 시점을 따로 설정**할 수 있게 한다. 설정은 선택이며 계좌 생성·기록 이용의 필수 조건이 아니다. 실계좌 등록 API나 은행 명의 확인이 없어도 사용자의 장부 기준값으로 설정한다.

| 합성 계좌 | 시작 잔액 설정 | 이후 기록된 변동 | 표시 |
| --- | --- | --- | --- |
| 생활비 계좌 A | 기준 시점 잔액 200,000원 | 입금 50,000원·출금 30,000원 | 장부상 잔액 220,000원 |
| 저축 계좌 B | 별도 기준 시점 잔액 1,000,000원 | 입금 100,000원 | 장부상 잔액 1,100,000원 |
| 지출 계좌 C | 미설정 | 입금 20,000원·출금 5,000원 | 잔액 미설정, 기록된 순변동 +15,000원 |

- 계산은 **해당 계좌의 시작 잔액 + 기준값에 포함되지 않은 이후 실제 입금 − 이후 실제 출금**이다. 기준값에 이미 포함된 거래를 다시 더하지 않도록 시점 경계·시각 미상 자료 처리를 상세 계약에 명시한다.
- 미설정과 사용자가 명시한 0원은 다르다. 현재 양수 금액 계약만으로 둘을 표현할 수 있다고 가정하지 않는다. 음수/부채 표현과 기존 `opening_balance` 구조 재사용 방식도 구현 전 금액 계약으로 검증한다.
- 계좌 A의 시작 잔액 변경이 B의 잔액을 바꾸지 않는다. 계좌 미지정 거래는 전체 입출금 합계에 포함하되 어느 계좌의 잔액에도 임의 반영하지 않는다. 나중에 계좌를 지정하면 그 계좌의 기준 시점과 실제 거래 시점을 비교해 한 번만 반영한다.
- 시작 잔액은 새 수입이 아니므로 입출금 통계에 더하지 않는다. 계좌 잔액은 계좌 전체 기록에 따른 값이며 소비 카테고리 필터에 따라 은행 잔액처럼 바뀌는 값으로 보여주지 않는다.
- 누락 알림·수기 보완 때문에 실제 은행 잔액과 다를 수 있다. 항상 ‘장부상 잔액’으로 안내하고 일부 계좌가 미설정이면 전체 계좌 잔액 합계를 완전한 값처럼 표시하지 않는다.
- 변경·삭제·복구·환불·이체도 실제 해당 계좌/날짜의 변동으로 계산한다. 다른 계좌의 시작 잔액이나 실제 입출금 원장을 수정해 차액을 억지로 맞추지 않는다.
- 기존 조건은 유지한다. **시작 잔액 기능 구현 전에 변경 파일·코드량·작업 규모·구현/검증 예상 소요를 보고**하고 부담이 크면 B안(초기에는 입출금·순변동만 제공) 전환을 사용자와 확인한다. 이번 A안 승인은 무조건 초기 구현을 강제하거나 잔액 기능까지 완료했다는 뜻이 아니다. 시작 잔액의 PC/모바일 편집 경로·서버 권한은 계좌 관리 및 신규 거래 제한과 맞춰 상세 계약에 명시한다.

## 9. 선택형 분류와 안내

자동 분류는 기본 꺼짐이며 한 번 분류했다고 규칙을 만들지 않는다. 사용자가 활성화한 계좌·출처/유형·입출금 방향·거래 대상 범위 안에서만 적용한다. 개인 상대는 동명이인·목적 변경 가능성을 고려해 이전 분류 후보를 보여주고 매번 확인하는 흐름이 기본이다.

| 조건 | 승인된 경계 |
| --- | --- |
| 대상명 | 추출한 표기와 정확 일치, 사용자 명시 별칭만 연결. 부분/유사/AI 일치 금지 |
| 정리 | 앞뒤 공백 같은 최소 정리만. 내부 공백·지점·숫자·마스킹을 임의 삭제해 합치지 않음 |
| 금액 | 정확 금액 또는 범위, 양 끝 포함. 최소>최대는 잘못된 조건 |
| 요일·시간 | 선택 요일 안 OR, 다른 조건과 AND. 시작 포함·종료 제외, 자정 넘김은 시작 요일 |
| 시간 조건 없음 | 시각 미상만으로 실패시키지 않음. 같은 시작/종료를 임의 24시간으로 해석하지 않음 |
| 추정 시각 | 시간 조건 규칙에서는 기본 불허. 사용자가 규칙별 대체를 허용해야 적용 |
| 여러 규칙 | 서로 다른 카테고리 충돌은 미분류·확인. 첫 규칙 임의 채택 금지 |

별칭은 사용자/규칙 범위에서 관리하고 새 별칭으로 과거 기록을 일괄 변경하지 않는다. PG 표기가 조건에 맞아도 실제 가게를 검증한 것은 아니며 사용자가 언제든 정정할 수 있다. 카테고리 보관은 기존 기록/필터를 유지하되 새 선택에서 숨기고 관련 분류 규칙을 비활성화한다. 복원해도 규칙을 자동 재활성화하지 않는다. 계좌 보관은 목록 정리이며 수집 중지와 다르다. 유효한 동의·계좌 연결이 있으면 보관 계좌의 새 기록도 집계하고 해당 계좌임을 안내한다.

새 미분류/확인 사유의 첫 발생에서 **고정 60초 창**으로 안내를 묶는다. 새 건이 들어와도 계속 연장하지 않고 장부 저장을 60초 지연시키지도 않는다. 발송 직전 해결한 항목은 빼고 남은 것이 없으면 취소한다. 한 거래의 여러 사유를 여러 거래로 세지 않는다. 같은 사유는 반복 안내하지 않으며 기존 거래에 새 사유가 생기면 새 사유에 대해 한 번 안내할 수 있다. 일일 독촉은 없다.

60초는 논리적 묶음 기준이며 OS가 정확히 그 시각에 알림을 배달한다는 약속이 아니다. 다중 기기 조정·경계 동시 도착은 안내 계약에서 정한다. 잠금화면 금융정보는 기본 숨기고 자체 알림은 재수집하지 않는다. 모든 추출 기록과 확인 이유는 앱 안에서 확인 가능하게 하되 원문 알림을 영구 재생하는 기능은 제공하지 않는다.

## 10. 실패·계정 전환·보관·삭제

| 자료/상태 | 승인 정책 | 구현 시 주의 |
| --- | --- | --- |
| 알림 원문·스크린샷 | 별도 영구 보관 없음, 분석 후 폐기 | DB·로컬 파일·로그·오류 보고로 유출하지 않음 |
| 서버 장부 | 계좌/분류/상대가 미지정이어도 정상 원장 보관 | 미분류 거래를 실패 표식처럼 30일 자동 만료하지 않음 |
| 서버 미해결 확인 후보 | 서비스 이용·확인 목적이 유지되는 동안 사용자 처리까지 최소 추출값 보관(A안) | 금액/방향 불명확·중복 후보 대상. 90일 자동 만료 B안 미채택 |
| 미전송 금융 자료 | 장기 대기열·자동 재전송 없음 | 판독 실패와 전송 실패를 구별 |
| 최소 실패 표식 | 최초 실패부터 최대 30일, 해결 시 조기 정리 | 요청 ID·상태·실패 시각 등 최소 정보. 재로그인·중지로 기간 연장 금지 |
| 일반 거래 삭제 | 목록·집계에서 제외, 30일 복구 | 복구를 위해 보호된 실제 데이터가 남음. 즉시 물리 삭제라고 안내하지 않음 |
| 동의 철회/탈퇴 | 수집 중지·세션/권한 철회·해당 삭제 정책 적용 | 일반 삭제의 30일 복구를 계정 탈퇴에 자동 적용하지 않음 |

전송 결과가 불명이면 원래 요청의 저장 상태부터 조회한다. 저장되었으면 기존 거래를 보여주고, 미반영이 확인된 경우에만 모바일 수기 보완으로 연결한다. 이 상태 조회는 금융 payload의 자동 재전송이 아니다. 목록에 안 보이거나 실패 표식이 만료되었다는 사실만으로 미저장을 증명하지 않는다. 늦게 완료되는 원래 요청과 수기 보완의 경쟁은 원자적 중복 방지 계약이 필요하다.

확인 후보를 확정·기존 거래 연결·제외/삭제하면 불필요해진 중복 추출 사본을 정리한다. 명시적 삭제·탈퇴·해당 동의 철회·목적 소멸 정책은 미해결 보관 원칙보다 우선한다. 처리 결과·감사 근거·재수신 방지 표식의 최소 필드/수명과 백업 정리는 별도 계약으로 남긴다. 검색 범위 24시간과 자료 보관 기간을 혼동하지 않는다.

계정 A의 최소 표식은 A 재인증 뒤에만 확인한다. B 로그인 화면·캐시·배지·대기 안내에 A 자료나 건수가 나타나면 안 된다. 로그아웃/계정 전환 때 메모리 금융 자료를 지우며 A 요청을 B 자격으로 보내지 않는다. 수집 일시 중지는 새 수집·판독·전송만 멈추고 기존 장부·최소 표식·결과 확인은 유지한다. 재개는 이후 새 알림부터이며 중지 중 과거 알림 복원을 약속하지 않는다.

같은 구매로 연결한 지출·환불을 삭제할 때는 영향 범위를 미리 보여주고 승인된 묶음을 함께 삭제·복구한다. 다른 구매로 이어지는 모호한 관계는 무제한 연쇄 삭제하지 않고 범위를 해결하기 전 중단한다. 복구는 원래 ID·관계·날짜를 유지하며 동시 편집/유효하지 않은 관계를 조용히 덮어쓰지 않는다. 부분 복구 기능은 별도 승인 없이 추가하지 않는다.

삭제 후 재알림으로 부활하지 않아야 하지만, 영구 삭제와 재접수 방지 표식의 기간·백업 잔존·복구 충돌 처리는 아직 상세 계약이 필요하다. 30일 뒤 복구 불가와 물리 정리 작업의 완료 시점을 구분해 안내한다. 오프라인 기기·백업을 즉시 모두 삭제했다고 약속하지 않는다. 운영·법률 검증을 마친 것으로 표현하지 않는다.

### 한 구매의 처음부터 복구까지 — 합성 예시

1. 거주 기준 10월 5일 15:53, 상대 ‘상점 A’에게 20,000원 실제 출금이 판독된다. 계좌/카테고리 미지정이어도 출금 T1 한 건을 기록하고 전체 10월 5일 출금 합계에 20,000원을 포함한다.
2. 사용자가 생활비 계좌를 지정하면 같은 T1의 계좌 관계만 바꾼다. 특정 계좌 조회에 나타나지만 전체 합계는 여전히 20,000원이다. 시작 잔액이 설정돼 있다면 기준값에 포함된 거래인지 확인해 해당 계좌 잔액에 한 번만 반영한다.
3. 사용자가 ‘운동용품’으로 분류한다. T1의 카테고리와 수정 이력만 바뀌며 자동 규칙은 생성하지 않는다. 이미 해결했으므로 예정된 미분류 안내에서도 빠진다.
4. 은행/토스 두 알림이 5초 이내·안전 조건을 충족하면 근거를 T1에 자동 연결한다. 늦은 의심 알림은 사용자가 같은 거래로 확인한 뒤 연결하며 추가 금액을 더하지 않는다. 거래 시각이 없을 때만 최근 24시간 자동 후보 검색을 적용하고 수동 연결도 유지한다.
5. 10월 12일 실제 입금 7,000원은 T2로 저장한다. 사용자가 T1의 부분 환불로 연결하면 같은 구매 안의 배분 관계를 만든다. 10월 5일 출금 20,000원과 10월 12일 입금 7,000원은 각각의 날짜에 남는다.
6. 사용자가 이 구매를 삭제할 때 T1·T2와 연결 관계를 미리 보여주고 함께 삭제한다. 두 날짜의 집계에서 제외하지만 다른 구매의 기록은 바뀌지 않는다.
7. 30일 이내 복구하면 원래 T1·T2·관계를 복원하고 원래 날짜의 합계로 돌아간다. 새 거래 2건으로 다시 만들지 않으며 충돌이 있으면 먼저 해결한다.

이 흐름은 채택 정책의 정합성 예시다. 30일 경계·영구 정리·재접수 방지의 실제 구현은 아래 선행 계약과 시험을 거쳐야 한다.

## 12. 구현 전에 닫을 상세 계약

확정한 정책을 다시 A/B 질문으로 돌리지 않는다. 아래 **기술 계약 6개 묶음**은 하위 설계 담당자가 근거·제안·영향·테스트를 준비할 항목이다. 6번 더 사용자 선택을 받아야 한다는 뜻은 아니다. 구현에 필요한 계약을 관련 기능 착수 전에 작성하며 미정 값을 코드의 임의 기본값으로 만들지 않는다.

| 계약 | 남은 확인 / 완료 조건 | 선행 시점 |
| --- | --- | --- |
| 모바일 인증·기기·채널 권한 | 복수 로그인·단일 수집 기기·PC 관리 범위는 승인. 갱신/철회·기기 전환, 안전한 자격 저장, 채널 권한의 서버 강제·늦은 쓰기 차단 | 모바일 API 접속 전 |

## 13. 하위 과제와 상대 규모

이 표는 개발 순서와 의존 관계이지 실행 승인이나 정밀 일정이 아니다. 각 단계의 파일별 계획은 이 통합 설계 검토 뒤 작성한다. 하나의 큰 파일에 수집·판독·집계·UI를 넣지 않고 책임별 모듈로 나눈다.

| 순서 | 결과물 | 주요 영향 경로·상대 규모 |
| --- | --- | --- |
| 1 | 기본 원장 정합성: 일반 입출금 계좌/카테고리 nullable·거래 상대명·조회/수정·PC 표시와 검증 | `packages/contracts`, `packages/database`, `apps/api/src/transactions`, 웹 거래 화면·테스트 · 중 |
| 2 준비 | 모바일 인증·채널/기기 권한, 정밀 시각·거주 기준 이력 등 각 후속 단위의 기술 계약 | 기존 인증/원장 경계 재사용 검토, 영향 범위별 분리 · 중~대 |
| 2 | 모바일 로그인·계좌 지정·수기·기본 조회 | 신규 `apps/mobile`, 기존 API 재사용 · 대 |
| 3 | 검증 가능한 한 형식의 알림→미분류→분류→PC 조회 | 네이티브 수집·판독·접수·후보 저장 · 대 |
| 4 | 여러 출처·중복/실패·선택형 규칙·안내 | 수집/규칙/안내 모듈, 기기 검증 · 대 |
| 5 | 이체·환불·구매 묶음·삭제/복구·정밀 집계 | DB 관계·집계 계약·모바일 상세/복구 · 대 |

기본 조회와 필요한 PC 표시, 각 단계의 단위·계약·DB 검증은 해당 단계에 포함한다. 모든 PC 작업과 시험을 마지막에 몰아두지 않는다. 한 알림 형식으로 기술 검증하는 것은 사용자 은행을 한 곳으로 제한한다는 뜻이 아니다. 선택형 규칙은 사용자에게 선택이라는 뜻이며 개발 대상에서 제외한다는 뜻이 아니다.

첫 단위는 기존 원장 기반을 맞추는 작업이며 모바일 수집기·정밀 시각 전체 이관·환불·규칙·다중 필터를 한 번에 넣지 않는다. 이들은 후속 단위로 분리한 것이지 요구사항에서 삭제한 것이 아니다. 계좌별 시작 잔액은 계좌 관리 단계에서 별도 공수 보고 후 편성한다. 정확한 변경 파일 수·실행 명령은 첫 단위의 상세 계약과 파일별 실행 계획에서 확정한다.

DB는 추가형 migration으로 검토하고 폐기용 PostgreSQL에서 기존 자료·권한 보존을 확인한다. 실제 개발/운영 적용은 프로젝트·migration 이력·실행 주체를 확인하는 별도 단계다. 기존 은행 A5 미커밋 작업, 무관한 디자인/진입점 변경을 함께 수정·커밋하지 않는다.
