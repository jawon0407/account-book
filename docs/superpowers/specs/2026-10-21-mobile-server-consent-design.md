# Android 화면의 서버 동의·철회 연결

## 사용자 목표와 범위

기존 수집 설정 화면에서 서버가 확인한 동의 상태를 보고 명시적으로 동의/철회한다. 사용자는 별도 승인 질문 없이 기존 문서에 따라 개발·검증하고 변경 파일과 진행 상황을 기록하도록 요청했다. 기존 화면과 서버 계약을 잇는 한정된 작업이며 별도 기능/의존성을 추가하지 않는다.

실제 알림 읽기·업로드·수집 시작/중지·출처 선택·운영 Supabase 변경·외부 배포는 제외한다. 기존 수기 장부는 유지한다. 새 기기 권한이나 USB 디버깅 허용을 강제로 설정하지 않는다.

## 선택한 연결 방식

기존 NativeCollectorClient에 고정 경로 `collector/consent`의 readConsent/changeConsent를 추가하고 SessionManager의 인증·세대·401 처리 경계를 재사용한다. 별도 HTTP 구현/이중 동의 저장소보다 경계가 작다. UI는 서버 상태만 사용하며 이전 SecureStore의 로컬 동의를 읽거나 자동 전송하지 않는다. 오래된 저장 값은 이 단계에서 삭제/이관하지 않는다.

서버 계약은 기존 NotificationConsentState와 NotificationConsentChangeInput을 그대로 사용한다. 회원·설치 ID/시각/토큰은 화면의 요청 본문에 넣지 않는다. 요청 자동 재전송은 0회다.

## 상태와 사용자 경험

1. 화면 진입/앱 복귀 후 검증된 세션으로 서버 동의와 Android 접근 상태를 각각 조회한다. 서버 조회 전/실패/변경 중에는 동의를 유효하게 표시하지 않는다.
2. `not_granted`, `granted`, `withdrawn`, `outdated`를 구별한다. `outdated`는 재확인 또는 철회할 수 있다. 수집 기기 지정·OS 접근·서버 동의는 별개이며 자동 수집은 아직 시작하지 않는다.
3. 동의는 고지와 현재 기대 버전을 사용자가 확인한 뒤 PATCH한다. 반환 버전은 기대 버전+1, 상태는 요청한 결과와 같아야 한다.
4. 철회도 서버 성공을 확인해야 완료라고 표시한다. 기존 거래와 Android 권한은 자동 삭제/해제하지 않는다.
5. 409·네트워크/응답 오류는 미확정 상태로 닫는다. GET 재조회 뒤 현재 상태를 보여주며 PATCH를 재시도하려면 사용자의 새 확인이 필요하다. 철회 실패 후 서버가 여전히 granted이면 다시 철회가 필요하다고 안내한다. 이 단계에는 자동 수집 자체가 없으며 오프라인 철회 큐도 추가하지 않는다.
6. 서버 조회가 실패해도 OS 상태가 확인되었고 접근이 켜져 있으면 권한을 끄기 위한 설정 이동을 허용한다. OS 조회 실패가 서버 철회를 막지 않는다. 서버 상태를 모르는 동안 권한을 새로 켜도록 유도하지 않는다.
7. 로그아웃/계정 변경/백그라운드 재검증/화면 이탈 뒤 도착한 응답은 표시하지 않는다. 중복 버튼은 한 요청만 보낸다. 서버 변경 뒤 OS 설정은 자동으로 열지 않는다.

## 검증

- HTTP 고정 경로·Bearer/쿠키 제외·strict 입력/응답·위조/오래된 고지 거부·무재전송.
- 세션 만료/갱신·로그아웃/재검증 뒤 늦은 응답 차단.
- 모델의 위 7개 상태 흐름, 부분 실패, 충돌 재조회, 동일 요청 중복 차단.
- 전체 회귀·타입·린트·Android 번들, PC Playwright 조회/새로고침/로그아웃.
- 실제 휴대폰이 없으면 새 모바일 UI의 실기기 결과로 표시하지 않는다. 로컬 테스트 API의 DB 준비 상태도 별도로 확인해 코드 연결과 실행 환경을 구분한다.

완료 기준은 제품 코드와 자동 검증 및 기록이다. 원격 CI·운영 DB·독립 APK·실금융 자동 기록 완료로 표현하지 않는다.
