# Android 세션 경계 — 첫 구현 단위

작성: 2026-10-16. 기준: `feature/bank-state-transitions`, 기존 미커밋 원장·인증 보완을 보존한다.

## 목적과 범위

Android부터 구현한다는 승인에 따라 모바일 접속 전 필요한 서버 인증 경계를 만든다. **이 문서의 첫 단위를 완료해도 Android 앱, 모바일 로그인 HTTP 경로, 단일 수집 기기가 완성된 것은 아니다.**

현재 웹은 Supabase 제공자 토큰을 서버에서 암호화하고, 무작위 세션 식별자만 브라우저 쿠키로 전달한다. 모바일에서도 이 저장·갱신·철회 정책을 재사용한다. 제공자 갱신 토큰이나 BFF→API 서명키를 앱에 배포하지 않는다.

## 검토한 방식

| 방식 | 판단 |
| --- | --- |
| Android가 Supabase 토큰으로 NestJS에 직접 접속 | 가능하지만 두 번째 JWT 검증·철회 경로와 소셜/네이버 차이를 동시에 추가해야 한다. 첫 단위에서는 채택하지 않는다. |
| Android도 서버의 불투명 세션 경계 이용 | 기존 제공자 어댑터·암호화·복구 철회를 재사용한다. 이 방향으로 단계적으로 구현한다. 모바일용 경로의 입력/응답과 요청 제한은 후속 단위에서 연결한다. |
| 웹 세션에 `mobile` 헤더만 붙임 | 거부. 사용자 지정 헤더가 서버 권한을 바꾸면 안 된다. |

## 이번 단위의 확정 계약

1. `app_private.auth_sessions.client_channel`은 `web` 또는 `android`다. 기존 행과 기존 생성 경로는 `web`으로 유지한다.
2. `device_id`는 앱 설치 단위를 나타내는 무작위 UUID다. Android 세션에는 필수이고 웹에는 NULL이다. 전화번호·IMEI·광고 ID를 쓰지 않는다. 실제 물리 기기나 정식 앱의 증명은 아니다.
3. `SessionService`의 채널은 서버가 인스턴스를 구성할 때 고정한다. 요청 헤더·본문에 따라 웹 인스턴스의 채널을 바꾸지 않는다. Android용 인스턴스만 `create(tokens, now, deviceId)`로 세션을 만든다.
4. `resolve`·`refresh`는 저장된 채널과 서비스의 채널이 다르면 `expired`로 거절한다. 잘못된 Android 기기 ID, 웹에 붙은 기기 ID, 채널이 없는/알 수 없는 DB 행도 허용하지 않는다. 채널 검사 전에 토큰을 복호화하거나 제공자 갱신을 호출하지 않는다.
5. `revokeCurrent`는 해시와 고정 채널을 DB 조건으로 함께 검사한다. 웹 로그아웃이 Android 식별자를 받아도 Android 세션을 변경하지 않는다. 반대 방향도 동일하다.
6. 전체 로그아웃·비밀번호 복구는 **모든 채널**을 철회한다. 채널 도입으로 비밀번호 복구 후 Android 세션이 살아남아서는 안 된다.
7. 기존 7일 유휴/30일 절대 수명과 암호화 토큰 교체 CAS를 유지한다. 토큰 갱신으로 채널·기기 ID를 변경하지 않는다. 앱 식별자 자체의 회전 프로토콜은 이 단위의 기능이 아니며 모바일 HTTP 계약에서 별도로 정한다.
8. `app_session_bff`만 기존 인증 테이블에 접근한다. `app_api`, `anon`, `authenticated`, `service_role`에 인증 테이블 권한을 추가하지 않는다. 기존 금융 테이블/RLS는 변경하지 않는다.

## 후속 계약과 연결 순서

- **모바일 로그인 경로:** Android 전용 서버 세션 인스턴스, 검증된 사용자, 쿠키와 분리된 Bearer 식별자, 요청 제한, 안전한 응답, 로그아웃·계정 전환을 연결한다. 외부 OAuth는 시스템 브라우저/PKCE·일회성 교환으로 설계하며 토큰을 URL에 싣지 않는다. 이번에는 HTTP 경로를 열지 않는다.
- **NestJS 위임:** 서버가 검증한 채널·기기만 서명한 위임 토큰에 포함한다. PC의 새 거래 작성 제한도 서버에서 강제한다. 단순 `channel` 헤더와 기기 UUID만으로 OS 진위를 보증하지 않는다. 강한 앱/기기 증명이 필요하면 별도 attestation 과제로 다룬다.
- **단일 수집 기기:** 로그인 세션과 수집 권한은 별개다. 계정별 활성 기기·단조 증가 세대 번호를 두고 전환/수집 쓰기가 같은 잠금 경계에서 직렬화되어야 한다. 전환이 먼저 commit되면 이전 세대의 새 쓰기를 거부한다. 기기 교체가 다른 기기의 조회 로그인까지 로그아웃시키지는 않는다. 이 구조의 DB/API는 다음 단위에서 구현·동시 시험한다.
- **Android 앱:** 안전한 저장소에 앱 식별자/설치 ID만 보관하고 백업에서 제외한다. 원문 알림·서버 비밀키는 저장하지 않는다. Expo Go만으로 네이티브 수집 검증을 완료했다고 하지 않는다.

## 검증과 배포

합성 사용자만 사용한다. 서비스 단위 시험으로 양방향 채널 혼용·잘못된 행·갱신 부작용을 검사하고, 실제 폐기용 PostgreSQL에서 기존 행 기본값·CHECK·runtime 권한·저장/조회·채널별 및 전체 철회를 검증한다. 기존 웹 로그인/복구/로그아웃은 PC Playwright 회귀로 확인한다.

배포 순서는 추가형 migration → BFF 코드다. 새 코드는 추가 열이 없는 DB에서 정상 실행된다고 가정하지 않는다. migration을 먼저 적용해도 구버전 웹 INSERT는 `web` 기본값으로 호환된다. hosted DB 적용·운영 배포는 이번 범위가 아니다.

## 공식 근거 및 한계

- [Supabase 세션](https://supabase.com/docs/guides/auth/sessions): 제공자 세션과 앱의 서버 세션은 별개다. JWT 만료만으로 즉시 철회를 대체하지 않는다.
- [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/): Android Keystore 기반 암호화와 백업 제외 요구를 앱 구현 시 검증한다. 이번 단위는 SecureStore 설치/실기기 시험이 아니다.
- [Supabase 변경 이력](https://supabase.com/changelog): 2026-10-16 확인. 11/10 예정된 구형 TLS 암호군 중단은 향후 모바일 연결 시험 항목으로 남긴다. 이번 변경은 제공자 API 형식을 바꾸지 않는다.

이 단위의 결과는 채널 경계이지 금융 알림의 진위 증명, 한 대 수집 제한, 정식 APK, iOS 지원 완료가 아니다.
