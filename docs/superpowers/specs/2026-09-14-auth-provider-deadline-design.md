# 인증 제공자 작업 시간 제한 설계

- 설계 식별일: 2026-09-14. 도구 오류로 미뤄졌던 기록을 사용자 재개 요청 후 저장했다.
- 브랜치/기준: `feature/auth-provider-deadline` / `bb537e5`.
- 승인: 사용자가 **A안(Supabase SDK 유지), 작업당 총 5초**를 확정했다.
- 상태: 2026-09-15 [파일별 실행 계획](../plans/2026-09-15-auth-provider-deadline.md)에 따라 제품 구현과 테스트를 추가했다. JSON 구문 오류 보호까지 보완한 최종 전체 verify는 937개 테스트·타입·lint·API/웹 빌드 통과다. 마지막 보안 보완은 독립 재검토 Approved이며 새 수정 요구사항은 없다. 분기 coverage 92.48%는 기존 100% 기준 미달로 남고 이번 코드 검토로 면제되지 않는다. 실제 배포 환경 검증·커밋·푸시는 하지 않았다.
- 결정 근거: [R1 이후 검토 기록](../../status/2026-09-14-auth-provider-deadline-design-review.ko.md).

## 1. 목적과 범위

외부 인증 서버가 응답하지 않을 때 가계부 서버가 오래 기다리지 않도록 한다. 기존 Supabase SDK를 유지하면서 직접 HTTP 호출과 SDK 호출에 같은 시간 정책을 적용한다. 인증 제공자 작업을 시작한 뒤 총 5,000ms를 넘으면 요청을 취소하고 고정된 가용성 오류로 종료한다.

이 시간은 사용자의 소셜로그인 입력이나 이메일 확인을 기다리는 시간이 아니다. DB 처리, 전체 BFF 요청, 화면 첫 표시(FCP)도 이번 시간 예산에 포함하지 않는다. 따라서 화면 전체가 항상 5초 안에 완료된다는 뜻은 아니다. 이벤트 루프가 멈추면 타이머 실행도 늦어질 수 있으므로 실시간 시스템 수준의 보장은 아니다.

신규 라이브러리, SDK/프레임워크 교체, DB 스키마, 화면/CSS, 브라우저 연결 종료의 전역 전파, 자동 재전송은 추가하지 않는다. 기본 브랜치의 기존 보안 패치 반영·배포는 별도 승인 작업이다.

## 2. 작업 하나의 의미

| 제공자 작업 | 포함되는 흐름 | 예산 |
| --- | --- | --- |
| 가입 | signup 요청과 본문 읽기 | 총 5초 |
| 비밀번호 로그인 | SDK 로그인과 응답 검증 | 총 5초 |
| 메일/OAuth/복구 코드 교환 | 공통 PKCE 교환과 응답 검증 | 교환 1회당 총 5초 |
| 세션 갱신 | SDK 갱신과 그 내부 재시도 | 총 5초 |
| 제공자 로그아웃 | setSession 후 signOut | 두 단계 합계 5초 |
| 비밀번호 변경 | setSession, 사용자 일치 검사, updateUser | 전체 합계 5초 |
| 복구 이메일 요청 | recover 요청과 본문 읽기 | 총 5초 |
| OAuth 시작 URL 생성 | URL 조립만 수행 | 타이머 없음 |

입력·설정 검증을 통과한 후 외부 작업을 시작할 때 예산을 만든다. 네트워크 요청이 하나 더 생겨도 마감 시각을 초기화하지 않는다. 예를 들어 setSession에 3초를 썼다면 updateUser에는 최대 2초가 남는다. 서로 다른 호출은 서로의 예산이나 취소 상태에 영향을 주지 않는다.

## 3. 구성 요소와 책임

```text
인증 서비스
  → 기존 SupabaseAuthAdapter (입력 검증·작업 순서)
    → 작업 전용 deadline (총 예산·취소·종료 상태)
      → 직접 HTTP 또는 SDK에 주입한 fetch
        → Supabase Auth
```

### 3.1 어댑터

공개 `AuthProviderPort` 메서드의 인자와 결과는 유지한다. 기존 입력 검증·사용자 ID 대조·응답 검증도 보존한다. 작업의 시작과 끝을 감싸는 위치에서 deadline을 만들고, 두 단계가 이어지는 작업에서는 같은 인스턴스를 전달한다. 다음 단계 호출 직전과 결과를 성공으로 반환하기 직전에 유효 상태인지 확인한다.

### 3.2 Deadline

서버 전용 모듈이 경과 시간 측정, 마감 시각, AbortController, 활성 타이머/리스너의 정리를 담당한다. 경과 시간은 단조 증가 시계를 기준으로 삼으며 정상 응답과 마감이 경쟁할 때 마감 시각 이상이면 성공을 수용하지 않는다.

상태는 실행 중에서 성공·실패·시간 초과·외부 취소 중 하나로 단 한 번 전이한다. 종료된 객체는 다시 열리지 않는다. 메서드 이름·구체적인 TypeScript 인터페이스는 실행 계획에서 정하되 이 상태 계약을 변경하지 않는다.

### 3.3 직접 HTTP 경계

fetch의 헤더 수신뿐 아니라 응답 본문을 읽는 구간까지 보호한다. 전달받은 signal이 있으면 유지·결합하며 원본 Request나 호출자의 AbortController를 변경하지 않는다. 만료 시 실제 요청 및 본문 스트림을 취소한다. 주입된 비협조적 fetch가 abort를 무시해도 늦은 결과를 성공으로 반영하지 않으며, 해당 mock의 실제 네트워크 중단까지 보증했다고 주장하지 않는다.

### 3.4 SDK 경계

기존 요청별 새 비영속 SDK 클라이언트 생성 원칙을 유지한다. SDK의 사용자 정의 fetch 연결 지점에 작업 전용 전송 함수를 넣는다. SDK 전체를 mock하지 않고 현재 설치된 SDK에 이 함수를 연결한 테스트로 실제 호출 경로를 확인한다.

SDK 내부에 이미 존재하는 재시도는 전체 5초 예산 안에 제한한다. 앱이 새 재시도를 추가하지 않는다. SDK backoff 중 마감되더라도 호출자에게 실패를 반환할 수 있어야 하며, SDK가 나중에 다시 호출하더라도 네트워크 전송은 차단한다. 외부 SDK의 내부 대기 promise 자체를 강제로 중단할 수 있다고 주장하지 않는다. 우리 코드가 소유하는 타이머·리스너·전송은 정리하고 늦은 promise 종료를 안전하게 관찰한다.

## 4. 오류·보안 정책

- 시간 초과·취소·전송 장애는 기존 `AUTH_PROVIDER_UNAVAILABLE`로 처리한다. 원시 URL·헤더·토큰·비밀번호·제공자 응답 원문·예외 원문은 공개 응답이나 로그로 전달하지 않는다.
- SDK가 fetch 예외를 로그로 남기는 경로도 보호 대상이다. SDK에 원시 예외를 그대로 던진 뒤 어댑터 최상위에서만 숨기는 것으로 완료하지 않는다. 본문 읽기 실패도 포함한다.
- 내부 오류 변환 방식은 실제 SDK로 검증한다. SDK를 중단하려고 만든 내부 응답이 잘못된 비밀번호 오류나 계정 열거 방지 성공으로 오인되지 않아야 한다. HTTP 400만 반환해 이를 해결한 것으로 간주하지 않는다.
- 실제 공급자의 429, 이메일 미인증, 잘못된 자격 증명, PKCE 오류, 가입·복구의 계정 존재 여부 은폐 정책은 기존대로 유지한다.
- 전역 console 교체, node_modules 직접 패치, 테스트에서 오류 검사를 삭제하는 방식은 사용하지 않는다.
- 성공·실패·취소·만료 모두 정리 경로를 실행한다. 늦게 reject된 promise를 방치해 unhandled rejection이 생기지 않게 한다.

## 5. 취소와 데이터 변경의 한계

취소는 롤백이 아니다. 우리 서버가 응답을 받기 전에 Supabase가 비밀번호 변경이나 토큰 교환을 처리했을 수 있다. 이런 결과 불확실성을 이유로 가입·변경 요청을 자동 재전송하지 않는다.

어댑터가 실패한 뒤 상위 서비스가 정상 로그인 완료·로컬 세션 회전 완료 등 성공 후처리로 진행하지 않는지 확인한다. 기존 로컬 로그아웃 우선 처리, 복구 요청 선점, 재사용 차단 정책도 보존한다. 외부 변경 성공/로컬 실패의 보상 프로토콜까지 새로 도입해야 하는 결함을 발견하면 별도 설계 대상으로 보고하며 이번 패치에 섞지 않는다.

## 6. 변경 후보와 규모

**2026-09-15 실행 계획 확정:** 아래는 최초 후보이며 실제 파일 지도는 [실행 계획 0절](../plans/2026-09-15-auth-provider-deadline.md#0-현재-상태와-파일-지도)을 따른다. 기존 `http-client.ts`의 fetch 주입점을 재사용해 이 파일은 수정하지 않는다. 새 모듈은 `auth/supabase/provider-request-deadline.ts`(시간 관리)와 `auth/supabase/provider-operation.ts`(전송 경계)로 분리한다. 총 14파일, 제품 약 180~300줄·테스트 약 250~450줄로 구체화했으며 정책 범위는 동일하다.

이 설계 기록 단계는 문서 3파일이다. 구현은 중간 규모이며 제품·테스트·설정·결과 문서 약 12~14파일을 예상한다. 기존 검토 기록과 이 서면 설계의 유지보수는 별도 문서 이력이다. 정확한 파일 수는 실행 계획의 책임별 분리 결과로 고정한다.

| 구분 | 파일/역할 |
| --- | --- |
| 제품 수정 | `apps/web/src/server/auth/supabase-auth-adapter.ts`: 작업 수명 연결 |
| 제품 수정 | `apps/web/src/server/auth/supabase/http-client.ts`: 전송·본문 읽기 경계 |
| 제품 수정 | `apps/web/src/server/auth/supabase/sdk-client.ts`: 작업 fetch 주입 |
| 제품 신규 | `apps/web/src/server/auth/provider-request-deadline.ts`: 예산·취소·정리 |
| 테스트 | 어댑터 연결 회귀, deadline 단위, 실제 SDK 전송, 필요한 fixture/상위 서비스 회귀 |
| 설정 | `apps/web/vitest.config.ts`: 신규 서버 모듈 coverage 포함 |
| 결과 문서 | 실행 계획, 백엔드 인증 설명, 테스트 가이드, 진행 현황 |

초기 추정은 제품 150~250줄, 테스트 200~350줄 변경이다. 줄 수 목표를 맞추려고 실패 경로나 검증을 생략하지 않는다. 새 함수에는 역할·인자·반환값·오류와 취소 책임을 한국어 주석으로 설명한다. 인증 토큰·서버 비밀 타입은 공용 브라우저 패키지로 옮기지 않는다.

## 7. 검증과 완료 기준

다음 실패를 통제한 fetch와 fake timer로 먼저 재현하고 최소 구현으로 통과시킨다. 민감값 테스트에는 실제 비밀 대신 고유한 가짜 표식만 사용한다.

| 검사 | 통과 조건 |
| --- | --- |
| 마감 직전/정확한 마감/마감 이후 | 경과 시간 기준이 일관되고 늦은 성공을 거부 |
| 헤더·본문이 각각 지연 | 두 구간 모두 예산에 포함, 실제 signal 취소 확인 |
| 두 단계 순차 작업 | 합계 5초, 첫 단계 후 다음 단계 진입 검사 |
| SDK 갱신 재시도/backoff | 5초 이후 추가 네트워크 호출 없음 |
| 정상·실패·만료·외부 취소 | 우리 타이머·리스너 정리, 미관찰 거부 없음 |
| 병렬 작업 | 한 작업의 취소가 다른 작업에 전파되지 않음 |
| 로그·오류 | 토큰/비밀번호/URL/원시 예외 표식이 출력에 없음 |
| 기존 인증 정책 | 429·PKCE·계정 열거 방지·사용자 대조·후속 처리 유지 |

focused 검사 후 전체 `pnpm verify`, coverage 측정, 독립 리뷰와 한국어 결과 문서를 남긴다. 기존 웹 분기 coverage 91.86%와 100% 임계값의 격차를 숨기거나 임계값을 낮추지 않는다. 테스트 개수보다 실패 경로의 검증 여부가 완료 기준이다. 실제 hosted IdP·DB·한국망 p95·timeout 비율은 별도 환경에서 측정해야 한다.

## 8. 문서 검토와 다음 단계

A안과 5초 예산은 이미 승인됐으므로 다시 선택을 요청하지 않는다. 이 서면이 승인 내용을 정확히 담았는지 확인한 후 실행 계획을 작성한다. 그 단계에서 SDK 전송 오류의 안전한 표현, 함수 인터페이스, 파일별 변경·테스트 순서를 실제 설치 SDK와 맞춰 명시한다. 요구사항을 충족하려면 새로운 정책이나 범위 확장이 필요한 경우에만 추가 결정을 요청한다.

자체 검토: 작업 단위와 제외 시간, 성공/마감 경쟁, SDK 잔여 작업, 본문 취소, 민감값 경계, 기존 정책 보존, 검증 범위를 서로 대조했다. 구현 완료·실환경 검증·배포를 주장하지 않는다. 이번 설계 문서 저장에는 새로운 코드 테스트를 실행하지 않았다.
