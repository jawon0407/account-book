# 알림 거래 접수 API·DB 기반 — 2026-11-02

## 현재 범위

보안 수정 커밋 `a381626`의 원격 CI 두 건 성공을 확인한 뒤, 알림 판독 결과를 서버 장부에 접수하는 **비활성 상태의 서버 기반**을 구현했다. 이번 단위가 휴대폰의 실제 알림을 자동으로 저장하기 시작했다는 뜻은 아니다. 운영 Supabase에는 SQL을 적용하지 않았다.

작업 계획: [API·DB 기반 계획](../superpowers/plans/2026-11-02-notification-ingestion-foundation.md). 보안 원인·수정·원격 CI 근거: [의존성 보완 결과](2026-11-02-notification-dependency-security.ko.md).

변경 범위는 문서 포함 19개 파일(신규 11개)이다. 보안 패치와 분리한 로컬 기능 커밋으로 정리하며, 이 후속 단위의 원격 푸시·CI는 보안 패치의 성공과 구분한다.

## 데이터 흐름과 역할

1. Android에서 판독한 최소 필드를 서버에 전달하는 계약을 정의했다. 전체 알림 본문, 계좌번호, 사용자 ID, 임의 메모는 이 입력에서 받지 않는다. 현재 검증한 입력 형식은 `kb-v1` 한 종류다. 금융 앱 선택 화면을 고정 목록으로 제한한다는 의미는 아니다.
2. NestJS는 서명된 사용자·Android 세션·전용 권한을 확인한다. 웹 채널은 거래 접수를 할 수 없다. 본문으로 다른 회원을 지정할 수 없다.
3. 저장소는 현재 동의와 대표 수집 기기 버전을 같은 DB transaction 안에서 잠그고 확인한다. 다른 잠금 대기로 시간이 흐른 경우 INSERT 직전에 만료 여부를 다시 확인한다.
4. 명확한 입출금은 기존 `finance.transaction_history`에 저장한다. 계좌·카테고리는 미지정(NULL)이어도 된다. 거래 상대명과 금액은 이 원장에만 있으며, 별도 접수 표에 복사하지 않는다.
5. `finance.notification_receipts`는 회원별 이벤트 ID, 원장 ID, 요청 내용의 지문, 판독기 버전, 수신 시각, 시각 확인 필요 여부만 가진다. 원장과 접수 기록이 모두 저장되거나 둘 다 취소된다.
6. 같은 회원·이벤트 ID의 같은 입력을 다시 보내면 처음 원장 ID를 돌려준다. 같은 ID에 금액 등 다른 내용을 넣으면 충돌 오류다. 사용자가 수정하거나 휴지통으로 보낸 원장을 재전송으로 덮어쓰거나 복구하지 않는다.

### 두 가지 ‘중복’의 차이

| 상황 | 이번 단위 |
| --- | --- |
| 네트워크 때문에 같은 접수 ID가 두 번 전송됨 | 한 번만 저장 |
| 국민은행 알림과 토스 알림이 같은 거래를 각각 알려줌 | 아직 판별하지 않음. 5초·안전 조건 정책은 후속 |

두 번째 중복 판별과 모바일 결과 확인이 끝나기 전에는 실제 자동 저장을 활성화하지 않는다.

## API와 저장소

- `POST /v1/notification-transactions`: 서명된 `notification:write` 권한의 Android 요청만 허용한다. UUIDv4 이벤트 ID와 동의/기기 버전, 양수 원화 금액, 입금/출금 방향, 상대명 또는 NULL, 기기 수신 시각 및 선택적 실제 거래 시각을 받는다.
- `GET /v1/notification-transactions/:eventId`: 서명된 `notification:read` 권한으로 본인 접수 결과만 조회한다. 수집 중지·동의 철회 뒤에도 유효한 본인 Android 세션으로 이미 저장된 결과를 확인할 수 있다. 세션 만료·철회는 별도로 차단한다.
- 응답에는 이벤트 ID·거래 ID·시각 확인 필요 여부만 포함하고 캐시하지 않는다. 금융 내용은 기존 거래 조회 경로에서 확인한다.
- 런타임 제공자는 기본 `enabled=false`이며 이를 켜는 환경변수나 모바일/BFF 호출 경로도 아직 없다. 합성 시험에서만 명시적으로 활성화한다. 일반 실행에서는 503으로 닫힌다.

## 시각 처리

완전히 해석된 알림 거래 시각이 있으면 이를 우선한다. 없으면 기기 수신 시각을 사용하고 확인 필요로 표시한다. 서버 도착 시각을 거래 시각으로 만들지 않는다. 장부 날짜는 사용자의 거주 시간대 이력을 기준으로 정한다. 수신 시각만 있는데 거주 기준 변경이 있었다면 임의로 날짜를 정하지 않고 확인 오류를 반환한다.

## 검증 현황

- 전체 자동 테스트 2,427건 통과. 별도의 PostgreSQL 통합 검사 447건 통과. 이 중 신규 입력 계약은 29건, 접수 저장소는 경합 포함 10건, 신규 표의 실제 권한/제약 검사는 3건이다. core HTTP 묶음 41건도 통과했다. 숫자를 중복 합산하지 않는다.
- lint(기존 무시된 output/을 로컬 명령에서만 제외), 전체 typecheck, API 빌드, Android export, 웹 빌드 통과. 기존 OneDrive .next 생성물의 ReadOnly/reparse-point 삭제 오류로 웹 빌드가 두 차례 실패했으나, 웹 서버가 없음을 확인하고 해당 생성물만 output/next-build-preserved-20261102로 보존한 뒤 새 빌드가 종료0으로 완료됐다. 제품 설정과 검사 기준은 바꾸지 않았다.
- 독립 리뷰: Critical0 / Important0 / Minor2. 리뷰어가 계약29·HTTP41을 독립 재실행했다. DB447·전체2427은 실행자의 결과를 검토했으며 두 번째로 실행한 것은 아니다.
- Minor 후속1: mock으로 바꾸지 않은 실제 CoreModule 제공자가 항상 비활성 응답을 내는 HTTP 회귀시험 보강. 현재 비활성 제공자 코드는 확인했다.
- Minor 후속2: 알림 전용 거주 이력 SQL에 변경 전 지연 도착·변경 경계·분 단위 구간 내부 변경 시험 추가. 현재 날짜 오류를 재현한 결함은 아니다.
- 실제 원격 Supabase, 실계좌, 실제 금융 알림, 휴대폰 자동 전송 시험은 이번 범위에 없다.
- PC UI 파일은 변경하지 않았다. 이번 단위에 대해 새 PC 화면 Playwright 검사를 수행했다고 주장하지 않는다. 보안 패치의 기존 원격 CI 브라우저 E2E 통과와 구분한다.

## 실제 사용 전 남은 단계

1. 최소 이벤트 ID를 Android에서 안정적으로 만들고, 계정/세션 전환 시 이전 자료가 섞이지 않게 한다.
2. ‘판독만 하고 저장하지 않는다’는 현재 안내·동의 버전을 실제 저장 기능에 맞게 변경한다.
3. 네트워크 응답 유실 시 접수 결과 조회와 수기 보완 충돌을 처리한다. 금융 내용의 장기 자동 재전송 대기열은 만들지 않는다.
4. 여러 앱 알림 중복 후보와 사용자 확인을 연결한다.
5. 30일 휴지통 정리·탈퇴·접수 표식 수명을 함께 구현한다. 현재 FK는 접수 기록이 가리키는 원장의 물리 삭제를 막는다. 영구 보관을 승인한 것이 아니며, 삭제 정책이 완성되기 전 활성화하지 않는다.
6. 개발 DB migration 이력과 최소 권한을 확인한 뒤 별도 적용하고, 합성 알림→저장→PC 조회의 전체 흐름을 검증한다.

현재 추가로 입력받아야 할 API 키나 실제 금융 정보는 없다.

## 검토 판단과 남은 위험

- 승인된 후속 작업은 추가 제품 승인 없이 작은 서버 기반으로 진행했다. 범위가 다르게 해석될 위험은 비활성 상태와 사전 파일 목록으로 제한했다.
- 기존 동의는 판독만 안내하므로 모바일/BFF 연결과 런타임 활성화는 제외했다. 따라서 지금 휴대폰 자동 저장은 사용할 수 없다.
- 이전 시험용 PostgreSQL 실행 파일의 DLL 문제로 OneDrive 밖에 새 폐기용 PostgreSQL17.11을 사용했다. 호스팅 환경 차이는 후속 배포 검증으로 확인해야 한다.
- 물리 삭제·접수 표식 수명은 활성화 전 필수다. RESTRICT FK는 재전송 부활을 막는 현재 보호 장치이지 삭제 기능의 완성이 아니다.
- 고정 Node/pnpm 래퍼와 로컬 임시 output/ 제외를 사용했다. 원래 CI 설정은 유지했고 제품 코드를 빼고 검사하지 않았다. 빌드 생성물 백업은 Git에서 제외했다.
- 독립 리뷰 범위는 a381626 이후 이번 단위 전체다. 기존 장기간 기능 브랜치 전체를 새로 보안 인증한 것은 아니다.
- 실기기 수집·재부팅·백그라운드·권한 해제, 실제 판독 정확도·다른 은행 지원은 아직 인증하지 않았다. 지원 확대 전에 합성·실기기 검사가 필요하다.
- native 이벤트 ID·계정 전환 정리, 응답 유실 결과 확인·수기 보완 경쟁, 교차 앱/갱신 중복은 후속이다. 완료 전에는 중복·오귀속 위험 때문에 활성화하지 않는다.
- 저장 안내·동의 개정, 30일 정리·탈퇴·표식·백업 정책은 후속이다. 미완료 상태의 실제 개인정보 저장을 승인한 것이 아니다.
- 계좌 자동 연결·분류·환불·이체·시작 잔액·안내 묶음은 이번 서버 단위에 포함되지 않는다. 기존 제품 요구에서 삭제하지 않았다.
- 운영 요청 빈도·용량·로그 정책, hosted migration/실제 역할 구성, PC 화면의 새 실사용 검증은 별도로 남는다. 로컬 테스트 통과로 운영 준비 완료를 선언하지 않는다.
