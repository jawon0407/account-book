# 인증 제공자 요청 시간 제한 — R1 이후 상세 설계 검토

- 기준: 2026-09-14, `bb537e5`에서 분기한 `feature/auth-provider-deadline`.
- 상태: **A안·작업당 총 5초 구현 / 전체 verify 937개 테스트·타입·lint·빌드 통과 / 마지막 JSON 보호 보완 독립 재검토 Approved**. 2026-09-15 [2작업 실행 계획](../superpowers/plans/2026-09-15-auth-provider-deadline.md)에 따라 구현했다. 분기 coverage 92.48%는 기존 100% 기준 미달로 남으며 코드 검토 승인으로 면제되지 않는다. 실제 배포 검증·커밋·푸시는 하지 않았다. 아래 대안·파일 후보·보안 알림·CI 수치는 9월 14일 당시 기록이며 새 조회 결과가 아니다.
- 기존 [시간 제한 제안](2026-09-10-auth-deadline-next-work.ko.md)을 실제 R1 분리 구조에 맞춰 검토한 이력이다. 사용자의 "확정해줘" 이후 도구 오류로 지연됐던 승인 기록을 재개 시 반영했다. 아래 대안 비교는 결정 전 근거이며, 현재 기준은 [서면 설계](../superpowers/specs/2026-09-14-auth-provider-deadline-design.md)와 문서 상단의 최신 상태다.

## 1. 완료한 선행 작업과 운영 주의사항

Vitest 패치 `bb537e5`는 `hotfix/vitest-security-20260914`로 푸시했고 로컬/원격 SHA가 일치했다. 전송 전 verify는 878개 테스트·lint·타입·API/웹 빌드 exit 0, audit는 알려진 취약점 0건, pre-push는 714개 blob 검사 통과다. CI는 확인 당시 실행 중이다. 기존 coverage branches 91.86%/기준 100%는 별도 미달 항목이다.

GitHub 기본 브랜치 main에는 critical 4건·moderate 4건이 열려 있다. main의 apps/web/package.json은 Next 16.2.11이고 현재 작업 브랜치는 16.3.3이다. GitHub 공지의 최소 수정 버전은 Next 16.3.3, baseline-browser-mapping 2.11.0, Vitest/mocker 4.1.11이며 현재 lockfile은 이 버전들이다. 8개 알림은 여러 manifest에 중복 보고된 항목을 포함한다. 로컬 audit 0건과 main 경고는 검사 대상이 다르다. 기능/패치 브랜치 푸시는 main 병합이나 배포가 아니므로 경고 해결을 선언하지 않는다. 기본 브랜치 패치 반영은 별도 PR 범위 검토·승인이 필요하다.

## 4. 먼저 결정할 시간 예산

추천은 **공급자 작업 하나에 총 5초**다. 8초 단일 예산은 느린 외부 응답을 더 기다릴 수 있지만 현재 route maxDuration 10 설정 아래 DB 처리 여유가 작다. 작업별 다른 값은 세밀하게 조정할 수 있으나 실측 자료 없이 정책만 복잡해진다. 5초도 측정으로 검증한 최적값은 아니며 hosted p95/timeout 비율을 보고 재검토한다.

여기서 작업은 어댑터의 로그인/갱신/가입/코드 교환 같은 호출 1회다. `setSession → signOut`, `setSession → updateUser`는 두 요청을 합쳐 하나의 예산을 쓴다. 계정·입력 검증 뒤 네트워크 작업을 시작할 때 시간을 측정한다. 사람이 Google/Kakao/Naver 화면에서 로그인하는 시간, 메일 클릭을 기다리는 시간, DB 호출과 전체 BFF 요청 수명은 이 5초와 다르다. 전체 사용자 응답이 항상 5초 이내라는 보장은 아니다.

## 5. 승인 후 고정할 실행 원칙

1. 서버 전용 deadline 객체가 단조 증가 시계 기준의 만료 시각, AbortController, 안전한 실패 상태, 정리 책임을 소유한다. 서로 다른 요청끼리 상태를 공유하지 않는다.
2. 직접 HTTP와 SDK에 작업별 fetch를 연결한다. SDK 팩토리의 주입 인자는 기존 호출 호환성을 검토해 최소한으로 확장하고 공개 AuthProviderPort의 업무 메서드 의미는 유지한다.
3. 만료하면 실제 요청/본문 읽기를 취소한다. Promise.race만으로 기다리기를 멈추고 전송은 계속 두는 구현은 채택하지 않는다. 늦은 완료/거부는 관찰하여 unhandled rejection을 막고 성공 후처리를 진행하지 않는다.
4. SDK 재시도 대기 중에도 전체 작업은 마감되어야 하며 이후 재시도는 실제 네트워크로 나가지 않게 한다. 새로운 앱 자동 재시도는 추가하지 않는다. SDK의 기존 재시도와 그 종료 방식은 별도로 검증한다.
5. 원시 예외·URL·헤더·토큰·비밀번호는 SDK 로그나 공개 응답에 전달하지 않는다. 전송 실패를 SDK에 안전하게 전달하는 방식은 응답 본문 읽기 오류와 함께 검증한다. 단순히 임의의 HTTP 400을 반환하면 기존 오류 매퍼가 잘못된 비밀번호로 분류할 수 있으므로 그렇게 확정하지 않는다.
6. 만료/취소는 `AUTH_PROVIDER_UNAVAILABLE`로 분류한다. 429·계정 열거 방지·PKCE·잘못된 자격 증명의 기존 분류는 보존한다. 타이머/리스너는 성공·실패·취소 모두에서 정리한다.
7. **취소는 롤백이 아니다.** 서버가 이미 가입·비밀번호 변경·토큰 교환을 처리했을 수 있으므로 자동 재전송하지 않는다. 비밀번호 복구 선점·세션 회전 등 상위 서비스의 실패 처리도 회귀 확인한다. 별도 거래 보상/세션 프로토콜 변경이 필요하면 이 작업에 몰래 추가하지 않는다.

## 6. 예상 변경 파일과 규모

중간 규모, 약 12~14파일이 초기 추정이다. 구현 설계 확정 시 테스트 경계에 따라 정확한 목록을 고정한다.

- 제품 4파일: 어댑터, http-client, sdk-client 수정 및 `auth/provider-request-deadline.ts` 신규 후보.
- 테스트 3~5파일: 어댑터 연결 테스트, deadline 단위 테스트, 실제 SDK 전송 테스트, 필요하면 기존 fixture 및 상위 서비스 회귀 테스트 보완.
- 설정 1파일: `apps/web/vitest.config.ts`의 coverage 대상 추가. 기존 임계값 유지.
- 문서 4파일: 승인된 설계/계획과 백엔드 인증 설명·테스트 가이드·진행 현황. 현재 검토 기록은 별도 이력으로 유지한다.

제품 약 150~250줄, 테스트 약 200~350줄 변경이 초기 추정이며, 줄 수 제한을 위해 안전 검사를 생략하지 않는다. 새 함수에는 역할·매개변수·반환·실패·취소 책임을 한국어 주석으로 남긴다. lockfile·DB 스키마·Heroku API·UI·CSS는 기본 범위 밖이다. 서버 전용 변경이므로 FCP 개선을 목표로 하지 않는다.

## 7. 검증·완료 기준

시간 경계 전후, 헤더 지연, 본문 지연, 순차 호출 합산, SDK 재시도 중 만료, 만료 후 추가 전송 차단, 외부 signal 결합, 병렬 격리, 타이머/리스너 정리, 로그/응답의 민감값 부재를 확인한다. 실제 설치 SDK에 통제한 fetch를 주입하며 SDK 전체 mock만으로 끝내지 않는다. 수정 전 실패→최소 구현→통과의 TDD를 기록하고 전체 verify·coverage·독립 리뷰를 수행한다. 실제 IdP/DB/한국망 지연은 별도 운영 검증이다.

**A안과 작업당 총 5초는 확정됐다.** 서면 설계에 대상 작업·취소·오류·검증 기준을 정리했다. 재승인 대상은 A안이나 5초 자체가 아니라 서면에 잘못 옮긴 요구사항 또는 새로 발견한 범위 변경이다. 아직 제품 코드·의존성·DB·UI를 수정하지 않았다.
