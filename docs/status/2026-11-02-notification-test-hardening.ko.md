## 4. 현재 구현 경계

모바일은 설정 화면에서 판독한 결과를 메모리에 표시한다. 서버 접수 API·저장소·접수 테이블은 합성 시험에서 동작하지만 실제 실행의 제공자는 계속 비활성이다. 모바일과 BFF의 전송 경로는 아직 없다.

특히 `CaptureEngine`은 현재 마지막 판독 결과 하나와 건수만 보관한다. 이 표시 값을 주기적으로 서버에 보내면 연속 알림 중 앞선 알림이 빠질 수 있다. 전송 전에 알림별 전달 계약부터 만들어야 한다.

현재 파서는 KB 형식의 제한된 검증 기반이다. 금융 앱 전체·문자·카카오톡 지원이 끝났다는 의미는 아니다. 실계좌 API 연동을 다시 도입하는 작업도 아니다.

## 5. 다음 개발 권장 순서

### 1단계: 모바일 알림별 전달 계약 — 먼저 진행할 단위

- 알림마다 안정적인 접수 UUID를 만들고, 같은 이벤트의 결과 확인에는 동일 ID를 유지한다.
- `last` 화면 값과 전송할 개별 이벤트를 분리한다. 원문 대신 검증된 최소 항목만 일시 전달하고, 용량을 제한한다.
- 계정·세션 세대 변경, 중지, 동의 철회 때 이전 금융 자료를 비운다.
- 무제한 자동 재전송·장기 금융 대기열은 만들지 않는다. 실패·누락은 안내 후 수기로 보완한다.
- 우선 합성 알림만 사용하고 실제 서버 전송은 아직 비활성으로 둔다.

파일 후보: `CaptureEngine.kt`, `NotificationAccessModule.kt`, `apps/mobile/src/collector/android-capture.ts`, 신규 이벤트 전달 모델과 각 Kotlin/TypeScript 테스트. **예상6~8파일, 중간 규모**. 단순 CSS 수정이 아니므로 회귀 테스트가 필요하다.

### 2단계: Android 인증 전송과 BFF 접수 연결

- 신규 모바일 접수 클라이언트가 기존 HTTPS·세션·응답 검증 경계를 재사용한다.
- BFF에 Android 전용 POST/결과 조회 경로를 추가하고, 정확한 내부 권한·경로·본문으로 서명한다.
- 서버 저장이 실제로 시작되기 전에 현재 판독 전용 안내와 동의 버전을 개정하고 재동의를 요구한다.
- 서버 저장 성공 후 응답만 유실되면 같은 접수 ID로 결과를 조회한다. 확인되지 않은 상태를 성공으로 표시하지 않는다.
- 기존 비활성 테스트를 삭제하지 않고, 기본 비활성/명시적 시험 활성화 두 경우를 검증한다.

파일 후보: 신규 `apps/mobile/src/api/native-notification-client.ts`, `native-client.ts`, `session-manager.ts`, `collection-runtime.ts`, 신규 `apps/web/src/app/api/native/notification-transactions/` 라우트2개, `apps/web/src/server/core/operations.ts`, `core-controller.ts`, 동의 계약·문구·새 migration 및 대응 테스트. **여러 계층을 연결하는 중대 규모**이며 별도 사전 파일 목록을 확정한다.

### 3단계: 개발 DB·실기기·PC 끝단 검증

- 개발 DB의 migration 이력과 실제 최소 권한을 먼저 확인한다.
- 합성 알림→모바일→BFF→NestJS→DB→같은 계정 PC 조회를 연결해 검증한다.
- 응답 유실, 연속 알림, 중복 전송, 로그아웃, 기기 교체, 동의/OS 권한 철회를 재현한다.
- PC 확인은 Playwright, 모바일 확인은 USB 실기기에서 수행한다.
- 그다음 교차 앱 중복 판별, 미분류/확인 필요 안내, 수기 보완 충돌을 연결한다.

### 실제 자동 저장 활성화 전 필수 조건

저장 동의 개정,30일 삭제·탈퇴·재접수 방지 표식 수명, 교차 앱 중복 및 수기 보완 충돌, 요청량·로그 최소화, 실제 기기 검증이 남아 있다. 현재 접수 테이블의 RESTRICT 외래키는 물리 삭제를 막으므로 삭제 정책과 함께 보완해야 한다.

첫 연결 단계는 계좌 자동분류·소비 카테고리 규칙 전체 구현이 아니다. 사용자 지정 규칙은 선택 기능이라는 기존 설계도 유지한다.
