- 범위: 코드·진행 기록을 읽고 후속 작업을 제안했다. 제품 코드 변경, 테스트 실행, 외부 전송, 배포는 하지 않았다.

## 1. 현재 작업과 구분

직전 Vercel 리전 설정 이전은 로컬 구현·검증이 끝났지만 아직 미커밋이다. 향후 Vercel 프로젝트의 Root Directory는 `apps/web`, 설정 파일은 `apps/web/vercel.json`이다. Vercel 프로젝트 자체는 아직 생성되지 않았다.

직전 기록의 focused 16/16, 전체 verify 874개 테스트·타입·lint·빌드 통과는 **이전 작업의 결과**이며 이번 검토에서 재실행한 결과가 아니다. 이전 보안 업데이트 SHA의 CI 성공을 미커밋 리전 변경의 CI 성공으로 해석하면 안 된다. 상세 근거는 [리전 이전 기록](../superpowers/plans/2026-09-09-vercel-region-policy.md)에 있다.

후속 제품 수정 전에 리전 변경을 별도 커밋으로 정리하는 편이 좋다. 커밋·푸시와 다음 기능 브랜치 생성은 별도 승인 범위를 확인한다. 기존 `.gitignore` 변경은 이번 작업 소유가 아니므로 일괄 포함하지 않는다.

## 2. 확인한 두 가지 후속 후보

### 후보 1 — 사용하지 않는 DB 연결의 오류 처리

연결 풀은 DB 연결을 매번 새로 만들지 않고 보관했다가 재사용하는 장치다. 쿼리를 실행하지 않는 동안에도 DB 재시작이나 네트워크 단절로 오류가 발생할 수 있다.

- `packages/database/src/client.ts`: Drizzle의 node-postgres 드라이버로 풀을 만든다. 설치된 드라이버 구현도 확인했으며 이 경로에 풀의 `error` 이벤트 수신 처리가 없다.
- `apps/api/src/me/me.module.ts`: 직접 `new Pool(...)`을 호출하지만 풀의 `error` 이벤트 수신 처리가 없다.
- [node-postgres 공식 문서](https://node-postgres.com/apis/pool)는 유휴 연결 오류에 수신 처리가 없으면 처리되지 않은 오류로 프로세스가 종료될 수 있다고 설명한다.

이는 정적 코드와 라이브러리 동작을 대조한 결과다. 실제 운영 장애나 공격을 재현했다는 뜻은 아니다.

이미 있는 보호 장치는 유지한다. API 풀에는 최대 5개 연결, 연결 대기 2초, 유휴 10초 설정이 있다. BFF는 프로세스 안에서 DB 클라이언트를 재사용한다. API replay 저장소는 쿼리 실패를 안전한 오류로 바꾸고, 종료를 한 번만 실행한다. 이번 보완은 이들과 다른 **백그라운드 오류 경로**를 다룬다.

### 후보 2 — 실제 인증 공급자 요청의 시간 제한

`apps/web/src/server/auth/supabase-auth-adapter.ts`에는 SDK 호출과 직접 HTTP 호출이 함께 있다. 두 경로에 애플리케이션이 명시적으로 관리하는 요청 마감 시간·취소 신호가 연결되어 있지 않다. 플랫폼 제한이 전혀 없거나 모든 요청이 무한 대기한다는 뜻은 아니다.

별도 작업에서 SDK 내부 재시도, 응답 본문 읽기, 기존 호출 취소, 함수 실행 예산을 함께 검토한다. 이미 제한이 있는 위임 API 호출까지 무조건 수정하지 않는다. 로그인·토큰 갱신 같은 변경 요청에 자동 재시도를 새로 추가하지 않는다.

## 3. 대안 비교와 추천

| 안 | 범위 | 장점 | 단점 |
| --- | --- | --- | --- |
| A — 추천 | 현재 DB 생성 지점 두 곳에 오류 수신·안전한 진단을 보강 | 작은 변경으로 양쪽 누락을 해결하고 기존 구조·종료 책임을 유지 | 두 곳의 진단 규칙을 일치시켜 관리해야 함 |
| B | 공용 풀 생성 모듈을 만들어 BFF와 API를 전환 | 향후 풀 정책의 중복을 줄일 수 있음 | 서로 다른 연결·종료 정책이 결합되고 공개 인터페이스 변경이 늘어남 |
| C | DB 오류·풀 예산·인증 시간 제한을 한 번에 수정 | 관련 운영 안정성을 함께 다룸 | 실패 원인·테스트 범위가 섞이고 검토·되돌리기 단위가 커짐 |

**A를 먼저 완료하고 후보 2를 별도 승인 작업으로 진행하는 것을 추천한다.** 현재 두 생성 지점만으로 공용 추상화를 새로 만드는 필요성은 크지 않다.

오류 원문, stack, DB URL, SQL, client 객체는 로그에 넣지 않는다. 안전한 고정 이벤트 코드와 발생 위치만 남기는 제한된 진단을 설계한다. 반복 장애의 로그 폭주도 제한한다. 전역 `uncaughtException`으로 오류를 덮거나, DB 장애를 인증 성공으로 처리하거나, 쿼리를 자동 재시도하지 않는다. 정확한 진단 빈도는 구현 전 상세 계획에 고정한다.

## 4. A안 파일 지도와 예상 규모

저장소 기준 상대 경로다. 줄 수는 검토 시점이며 추가량은 추정이다.

| 파일 | 현재 크기 / 작업 | 역할 |
| --- | --- | --- |
| `packages/database/src/client.ts` | 14줄 / 수정 | BFF에서 사용하는 풀의 오류 수신 |
| `apps/api/src/me/me.module.ts` | 70줄 / 수정 | API 풀의 오류 수신, 기존 설정 유지 |
| `packages/database/src/client.test.ts` | 신규 | 유휴 오류·비밀값 비노출·정상 종료 확인 |
| `apps/api/src/me/me.controller.test.ts` | 210줄 / 수정 | DI로 생성한 풀의 오류 처리와 기존 종료 계약 확인 |
| `docs/architecture/backend-authentication.ko.md` | 부분 수정 | 장애 처리 흐름을 초급 개발자 관점으로 설명 |

구현 대상은 **제품 코드 2개 + 테스트 2개 + 결과 문서 3개 = 7개 파일**로 예상한다. 별도 상세 계획 문서 1개도 작성한다. 현재 사전 검토 문서는 이 구현 파일 수에 포함하지 않는다. 예상 변경량은 제품 코드 약 20~60줄, 테스트 약 80~160줄이며 주석·진단 설계에 따라 달라진다. 의존성·lockfile·DB 스키마·화면 CSS 변경은 없다.

읽기 전용 회귀 확인 대상은 `apps/web/src/server/container.ts`와 해당 테스트, `apps/api/src/persistence/postgres-replay-store.ts`와 해당 테스트다. 기존 공유·실패 차단·종료 계약을 변경해야 한다면 범위를 다시 설명한다.

## 5. 승인 후 진행과 완료 조건

1. 직전 리전 변경의 Git 정리 범위를 확인하고 작업 단위를 분리한다.
2. A안의 진단 규칙과 테스트 방법을 상세 계획에 고정한다.
3. 실제 풀 또는 이벤트 동작을 재현하는 테스트로 누락을 먼저 확인한다(RED). 단순히 메서드 호출 여부만 검사하지 않는다.
4. 최소 수정과 한국어 함수·매개변수 주석을 추가한다.
5. 오류 이벤트가 처리되고 비밀값이 출력되지 않는지 확인한다(GREEN). 반복 오류의 진단 제한도 검사한다.
6. DB 공유, 쿼리 실패 차단, 종료 1회 계약을 회귀 검사한 뒤 전체 verify로 타입·lint·테스트·빌드를 확인한다.
7. 결과와 미실행 검사를 문서화한다. 실제 DB 재시작·네트워크 단절 검증은 별도 폐기 가능한 환경이 있을 때 수행한다.

단순 CSS 변경이 아니라 서버 오류 처리 변경이므로 테스트를 생략하지 않는다. 새로운 의존성, 풀 연결 수 변경, DB migration, 보안 완화, 전역 예외 처리, 운영 DB 접근이 필요하면 중단하고 재승인받는다.

## 6. 기대 효과와 후속 순서

- 보안: 오류 출력으로 비밀값이 새지 않도록 하고 기존 인증 실패 차단을 유지한다. 인증 우회 취약점을 재현·해결했다는 주장은 하지 않는다.
- 확장성: BFF/API가 증가해도 같은 원칙을 적용할 수 있으나 전체 연결 수 예산은 별도 설계다.
- 유지보수: 현재 구조를 보존하면서 실패 경로를 테스트로 남긴다.
- 응답 시간: 프로세스 오류로 인한 장애 위험을 줄이는 목적이다. 느린 쿼리 자체를 빠르게 만들지는 않는다.
- FCP: 서버의 풀 오류 수신 변경이므로 직접적인 화면 첫 표시 속도 개선은 기대하지 않는다.

추천 순서는 리전 작업 정리 → DB 유휴 오류 대응 → 실제 인증 요청 시간 제한 → 금융 기능 착수 전 DB 권한·연결 예산·남용 방어 잔여 사항 확인 → 거래 저장·조회와 웹 화면 → 별도 모바일 앱·같은 계정 데이터 연동이다. 운영 계정 생성 전에도 로컬 구현은 가능하지만 실제 배포·인증 공급자 연동·실제 금융 데이터 베타 승인은 별도 완료 조건이다.
