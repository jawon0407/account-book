# Android 우선 개발 — 로그인 자격 증명 갱신 보완

작성: 2026-10-16, 한국시간. 작업 트리 `ledger-public-contracts`, 브랜치 `feature/bank-state-transitions`, 기준 HEAD `8af7a0d`.

## 이번에 달라진 점

Android 로그인 연결에 앞서 **앱의 로그인 자격 증명을 갱신 때마다 교체하는 서버 기능**을 구현했다. 웹의 기존 쿠키 로그인 방식은 유지한다. Android HTTP 로그인 경로나 앱 화면·APK·알림 수집기를 완성한 것은 아니다. iOS는 Android 승인 범위 구현·실기기 검증 이후 진행한다.

앱 자격 증명은 ‘로그인이 유지되는 동안 사용하는 임시 출입증’이다. 제공자의 access/refresh token과 다르다. 제공자 토큰은 서버 안에서 암호화해 저장하고, 앱 자격 증명은 원문 대신 해시만 DB에 저장한다.

## 갱신 흐름

1. Android가 가진 현재 자격 증명을 서버에서 확인한다. 웹 세션은 Android 경로에서 사용할 수 없다.
2. 서버 내부에서 제공자 토큰을 갱신하고 새로운 무작위 앱 자격 증명을 만든다.
3. DB에서 **기존 해시·설치 ID·채널·버전·수명·폐기 상태가 모두 맞을 때만**, 새 해시와 제공자 토큰 암호문을 한 번에 교체한다.
4. 저장 성공 후 새 자격 증명을 반환한다. 이전 값은 조회·갱신·현재 로그아웃에 사용할 수 없다.
5. 두 요청이 겹치면 하나만 성공한다. 실패한 요청은 저장되지 않은 출입증을 받아 사용할 수 없다.

**앱 구현에 이어갈 UX 계약:** 갱신은 한 번에 하나만 실행하고 새 자격 증명을 안전한 기기 저장소에 교체한다. 서버 저장 후 응답을 잃으면 다시 로그인한다. 이전 자격 증명 재사용 유예를 두거나 복구 목적으로 원문을 서버에 저장하지 않는다. 이 경우 금융 거래를 자동으로 재전송한다는 뜻은 아니다.

독립 리뷰의 후속 주의점: 앱은 갱신과 로그아웃도 직렬화해야 한다. 이전 자격 증명으로 폐기를 요청해 `false`를 받은 것을 서버 로그아웃 성공으로 표시하면 안 된다. 현재 앱/HTTP 호출자는 아직 없어 이번 코드 결함은 아니며 다음 계약에 반영한다.

30일 절대 만료를 늘리거나 설치 ID를 바꾸지 않는다. 기존 7일 유휴 만료, 계정 전체 로그아웃, 비밀번호 복구 시 전체 세션 폐기는 유지한다. 설치 UUID는 하드웨어 증명이나 자동 수집 권한이 아니다.

## 파일별 역할과 규모

제품 3파일 + 테스트 3파일 + 문서 5파일의 중간 규모다. 새 의존성·DB 열·운영 DB 변경은 없다. 기존 브랜치 전체 변경 규모와 구별한다.

| 파일 | 역할 |
| --- | --- |
| `apps/web/src/server/persistence/auth-repository.ts` | 저장소에 전달할 이전/새 해시와 설치 ID 계약 |
| `apps/web/src/server/persistence/postgres-auth-repository.ts` | 채널·기기·이전 해시 검사 및 원자적 SQL UPDATE |
| `apps/web/src/server/session/session-service.ts` | Android 자격 증명 생성, 저장 성공/경합 처리 |
| 위 서비스·저장소의 `.test.ts` 2개 | 웹 호환, Android 교체·경합·실패·비밀 비노출 |
| `tests/database/native-session-channel.test.ts` | 최소권한 역할, 독립 DB 연결 2개 경쟁, 충돌 롤백·만료·폐기 |

주요 입력 `selectorRotation`은 이전 해시, 새 해시, 설치 UUID다. 선택 입력이지만 Android 행을 갱신할 때는 필수이며 생략하면 웹 행만 갱신한다. `SessionService.refresh(selector, now)`는 현재 자격 증명과 조회 시각을 받고 Android 성공 시 새 selector를 반환한다. 새 값은 외부 응답에서 비밀로 취급해야 하며 로그에 남기면 안 된다.

이번 테스트는 합성 자료와 loopback 임시 DB만 사용한다. 운영 Supabase·실제 소셜/금융 제공자·실기기 검증으로 확대하지 않는다. DB 충돌은 PostgreSQL unique 위반(23505)을 확인하고 기존 해시·암호문·버전이 모두 그대로인지 확인했다.

1,766개는 legacy/security 208 + contracts 96 + database 단위 19 + API 279 + web 1,078 + preflight 86이다. 최종 DB 경쟁 테스트 보강 후 린트·DB 타입 검사도 다시 통과했다. PC 개발 서버가 자동 변경한 `next-env.d.ts`의 경로 2줄은 테스트 전 production 경로로 되돌렸다.

임시 DB 재시작 시도는 이미 동일 경로의 서버가 실행 중이어서 실패했다. 권한이 제한된 상태의 프로세스 조회 결과만 믿지 않고 승인된 진단으로 실행 경로·data directory·loopback 포트를 확인한 뒤 기존 폐기용 서버를 사용했다. 제품 DB 실패와 구별한다.

`autoplan` 설치본의 필수 하위 참조 누락으로 전체 자동 파이프라인 완료를 주장하지 않는다. 설계 대조·TDD·직접 보안 검토·독립 리뷰로 보완한다. `qa-only`의 브라우저 검증은 이 프로젝트의 Playwright 회귀를 사용하며 Android 실기기 시험은 아직 수행하지 않았다.

## 남은 작업과 적용 경계

1. Android 전용 로그인·세션 확인·갱신·로그아웃 HTTP API, 크기/빈도 제한과 안전한 오류 계약.
2. 신뢰된 채널의 NestJS 위임과 PC 신규 작성 제한, 수집 기기 1대·교체·늦은 쓰기 차단.
3. `apps/mobile` 기본 앱, 안전한 자격 보관, 로그인·계좌/카테고리·수기·조회·PC 동기화.
4. 동의·알림 접근·금융 알림 최소 정보 판독·미분류 기록·확인 목록을 실기기까지 연결.

기존 추가형 세션 채널 migration은 BFF 배포 전에 필요하다. 이번 회전 단위는 새 migration을 추가하지 않았다. 실제 DB 적용·커밋/푸시·원격 CI·병합·배포는 수행하지 않았다. 기존 은행/원장 미커밋 작업은 보존했다.
