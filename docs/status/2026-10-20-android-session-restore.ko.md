# Android 로그인 유지·안전한 세션 복원

## 작업 계획 — 구현 전 기록

요청: 앱을 완전히 종료해도 다시 로그인할 필요가 없게 하되, 저장된 토큰만으로 장부를 열지 않는다. 기존 이메일 인증 흐름의 한정된 변경이다. 사용자 요청에 따라 계획과 변경 파일을 먼저 공유하고, 기존의 반복 승인 생략 지시에 따라 시험→구현→검증을 진행한다.

1. 저장 책임을 `session-persistence.ts`로 분리한다. 같은 서버·설치 ID의 엄격한 형식만 복원 후보로 받는다. 비밀번호·거래·원문 공급자 JWT는 저장하지 않는다.
2. `SessionManager.restore()`에서 서버 검증 후에만 ready 상태를 연다. 네트워크/서버 불가에는 unavailable로 가리고 재연결한다. 만료·철회·사용자 불일치는 정리한다. 갱신 결과 불명은 재전송하지 않고 재로그인한다.
3. 로그아웃 표시(tombstone), 늦은 응답, 복원/로그아웃 경합과 회전 저장 실패를 시험한다. OS 쓰기·삭제와 서버 폐기가 모두 실패한 로그아웃은 완료가 아니다. 앱 화면을 잠그고 정리를 다시 요구한다. 이 상태에서 앱을 강제 종료했을 때까지 완료를 보증하지 않는다.
4. 연결 실패 화면에 로컬 로그아웃 경로를 제공한다. 기존 보안 저장소·제한된 서버 세션 수명·계정 세대 경계는 유지한다.
5. 모바일/전체 자동 시험, 타입·린트, PC Playwright 및 독립 범위 리뷰를 수행한다. 실기기는 보안 설정을 다시 해제하지 않고 후속 게이트로 구분한다.

## 보안 경계

- 저장 토큰은 인증의 증거가 아닌 서버 확인에 쓰는 비밀값이다. 공개 상태·로그·Notion에는 포함하지 않는다.
- 서버 주소가 바뀐 저장 토큰을 새 서버에 보내지 않는다. 설치 ID가 없어졌거나 다르면 재로그인한다.
- 로그아웃 중 응답은 화면을 다시 열 수 없다. 회전 저장 실패 후 새 토큰은 폐기를 시도한다.
- 오프라인으로도 과거 장부를 보여 주는 캐시를 만들지 않는다. 자동 금융 재전송 대기열도 없다.
- 로컬 삭제와 원격 폐기는 별개다. 실패한 원격 폐기는 현재 프로세스 메모리에서 재시도하며 영구 폐기 큐를 이번에 추가하지 않는다.

## 구현 흐름 — 처음 읽는 개발자를 위한 설명

1. 앱이 시작되면 장부 대신 확인 중 화면을 표시한다. 저장소에서 설치 ID와 이전 세션 후보를 읽는다. 비밀번호를 저장하거나 다시 입력받아 자동 로그인하는 방식이 아니다.
2. `SessionPersistence`는 저장 형식·서버 주소·설치 ID가 맞는지 확인한다. 다른 서버나 설치의 자격 증명은 서버에 보내지 않는다. 설치 ID가 사라졌다면 이전 세션을 재사용하지 않는다.
3. `SessionManager`는 후보를 서버에 확인한다. 같은 사용자와 기기가 확인돼야 장부 화면을 연다. 필요 시 갱신을 한 번 직렬 처리하고 새 값을 안전 저장소에 저장한다. 갱신 응답을 잃으면 이전 토큰으로 반복 갱신하지 않고 재로그인한다.
4. 통신할 수 없으면 저장 후보는 유지하지만 장부는 가린다. 사용자는 재연결하거나 이 기기에서 로그아웃할 수 있다. 만료·철회·신원 불일치는 후보를 정리한다. 기존 서버 수명인 유휴 7일·절대 30일을 연장하지 않는다.
5. 로그아웃은 메모리 자격 증명을 먼저 끊고, 비밀 없는 로그아웃 표시를 저장한 뒤 삭제한다. 서버 폐기는 별도다. 실패한 정리를 성공으로 표시하지 않는다. 늦게 도착한 로그인·갱신 응답도 계정 세대와 검증 순서를 확인하므로 장부를 다시 열지 못한다.

## 발견한 문제와 보완

- 기존 재실행 동작은 저장된 세션을 검증·복원하지 않았다. 새 복원 시험에서 실패를 확인한 뒤 서버 검증 경로를 구현했다.
- 진행 중인 갱신 응답이 foreground 재검증보다 먼저 `ready`를 공개할 수 있었다. 저장과 화면 공개의 책임을 나눠 검증 잠금을 유지하도록 수정하고 경합 시험으로 확인했다.
- 독립 범위 리뷰에서 Important 1건: 시작 시 보안 저장소 읽기에 실패하면 설치 ID가 준비되지 않아 정리 후에도 로그인할 수 없었다. 설치 ID/세션 읽기 실패 두 시험을 먼저 실패시킨 뒤, 정리가 확인된 경우에만 설치 ID를 준비하도록 보완했다. 독립 재리뷰나 전체 PR 승인으로 표시하지 않는다.
- OS 쓰기·삭제와 서버 폐기가 모두 실패한 상태는 기술적으로 완료된 로그아웃이 아니다. 사용자가 앱을 강제 종료하기 전까지 정리 재시도를 요구하며, 이 극단 조건의 영구 로그아웃 보장을 주장하지 않는다.

10/20 HTTPS 통합 시험의 저장소는 메모리 대역이다. 이를 실제 Android SecureStore·재부팅 시험으로 확대 해석하지 않는다. **후속 10/21에는 실제 Android 16/Expo SecureStore로 앱 프로세스 재실행 복원·API 연결 실패 시 장부 숨김/재연결·로그아웃 후 재시작을 검증했다.** [실기기 결과](2026-10-20-android-session-device-test.ko.md)에 화면·서버 근거와 PC 재확인을 구분해 기록했다. 휴대폰 OS 재부팅은 아직이며 보안 설정을 임의 해제하지 않았다.

중간 실패도 보존한다. 전체 시험 첫 실행 중 새 리뷰 회귀 시험 2개가 RED 상태로 포함되어 실패했으며 수정 후 전체 2,164개를 다시 통과했다. 최초 HTTPS 도구의 Node fetch는 브라우저용 요청 메타데이터 때문에 CSRF 차단됐고, 서버 보호를 완화하지 않은 채 네이티브 비브라우저 요청에 맞는 HTTPS 시험 전송으로 교체했다. PC 첫 시험의 메뉴 이름 공백 불일치는 실제 DOM을 확인해 시험 선택자만 수정했다. Windows sandbox의 시험 실행 권한 문제는 허용된 재실행으로 구분했다.

근거 파일은 Git 제외 `output/android-device-2026-10-20/session-restore-project-tests-final.log`, `session-restore-android-export.log`, `session-restore-live.ts`와 `output/playwright/session-restore-pc-20261020.png`다. 자격 증명·인증서 비밀키·실제 금융 원문은 문서/Notion에 싣지 않는다.

## Supabase 소셜 준비 상태

- 읽기 확인 시 프로젝트 상태는 `ACTIVE_HEALTHY`, Google/Kakao 활성값은 모두 false였다. 로컬 BFF의 공급자 허용 목록도 미설정이다.
- Site URL·Redirect URLs의 실제 저장값과 Naver custom 등록 상태는 이번 공개 Auth 설정 응답으로 검증할 수 없었다. 확인하지 않은 값을 정상으로 표시하지 않는다.
- Google/Kakao는 Supabase 기본 공급자, Naver는 `custom:naver` 준비 경로다. Naver의 사용자 정보 매핑 호환성과 실로그인은 아직이며 NestJS Passport 구현 완료 상태가 아니다.
- 사용자 작업: Supabase 공급자 화면과 각 개발자 콘솔에 Client ID/Secret·정확한 callback을 설정한다. 키를 채팅으로 보내지 않는다. 자세한 순서는 [소셜 인증 준비 안내](../guides/social-auth-readiness.ko.md)에 있다.
- 운영 설정은 변경하지 않았다. 준비 완료 후 앱 공급자 허용 목록과 실제 웹 인증을 확인한다. Android 소셜은 시스템 브라우저·검증된 복귀·일회성 교환 경로를 추가해야 한다.
