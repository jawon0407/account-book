# 다음 개발 검토: 실제 Supabase 인증 요청 시간 제한

> 선행 구조 작업: 사용자 승인으로 [R1 역할별 분리](2026-09-10-auth-role-split-review.ko.md)를 먼저 수행한다. 분리 후 시간 제한의 파일 지도와 변경량은 다시 검토한다. 아래 A안/5초 예산은 아직 승인되지 않았으며 시간 제한 코드는 구현하지 않았다. 이 문서의 625줄/465줄·private request() 설명은 분리 전 조사 시점의 기록이다.

- 상태: **설계 제안 / 구현 승인 대기**. 새 제품 코드는 수정하지 않았다.
- 날짜: 2026-09-10
- 선행 작업: Vercel 리전 설정 이전, BFF/API DB 유휴 오류 경계 구현·리뷰 완료.
- 이번 요청 범위: 완료 작업의 로컬 커밋 및 다음 개발 계획. 푸시·PR·병합·배포 제외.

## 1. 현재 근거와 작업 규모

기존 인증 흐름을 보완하는 작업이지만, DB 오류 수신보다 큰 **중간 규모**다. `supabase-auth-adapter.ts`는 현재 625줄, 해당 테스트는 465줄이다. 파일 전체를 재작성하지 않고 HTTP 실행과 SDK 생성 경계를 변경한다.

직접 HTTP 요청(가입·복구·PKCE 교환)은 어댑터의 `request()`에서 fetch 후 JSON을 읽는다. SDK 요청(로그인·갱신·세션 설정·로그아웃·비밀번호 변경)은 별도로 생성한 SDK 클라이언트를 사용한다. 두 경로에 명시적인 애플리케이션 시간 예산이 없다. OAuth 시작 URL 조립은 네트워크 요청이 아니므로 타이머 대상이 아니다.

설치된 `@supabase/supabase-js`와 `auth-js` 2.110.7 소스를 확인했다. auth-js의 `_refreshAccessToken()`에는 재시도가 있으며 `_handleRequest()`의 fetch 예외 경로는 `console.error(e)` 후 재시도 가능 오류로 변환한다. 따라서 원시 fetch 예외를 그대로 SDK로 전달하거나 호출마다 시간 제한을 새로 시작하면, 원문 로그나 총 대기 시간 증가가 생길 수 있다. 실제 비밀 유출/운영 장애를 재현한 결과는 아니다.

SDK의 `global.fetch` 주입은 [공식 초기화 문서](https://supabase.com/docs/reference/javascript/initializing)와 설치 소스에서 지원을 확인했다. 다음 구현에서는 실제 설치 SDK를 사용한 테스트로 연결 여부와 재시도 동작까지 검증해야 한다.

## 2. 대안

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A — 추천 | SDK 유지, 직접 HTTP와 SDK에 작업별 공통 deadline/전송 경계 적용 | 기존 인증 동작을 유지하면서 양쪽 경로를 보호하고 로직 중복을 줄임 | SDK 재시도·JSON 읽기·에러 출력과의 상호작용 테스트가 필요 |
| B | SDK 인증 요청까지 직접 REST로 전환 | 전송·재시도·오류 처리의 소유권이 명확 | setSession·갱신·로그아웃 등 SDK 의미를 재구현하고 유지해야 하므로 범위·회귀 위험 증가 |
| C | 직접 HTTP 경로만 먼저 제한 | 변경이 작고 빠르게 일부 경로 보호 | 로그인·갱신 등 SDK 경로는 남으므로 전체 문제 해결로 볼 수 없음 |

A안을 추천한다. 단, SDK 내부 수정·패키지 업그레이드·공개 인증 인터페이스의 광범위 변경이 필요하다면 구현을 넓히지 않고 별도 승인받는다.

## 3. 제안하는 동작

1. **공급자 작업 1회에 총 5초 예산**을 제안한다. 로그아웃의 setSession→signOut, 비밀번호 변경의 setSession→updateUser는 각각 하나의 예산을 공유한다. HTTP 요청마다 5초를 새로 주지 않는다.
2. 헤더 도착뿐 아니라 응답 본문 읽기까지 예산에 포함한다. AbortController로 실제 전송/본문 읽기를 취소한다. Promise.race만으로 응답 대기를 끝내고 네트워크를 방치하지 않는다.
3. SDK 경로도 같은 예산을 사용한다. 만료 뒤 추가 네트워크 호출을 차단하고, SDK 재시도 대기 때문에 앱 반환이 계속 지연되지 않게 한다. 앱 차원의 자동 재시도는 추가하지 않는다.
4. 원시 오류·URL·헤더·토큰·비밀번호는 로그/공개 오류로 보내지 않는다. SDK에 도달하는 전송 실패도 안전하게 정규화한다. 전역 console 교체나 node_modules 직접 패치는 하지 않는다.
5. 시간 초과/취소는 기존 고정 `AUTH_PROVIDER_UNAVAILABLE` 경계로 처리한다. 429·잘못된 자격 증명·PKCE 오류의 기존 매핑과 계정 존재 여부를 숨기는 정책은 유지한다.
6. 정상 종료와 오류 종료 모두 타이머/리스너를 정리하고 병렬 작업끼리 취소 상태가 섞이지 않게 한다. 전달받은 fetch signal이 있으면 보존·결합한다. 브라우저 연결 종료를 모든 use-case까지 전파하는 전역 변경은 제외한다.

5초는 초기 설계값이며 운영 측정 결과로 검토할 수 있다. 현재 route의 `maxDuration=10`은 앱의 설정일 뿐 전체 BFF가 항상 10초 내 끝난다는 증명은 아니다. DB 읽기·저장과 여러 공급자 작업의 합은 별도다. 이 작업은 이벤트 루프 정체까지 막는 실시간 보장도 아니다.

**취소는 롤백이 아니다.** 응답을 받기 전에 공급자에서 가입·갱신·비밀번호 변경을 처리했을 가능성이 있다. 시간 초과를 근거로 변경 요청을 자동 재전송하지 않으며, 후속 동작이 성공으로 진행하지 않는지 검사한다.

## 5. 진행 단계와 완료 조건

1. 설계 승인 후 별도 `feature/auth-provider-deadline` 브랜치를 만들고 정확한 시간 예산·SDK 오류 처리 방식을 실행 계획에 고정한다.
2. 직접 HTTP 및 실제 SDK가 사용하는 fetch를 통제한 테스트로 정상/지연/실패를 재현한다. 실제 자격 증명이나 외부 서비스는 쓰지 않는다.
3. RED 후 최소 구현, GREEN 순서로 진행한다. 핵심은 헤더 지연, 본문 지연, 순차 호출 합산, SDK 재시도 중 마감, 마감 이후 추가 전송 없음, 병렬 격리, 타이머 정리, 비밀값 없는 출력, 성공 결과/오류 매핑 보존이다. 경계 시각 전후 테스트는 fake timer를 사용해 오래 기다리지 않는다.
4. SDK를 mock한 테스트만으로 완료하지 않는다. 설치 SDK에 통제 fetch를 연결한 검증이 필요하다. 여기에 fail-closed/계정 열거 방지 회귀 검사를 합친다.
5. focused 검사 → 전체 `pnpm verify` → 독립 리뷰 → 한국어 개발/검증 문서 갱신. 신규 사례 수는 약 12~20개 예상이며 개수보다 위 실패 경로 검증을 완료 조건으로 삼는다.

실제 Supabase 프로젝트 없이 로컬 구현·검증은 가능하다. 실환경 지연·한국망 p95·실제 Google/Kakao/Naver 인증·배포 후 타임아웃 비율은 나중에 별도로 측정한다. FCP 개선 작업은 아니며 느린 외부 인증의 대기 상한과 실패 응답 예측 가능성을 개선하는 작업이다.
