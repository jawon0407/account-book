# 개인 알림 가계부 클라우드 작업 인수인계

최초 작성: 2026-10-07. 최신화: 2026-10-13. 제품 방향은 개인 휴대폰 금융 알림 기반 가계부이며, 선택형 자동 분류 규칙을 포함한다. **새 기능은 설계 단계다. 문서 작성·업로드를 구현·DB 적용·출시 완료로 읽지 않는다.**

3. [Notion 엣지케이스 점검 현황](https://app.notion.com/p/3f5323168ba6816e9578c5151182018e), [10/7 개발일지](https://app.notion.com/p/3f1323168ba681ab9ae6c69129a8d69a).

최신 요구사항은 실계좌 API 대신 개인 알림·수기 기록을 우선한다. 예전 은행 후속 A5/A6, 공동 장부·라온·AI 분석은 보존/후속 범위다. 클라우드에서 이 순서를 다시 은행 API 우선으로 되돌리지 않는다.

## 2. Git 위치와 원격 전송 상태 구분

- 저장소: [jawon0407/account-book](https://github.com/jawon0407/account-book).
- 작업 브랜치: `feature/bank-state-transitions`, 로컬 경로는 저장소의 `.worktrees/ledger-public-contracts`.
- 10/13 문서 작업 전 HEAD: `264a7f6dff61622f52fadcc45feaaa69901313ca`. 코드 비교는 이 기능 체크아웃을 기준으로 했다.
- 이번 범위는 통합 문서 최신화와 Notion 기록이다. 원격 push·PR 수정·병합은 포함하지 않는다. 로컬 새 문서는 별도 전송 전까지 클라우드 clone에 나타나지 않는다.
- 10/7 당시 이력: 코드 기준 `00ff1c15f38afbf150727e43a2848a41009b03a0`, 원격 main 확인값 `b7ecd830c3aefd9b225b100b1087d78d39e2ddc1`, [PR #22](https://github.com/jawon0407/account-book/pull/22)는 당시 OPEN/base main이었다. 이를 10/13 원격 HEAD·PR·CI 재확인 결과로 읽지 않는다.

클라우드 작업 환경에서 저장소를 연결한 뒤 위 기능 브랜치를 선택한다. 기본 `main`만 열면 이 문서와 후속 코드가 없을 수 있다. Git을 직접 사용할 수 있다면 새 폴더에서 다음처럼 가져온다.

```sh
git clone --branch feature/bank-state-transitions --single-branch https://github.com/jawon0407/account-book.git
cd account-book
git status --short --branch
git log -1 --oneline
```

브랜치와 최신 문서의 원격 전송 여부를 먼저 확인한다. 위 clone은 원격에 올라간 내용만 가져온다. 이미 작업 중인 폴더에서 강제로 checkout/reset하여 변경을 버리지 않는다. 이 명령은 저장소 확보용이며 서버 실행·DB 연결·모바일 빌드를 완료하지 않는다.

## 3. 현재 구현과 새 목표의 차이

아래 코드 상태는 문서 작업 전 기준 SHA와 로컬 읽기 확인에 근거한다. 아래 표의 '재사용'은 이번 문서 작업에서 재시험했다는 뜻이 아니다.

| 영역 | 재사용할 현재 코드 | 필요한 후속 |
| --- | --- | --- |
| 웹 | 프로필·계좌·분류·일반 거래 조회/입력/수정/삭제 | 편집 중심 전환, 다중 필터, 시각/미분류 근거, 30일 복구 |
| 계약/API | 사용자 소유 검증, 일반 거래 생성·수정, 재시도 키·버전 충돌 | 시간·출처·다중 조회, 모바일 인증, 수집/분류 규칙 경계 |
| 거래 데이터 | 날짜 `occurred_on`, 필수 수입/지출 카테고리 | 시각 정밀도·미분류·수집 연결·구매/환불 관계·변경 이력 |
| 모바일 | React Native/Expo 방향 문서 | `apps/mobile`과 Android 네이티브 수집 신규 |
| 분류 자동화 | 이번에 합의한 제품 요구사항 | 조건 저장·실행·충돌 처리·미분류 안내 모두 미구현 |

현재 원장 이름은 `user.users`, `user.roles`, `user.role_history`, `finance.accounts`, `finance.transaction_categories`, `finance.transaction_history`, `finance.account_transfers`, `finance.request_deduplication`이다.

10/7 당시 읽기 전용 개발 DB 점검에서는 이 8개 테이블의 RLS/FORCE RLS와 기존 역할 접근 검사 19개 통과를 기록했다. 10/13에는 DB에 접속하거나 이 검사를 다시 실행하지 않았다. 새 모바일/알림 기능의 보안 보증도 아니다. 당시 `app_bank` 테이블은 실제 개발 DB에서 확인되지 않았다. SQL 파일 존재와 실제 적용을 구별한다.

기존 거래 API의 BFF 위임 인증은 모바일 인증 구현이 아니다. 서버 서명키를 앱에 넣거나 guard를 끄지 않는다. 현재 저장소는 보관 계좌의 일반 생성을 거부하지만 승인된 알림 정책은 유효한 보관 계좌의 수집을 유지한다. 자동 수집 경로의 권한·검증을 별도 설계해야 한다.

## 4. 로컬에만 남아 있는 작업

기존 개발 작업 트리에는 A5용 API/Web 가상 런타임, E2E 설정·은행 테스트, 은행 통합 문서의 미커밋 변경이 있다. **이번에는 그 작업을 커밋하지 않는다. 클라우드 clone에 따라오지 않는다.** 후속 은행 테스트를 재개할 경우 별도 인계가 필요하다.

대표 경로: `apps/api/src/bank-connections/testing`, `apps/web/src/server/bank-connections/e2e-runtime*`, `tests/e2e/bank`, `tests/database/support/bank-e2e-database.ts`, 은행 관련 모듈/컨테이너/E2E 설정 변경. 루트 checkout의 무관한 진입점·디자인 스킬 변경도 건드리지 않는다. 이러한 과거 작업의 보존은 현재 설계 문서 작성의 장애물이 아니다.

사용자 PC의 `.env`, 인증서, DB 연결 파일, 개인 캡처는 GitHub에 올리지 않는다. 클라우드에서 로컬 localhost 서버나 Windows 비공개 설정을 사용할 수 있다고 가정하지 않는다. 필요한 테스트 값은 승인된 클라우드 secret 경로와 폐기용 DB로 별도 준비한다. 실제 Android 기기의 알림 권한/백그라운드 검증은 실기기 또는 적절한 테스트 환경이 필요하다.

## 5. 바꾸면 안 되는 최신 결정

- 자동 분류 규칙 생성·활성화는 선택 사항. 규칙 없이도 앱의 기본 기록·조회 가능.
- 목적만 미분류인 거래는 입출금 합계에 포함하고 미분류 안내. 계좌·금액 불명확/중복 후보는 별도 확인대기.
- 첫 분류가 자동 규칙 생성 동의는 아님. 개인은 이전 분류를 제시해 매번 확인하는 흐름이 기본.
- 업체·기관의 자동 분류도 사용자별 명시적 선택. 계좌·방향·대상에 선택적 요일/시간/금액 조건.
- 시각은 사용자 확인 → 본문 거래 시각 → 같은 거래로 확인한 최초 기기 수신 시각(추정). 추정 기록도 합계 포함하되 시간 조건 규칙의 대체 허용은 기본 꺼짐·규칙별 선택. 서버 도착 시각 사용 금지.
- 처음 선택한 거주 시간대 고정. 여행/기기 시간대 변경으로 기준을 바꾸지 않음. 주는 월~일, 직접 날짜 범위는 양 끝 날짜 포함.
- 정확한 대상명과 명시 별칭, 금액 양 끝 포함, 시간 시작 포함·종료 제외. 조건 충돌은 미분류. 과거 정정 거래를 덮어쓰지 않음.
- 미분류/새 확인 사유는 첫 발생부터 고정 60초 묶음. 같은 사유 반복 안내·일일 독촉 없음. 앱 내 건수와 자기 알림 재수집 방지, 잠금화면 금융정보 기본 숨김.
- 조회 계좌/카테고리는 복수, 기간은 최대 한 방식. 기본은 전부 미선택으로 전체 조회.
- 사용자 정정은 자동 처리보다 우선. 실제 사용처 확인·누락 없는 전체 거래 수집·은행 실잔액을 보증하지 않음.
- 금융 여부조차 판독하지 못한 알림은 거래로 만들지 않음. 규칙·접근 권한이 없어도 수기 이용 가능하며 저장에는 서버 연결 필요.
- 원문 별도 영구 보관·미전송 금융 자료 장기 대기열·자동 재전송 제외. 최소 실패 표식은 최초 실패부터 최대 30일, 동일 계정 재인증 때만 확인. 결과 불명은 저장 여부부터 확인.
- 이체의 실제 두 기록과 원금/수수료 구분, 같은 구매 안의 환불 N:M·초과 보상 허용·각 발생일 유지. 실제 입금 초과 배분/이중 합산 금지.
- PC 기존 거래 삭제·복구 허용, 새 거래 작성은 모바일. 연결 구매 묶음을 함께 삭제·30일 복구하되 다른 구매까지 연쇄 삭제하지 않음.
- 시작 잔액은 조건부 A안. 구현 전 파일·규모·공수·검증을 보고하고 부담이 크면 B안으로 전환할 수 있다는 조건을 유지.

## 6. 다음 개발 단계와 검증

1. 이번 통합 설계 검토 후 첫 하위 과제의 모바일 인증·공용 계약·DB/API 명세를 작성한다. 승인된 제품 정책은 다시 선택하지 않는다.
2. 실제 변경 파일·규모·대안·보안·테스트를 제시하고 실행 계획을 검토한다. 미확정 세부 계약은 통합 설계 §12에서 추적한다.
3. 공용 계약·추가형 DB 변경·모바일 인증 → 기본 수기·계좌·분류·조회 → 한 알림 형식의 전체 흐름부터 연결한다.
4. 여러 출처/중복/실패 → 선택형 규칙·안내 → 이체·환불·삭제/복구·집계 → PC 편집 중심 완성으로 나눈다. 필요한 PC 표시와 테스트는 각 단계에도 포함한다.
5. 단위·계약·폐기용 DB 격리·API·PC Playwright·Android 합성/실기기 검증을 구별한다. 통합 설계의 V01~V18은 인수 기준 묶음이며 현재 실행 결과가 아니다.

실계좌 연동·운영 결제·기밀 공개·파괴적 DB 적용은 이 인계로 승인되지 않는다. autoplan 전체 검토·구현 계획이 이미 끝났다고 표시하지 않는다. 기존 migration 파일 수정이나 무조건적인 Supabase `db push`도 금지한다.

10/13 변경 대상은 이 인계, 요구사항, 새 통합 설계, `docs/README.md`의 4개다. 루트 README와 제품 코드·SQL·환경변수·패키지는 변경하지 않는다. 검증은 상대 링크·Git diff·비밀정보 패턴·정책 정합성과 기존 변경 보존을 대상으로 한다. 이 문서 작업을 새 기능 테스트/Playwright 통과로 기록하지 않는다. 로컬 커밋과 원격 전송은 구별하며 최종 결과는 Git 이력과 Notion 최신 절에서 확인한다.
