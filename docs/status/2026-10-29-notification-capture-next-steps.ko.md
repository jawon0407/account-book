# 알림 설정 전달 범위와 다음 개발 단계

기준: 2026-10-29, 한국시간. 기능 브랜치 `feature/bank-state-transitions`. 사용자가 완료한 수정의 커밋·푸시와 다음 작업 파악을 요청했다. 이 문서는 다음 기능의 구현 완료 또는 실제 금융 알림 수집 동의를 뜻하지 않는다.

## 이번 전달 범위

- 알림 허용/거부와 대표 기기 지정을 독립적으로 관리한다. 허용·설정 복귀만으로 대표 기기를 지정하지 않는다.
- 허용 상태에는 빨간 알림 거부 버튼을 표시하고, 동의 철회 후 남은 Android 접근을 사용자가 해제할 경로를 유지한다.
- 기기 지정·교체·해제는 중앙 확인 팝업을 사용한다. 오래된 계정/화면의 확인·취소가 새 작업에 적용되지 않도록 보호한다.
- 성공 토스트는 내용 너비에 맞춰 가운데 배치하고 상향 등장·2.5초 종료를 유지한다. 진행 막대는 제거한다.
- 서버·DB·네이티브·의존성·PC 제품 코드는 이번 커밋 범위에서 변경하지 않는다. 실제 알림 본문 수집은 아직 없다.
- 앞선 상태 문서의 ‘미커밋’은 당시 기록이다. 이번 후속 요청으로 관련 완료 작업을 함께 전송한다. 최종 커밋 SHA·원격 반영/CI 상태는 노션 개발일지 및 작업 응답에 별도로 기록한다.

커밋 전 현재 트리에서 전체 자동 테스트 2,377개를 다시 실행해 실패 0·종료 코드 0을 확인했다. 모바일 타입 2종, 변경 코드 ESLint, staged 공백 검사와 18파일 비밀값 패턴 검사도 통과했다. 패턴 검사는 등록된 규칙에 한정하며 전체 보안 감사와 다르다. 환경 파일·캡처·실행 로그는 Git 제외를 확인했다. 이번 재검사에서는 휴대폰을 다시 조작하거나 PC Playwright를 새로 실행하지 않았으며, PC 결과는 바로 앞 구현 검증 기록을 따른다.

## 코드와 문서 대조에서 확인한 상태

`NotificationAccessService.kt`는 연결/연결 해제 상태만 관리한다. `onNotificationPosted` 처리, 알림 판독, 자동 거래 전송이 없다. `NotificationAccessModule.kt`도 상태 조회와 Android 설정 이동만 제공한다. 현재 ‘허용됨’은 실제 자동 기록 중이라는 뜻이 아니다.

Notion 02/07의 이전 ‘고정 출처 선택’ 설명보다 10/28~10/29 사용자 변경과 개발일지를 우선한다. KB·카카오뱅크·토스만 고르는 목록은 다시 만들지 않는다. 다만 알림 접근 가능 범위와 안전하게 판독을 검증한 형식의 범위는 별개다. 미지원 형식이나 가려진 내용은 추정하여 거래를 만들지 않는다.

## 권장 순서

| 순서 | 작업 | 완료 기준 | 상대 규모 |
| --- | --- | --- | --- |
| 0 | 현재 코드 전달·남은 화면 검증 관리 | 기능 브랜치 푸시, 로컬/원격 SHA 일치, 새 원격 CI 상태 구분. 중단된 최신 토스트 성공 경로 실기기 확인은 별도 유지 | 작음 |

| 2 | 검증 가능한 알림 한 형식의 판독 | 입출금/금액/상대/계좌 단서/시각을 추출하고 광고·OTP·일반 대화·자체 알림·단순 승인·요약을 제외. 모호함을 정상 거래와 구분 | 중간~큼 |
| 3 | 최소 정보 접수·원장·PC 연결 | 인증된 접수, 중복 요청 1회 반영, 계좌/분류 미지정 거래 저장·전체 합계, 모바일 분류와 같은 계정 PC 조회/편집 | 큼 |
| 4 | 여러 형식과 예외 확대 | 은행/토스 5초 안전 연결, 지연 후보 24시간 검색, 실패 결과 확인/수기 보완, 선택형 규칙·미분류 안내 | 큼 |

2~3은 합성 알림 한 건이 모바일과 PC 같은 장부에 한 번만 나타나는 첫 종단 단위로 묶어 검증한다. 검증한 한 형식부터 켜는 것은 고정 은행 목록을 제품에 다시 도입하는 뜻이 아니다. 환불·이체·다중 필터·시작 잔액·iOS·공동 장부·실계좌 API까지 이 단위에 섞지 않는다.

## 바로 다음 단위의 예상 파일

아래는 코드 조사에 따른 예비 범위다. 상세 계약을 정할 때 실제 파일 수를 다시 확정하며 지금 파일을 생성하거나 기능 코드를 수정하지 않는다.

- 수정: `apps/mobile/modules/notification-access/android/src/main/java/com/accountbook/notificationaccess/NotificationAccessService.kt`, `NotificationAccessModule.kt`.
- 수정: `apps/mobile/src/collector/android-notification-access.ts`, `apps/mobile/src/platform/notification-access.ts`, `apps/mobile/src/ui/collector-screen.tsx`와 안내 문구.
- 신규 후보: 실행 상태 모델 `apps/mobile/src/collector/collection-runtime.ts`, 표시 패널 `apps/mobile/src/ui/collection-runtime-panel.tsx`, 네이티브 측 처리 허용 검사/수신 데이터 경계를 담당하는 별도 Kotlin 파일.
- 기존 모델/네이티브 계약 시험 보완과 신규 실행 상태 시험, 설계/결과 문서. 제품 코드 약 8~12파일, 테스트·문서 포함 약 12~20파일 예상. 단순 CSS 수정 범위가 아니다.
- 별도 서버 실행 상태·기한 있는 처리 권한이 필요하다고 결정하면 `packages/contracts`, `apps/api/src/collector` 및 DB 이관이 추가된다. 이를 현재 범위에 몰래 포함하지 않고 구현 계획에서 증분을 밝힌다.
- PC 제품 코드 수정은 첫 단위에 예정하지 않는다. 기존 Playwright 회귀는 유지하며, 접수/확인 상태 표시가 필요한 3단계에서 별도 산정한다.

## 코드 작성 전 닫을 기술 경계

1. **백그라운드 책임:** JS 화면이 닫혀도 OS 서비스가 살아 있을 수 있다. UI 토글만으로 보안을 보장하지 않고 네이티브 수신 시점의 세션/동의/대표 기기 판정과 폐기 규칙을 정한다. 서버 확인 실패·권한 만료 때 무조건 계속 수집하지 않는다.
2. **시작과 중지:** 대표 기기 지정·OS 접근·서버 동의·수집 실행을 혼동하지 않는다. 초기 실행은 꺼짐으로 두고 실제 수집이 가능한 버전에서 명시적으로 시작하게 한다. 기존 ‘지금은 읽지 않음’ 안내로 받은 동의와 실제 수집 활성화 안내의 정합성도 확인한다.
3. **개인정보 최소화:** 원문은 필요한 판독 동안 메모리에서만 다루며 로그·DB·분석 도구·장기 재전송 큐에 남기지 않는다. 합성 fixture로 시험하고 실제 금융 알림을 자동으로 시험 자료에 편입하지 않는다.
4. **수신과 저장 분리:** 읽기 허용이 은행 거래 검증을 뜻하지 않는다. 실제 출금/입금이 명확한 데이터만 거래가 되고, 모호함·중복 의심은 별도 확인 흐름으로 보낸다. 저장 계약 전에는 성공적인 자동 기록이라고 표시하지 않는다.
5. **네이티브 재빌드:** 이번 UI는 기존 개발 APK의 새 번들로 확인했다. 수신 기능은 Kotlin 변경이므로 새 APK가 필요하다. 기존 Windows 빌드 경로/캐시 재사용 이력과 깨끗한 재빌드 가능성을 먼저 점검한다.

## 검증과 사용자 준비

- 자동 시험: 시작 전 미수집, 중지/철회/계정 변경 뒤 늦은 콜백 폐기, 다른 기기·사용자 혼입 차단, 알림 갱신/요약/중복, 원문 로그 유출 방지, 전송 실패와 수기 보완 경계.
- 실기기: 시작/중지, Android 설정 왕복, 화면 종료·잠금·재실행·재부팅·연결 끊김. 지원하지 않는 상태는 수집 중으로 표시하지 않는다.
- PC: 합성 거래가 한 번만 나타나고 새로고침/재로그인에도 유지되는지, 다른 계정으로 보이지 않는지 Playwright 확인.
- 사용자는 지금 별도 설정을 바꿀 필요가 없다. 새 APK 검증 때 USB 연결과 일시 디버깅/해당 앱 알림 접근을 다시 요청한다. 실제 송금·개인 비밀번호 입력은 테스트의 전제가 아니다.

## 남아 있는 검증/운영 항목

- 최신 중앙 팝업의 바깥 닫기 및 확인 후 성공 토스트는 사용자의 중단 요청으로 실기기 미완료다. 자동 모델 시험 통과와 구분한다.
- 과거 기본 브랜치 Dependabot 경고와 현재 기능 브랜치 감사 수치는 동일하지 않다. 이번 UI 커밋의 비밀값/푸시 정책 검사 통과를 모든 의존성 취약점 해소로 보고하지 않는다.
- 실제 Supabase 이관, 운영 배포, 전체 보안/개인정보 운영 검증, 새로운 실제 금융정보 수집 승인은 이번 전달 범위 밖이다.
