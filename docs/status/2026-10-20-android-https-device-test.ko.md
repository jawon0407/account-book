# Android HTTPS 로그인·수기 입출금·PC 교차 확인

확인일: 2026-10-20. 대상: Android 16 / arm64 실기기 1대와 PC Chromium.

## 결론

**휴대폰 화면에서 로그인하고 수기로 저장한 지출 20,000원과 수입 50,000원이 PC의 같은 계정에서도 각각 한 건씩 조회됐다.** 두 번째 계정에서는 Android와 PC 모두 해당 기록이 보이지 않았다.

이번 시험은 합성 테스트 계정과 폐기용 로컬 DB를 사용했다. 실제 Supabase 사용자·운영 DB·은행 API·금융 알림을 사용한 시험이 아니다. 저장을 서버 직접 INSERT로 대체하지 않고 실제 Android 입력 화면을 조작했다.

## 사용자가 이해할 실행 흐름

1. 휴대폰의 개발 앱이 USB 연결을 통해 PC의 HTTPS 주소로 로그인 요청을 보낸다.
2. 테스트 인증 제공자가 합성 계정을 확인한다. 실제 Next.js BFF는 모바일 전용 세션을 발급한다.
3. 휴대폰에서 거래 방향·금액·날짜·거래 상대명을 입력하고 저장한다.
4. BFF의 서명된 요청을 NestJS API가 검증하고 로컬 PostgreSQL에 본인 거래를 저장한다.
5. PC는 별도의 웹 로그인 세션으로 같은 API/DB를 조회한다. 휴대폰 화면을 복사하는 것이 아니라 같은 서버의 같은 사용자 자료를 읽는다.

개발 앱은 Metro가 실행되는 PC와 USB 연결이 필요하다. 독립 배포본이나 상시 운영 서버가 아니다.

## HTTPS와 APK의 안전 경계

- 로컬 테스트용 단기 CA/서버 인증서를 생성했다. Android **debug source set**에서 localhost/127.0.0.1만 해당 CA를 신뢰한다. release source set·PC/휴대폰의 전역 신뢰 저장소는 변경하지 않았다.
- API 클라이언트의 HTTPS 요구를 유지했다. 개발 화면 전송용 Metro에 한해 loopback HTTP를 허용한다. 운영 secret/CA 개인키를 APK에 넣지 않았다.
- 독립 HTTPS 클라이언트가 CA 검증을 수행하여 `authorized=true`, `/login` HTTP200을 확인했다.
- PC Playwright는 이 테스트 인증서의 공개키 지문 한 개만 한정 허용한 전용 브라우저를 사용했다. 모든 인증서 오류를 무시하는 설정은 사용하지 않았다. 일반 브라우저가 이 개발 인증서를 자동으로 신뢰한다는 뜻은 아니다.
- 공개 터널·클라우드 배포·운영 Supabase 변경 없음. BFF/API/인증 제공자/DB/Metro는 loopback에 실행한다. DB는 별도 폐기용 cluster이며 기존 DB 덮어쓰기나 강제 삭제를 하지 않았다.

업데이트된 개발 APK: `output/android-apk/account-book-dev-https-arm64.apk`.

- 크기: 91,328,043bytes. SHA-256: `06510FD13FA58B67B77B2C730FDF96FB00A4333B6571EF9520A6A4ADE76B1B4F`.
- APK v2 서명 검증 통과, 실제 기기 업데이트 설치 성공.
- 인증서 리소스만 다시 묶은 Gradle 결과: 종료0, 24초, 445tasks(14실행/431재사용).
- **빌드 한계:** Windows 긴 경로 때문에 전체 네이티브 재컴파일 시도가 실패했다. 검증된 이전 네이티브 산출물을 재사용했고 APK의 23개 `.so`가 이전 검증본과 바이트 단위로 동일함을 확인했다. 깨끗한 환경의 전체 네이티브 재빌드 성공으로 표시하지 않는다.

## 발견한 문제와 보완

### PC 인증 폼의 초기 로딩 제출

JavaScript가 연결되기 전 기본 HTML 폼이 GET으로 제출돼 합성 자격 증명이 URL에 붙는 현상을 Playwright에서 관찰했다. 실제 비밀번호는 사용하지 않았다.

`auth-form.tsx`에서 로그인·가입·비밀번호 복구/변경 폼의 기본 전송을 POST로 명시하고, hydration 전에는 제출 버튼을 잠갔다. JavaScript가 꺼져 있으면 안내문을 표시한다. `useAuthFormReady()`는 서버 렌더링 중 false, 클라이언트 준비 뒤 true를 반환한다. 기존 서버 인증·CSRF·rate limit은 바꾸지 않는다.

- 회귀 시험: 변경 전 SSR 테스트 4개 실패(GET), 변경 후 신규 8개와 기존 인증 UI 19개 모두 통과.
- 실제 PC 브라우저: JavaScript 꺼짐 상태에서 버튼 잠금, Enter로 URL 이동 없음. 준비된 화면은 정상 로그인·거래 조회, 비밀번호 query 요청 0건.
- PC 로그아웃은 같은 URL에서 보호 화면으로 전환하는 기존 동작이다. `/login` 강제 이동을 기다린 첫 검증 스크립트의 timeout은 이를 잘못 가정한 시험 문제였고, 실제 화면 상태로 재확인했다.

### 테스트 실행기의 종료 처리

독립 범위 리뷰에서 Windows 자식 서버 누수(P1), 이미 signal 종료된 프로세스 대기(P2), 실패를 종료0으로 보고(P2)를 확인했다. `lifecycle.ts`는 이 실행기가 직접 만든 PID만 종료하고 Windows의 살아 있는 자식 트리까지 정리한다. 이미 종료된 프로세스는 건너뛰고 정리 대기는 제한 시간을 둔다. 예상 밖 종료/정리 실패는 종료1로 보고한다.

실제 테스트 자식/손자 프로세스를 이용한 종료·signal·실패 상태 5개 시험 통과. `run.ts`의 오류/종료 처리는 이 공통 정리 함수를 사용한다. OS 강제 종료로 부모가 이미 사라진 경우의 고아 프로세스 회수까지 보장하는 시스템 서비스는 아니다. 실행 중인 이전 버전의 테스트 서버는 자동으로 새 종료 코드로 교체되지 않는다.

- 독립 리뷰는 이번 테스트 도구 범위다. 이후 인증 폼 발견은 직접 원인 추적·회귀·Playwright로 검증했다. 혼합 브랜치 전체 PR 승인이나 전문 보안 감사가 아니다.
- using-superpowers/검증 스킬의 근거 우선, cso의 신뢰·비밀 경계, qa-only의 실제 화면 확인, review의 실행기 수명주기 점검을 적용했다. autoplan의 전체 제품·다중 모델 자동 파이프라인 통과로 확대하지 않는다.

## 변경 파일과 역할

- `apps/mobile/tooling/apply-debug-trust.cjs` + 시험: 공개 CA만 받아 생성된 Android debug 리소스에 적용한다. 개인키/기존 설정 덮어쓰기는 거부한다.
- `tests/e2e/device/run.ts`: 합성 인증·BFF·API·폐기용 DB 실행. 환경변수 상속을 제한하고 TLS 준비 여부를 검사한다.
- `tests/e2e/device/lifecycle.ts` + 시험: 소유 프로세스 종료와 실패 상태를 처리한다.
- `apps/web/src/components/auth/auth-form.tsx`, `auth-form-hydration.test.tsx`: 초기 제출 보호와 회귀.
- E2E package/tsconfig·기존 workspace 정책 시험: 새 시험이 검증 목록에서 빠지지 않게 한다.
- 이 상태 문서·계획·실기기 가이드. 기존 다른 미커밋 파일은 보존했다. 커밋/푸시는 수행하지 않았다.

## 다음 작업과 사용자 준비

현재 핵심 수기 기록 경로는 검증됐지만 다음 항목은 남아 있다.

1. 지속 로그인·세션 철회 내구성과 계좌/카테고리 관리 화면.
2. Android 수집 설정/알림 접근 권한 → 한 가지 검증된 금융 알림의 판독·저장·PC 확인.
3. 저장 중 통신 끊김, 기기 재실행, 시간대/DST, TalkBack·글자 확대·최근 앱 미리보기의 실기기 검증.
4. 다중 필터·선택형 자동분류·환불/복구·집계·시작 잔액 후속 구현. iOS는 이후다.
5. 기존 node-forge/braces 의존성 경고 2건은 이번 작업에서 해결/재감사하지 않았다. 실금융 베타 게이트는 유지한다.

사용자는 당장 은행/카카오톡/SMS 알림 접근을 켤 필요가 없다. 계속 시험할 때만 USB 연결·앱 열기를 유지하고, 종료 뒤에는 USB 디버깅을 끄고 일시 해제한 제조사 보안 설정을 복원한다. 개발 앱에는 실제 계정 비밀번호나 실제 금융정보를 입력하지 않는다.
