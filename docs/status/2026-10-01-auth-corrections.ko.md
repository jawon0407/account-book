# 가입·로그인·비밀번호 복구 수정 기록

## 요청과 확정 정책

사용자 보고: 복구 링크가 로그인 필요 화면으로 이동, 미가입 이메일에도 접수 안내, 중복 가입 구분 부재, 정상 로그인 시 인증 서비스 503.

2026-10-01 사용자는 이메일 존재 여부 노출 위험을 설명받은 후 **위험을 수용하고 존재 여부 표시**를 선택했다. 기존 계정 열거 방지 정책의 명시적 예외다. 비밀번호 찾기는 비로그인 사용자에게 공개하되, 실제 비밀번호 변경에는 일회성 복구 코드·서버 PKCE·브라우저 문맥이 필요하다.

## 조사 증거

- Playwright: 만료 오류를 가진 `/api/auth/password/callback`이 `/app`으로 이동하는 것을 재현했다. 복구 요청 페이지에 로그인 권한이 걸린 것이 아니라 실패 이동 대상이 잘못됐다.
- 실제 Supabase 잘못된 자격 증명: 401. HTTPS·CSRF·위임 API smoke 13개 통과.
- 실제 BFF/API 역할·TLS·최소 권한 32개 통과(검사 쓰기는 rollback).
- 읽기 전용 집계에서 최근 1시간 Supabase 로그인 기록 1개, BFF 세션 생성 0개. 사용자 행·비밀번호·토큰은 출력하지 않았다.
- DB 시계와 PC 시계 약 1초 차이. SDK는 expires_at이 없으면 로컬 시각으로 계산하므로 JWT exp와 엄격한 동일 비교는 정상 응답을 거절할 수 있다. 실제 사용자 로그인 재성공은 별도 확인해야 한다.

## 설계와 파일 범위

기존 인증 흐름에 한정하며 새로운 인증 제공자·결제·운영 배포는 추가하지 않는다. 사용자 기존 지시대로 작업 계획을 공개하고 불필요한 승인 반복 없이 진행한다.

1. `auth-controller.ts`와 공개 복구 실패 페이지: 실패 시 `/forgot-password/invalid-link`, 코드·토큰을 다음 URL에 남기지 않음.
2. `account-access.ts` 신규 서버 모듈·container 연결·공유 오류 계약: 가입 전 existing→409, 복구 전 absent→404, 조회 실패는503. CSRF/입력 검사 후 실행.
3. 신규 SQL 함수: BFF만 이메일 하나의 존재 상태 확인. `auth.users` 직접 SELECT/관리자 키/공개 RPC 허용 없음. 고정 search_path, 매개변수화, 기존 rate-limit 테이블에 이메일·브라우저 HMAC과 전역 예산 적용. 10분당 이메일5회·브라우저20회·전체120회, 가입/복구 종류별. 회전되는 인증 interaction과 별개인 600초짜리 `__Host-ab_auth_budget` 쿠키로 정상 요청 간 예산을 유지한다. 악성 클라이언트의 쿠키 삭제와 분산 공격을 완전히 막지는 못하므로 공개 운영 전 플랫폼 rate limit/CAPTCHA 필요.
4. OAuth signup intent를 서버 트랜잭션에 저장. 가입 callback은 앱 세션을 만들지 않고 로그인 안내로 이동한다. 신규/기존 여부를 공급자·PC 시각 비교로 추측하지 않는다. 동일 identity 중복 계정 방지는 Supabase가 담당한다.
5. 공급자 시각 검증: 허용된 작은 미래 발급 시각·SDK 계산 차이만 처리. JWT 실제 만료·폐기 기준·원시 응답의 모순 검사는 유지.
6. 테스트/문서: RED→GREEN, 실제 PostgreSQL 권한·요청 제한, 전체 일반 회귀, PC Playwright. 소셜 실제 성공은 아직 제공자 설정 전이므로 합성 검증과 구분한다.

최초 예상 15~25개에서 보안 회귀·적용 도구·문서를 포함해 **실제 47개 파일 추가/수정**으로 확대되었다(Next가 자동 생성한 `next-env.d.ts` 제외). 함수 역할·매개변수 주석을 유지했다. 인증과 연결된 범위이며 금융 기능 변경은 없다.

`scripts/local-auth/apply-auth-corrections.mjs --check`로 적용 후 전체 rollback을 먼저 확인하고 `--apply`를 수행했다. 도구는 승인 개발 프로젝트·SQL 해시·CA·TLS를 고정하고 기존 개체가 있으면 재실행을 거부한다. 초기 probe에서 관리형 postgres의 역할 전환 불가(42501)를 발견했지만 모두 rollback되었다. 권한을 추가하지 않고, 적용 후 실제 BFF 자격으로 검사하도록 바꿨다. 시험 호출의 rate counter도 rollback했다. **이미 적용된 현재 DB에 다시 실행하지 않는다.**

RED→GREEN 회귀에는 1초 SDK 만료 계산 차이, 60/61초 발급 경계, 만료 JWT 거절, 중복409·미존재404, 복구 공개 이동, 예산 쿠키 회전 독립성, OAuth 의도 보관과 가입 시 앱 세션 미발급이 포함된다. 첫 전체 검증의 기존 안내 문구 기대값과 Next 검색 파라미터 null 처리를 보완했고, Playwright의 중복 alert/status locator를 화면 영역으로 좁혀 재실행했다. 최종 수치는 재실행 성공 결과다.

## 리뷰에서 추가로 보완한 보안 경계

1. **브라우저 예산 초기화:** 인증 쿠키를 매번 바꾸면 제한 지문도 바뀌던 문제를 별도 예산 쿠키로 해결했다. 성공·404·409·429·503 모두 예산 쿠키를 유지하며 CSRF/본문 검증 실패 전에는 만들지 않는다.
2. **복구와 시계 오차:** DB 시각 T에서 비밀번호를 바꿔도 이전 토큰의 `iat=T+30`이 허용되던 조건을 차단했다. 복구 후 하한을 `max(기존 하한, floor(DB 현재 초)+61)`로 올리고, 원본 JWT 발급값은 그대로 비교한다. Auth·DB·BFF 시계 동기화가 필요하며 **Auth↔DB 오차가 60초 이내**인 조건이다. 새 로그인은 시계 차이에 따라 약 1~2분(경계상 최대 약 121초) 대기가 필요할 수 있어 재설정 완료 화면에 안내했다.

남은 운영 위험: 이메일 존재 여부 공개 자체, 쿠키 삭제 우회, 전역 예산 소진에 따른 다른 사용자의 일시 차단, rate counter 보존/정리 정책, 공개 서비스의 edge 호출 제한·CAPTCHA·경보. 이 작업은 침투테스트나 운영 보안 완료를 뜻하지 않는다.

## 사용자가 확인할 다음 단계

후속 확인(2026-10-01): 사용자가 “문제 없이 해결된거 확인했어”라고 직접 확인했다. 실제 본인 인증 성공에 대한 사용자 보고이며, 아래 메일·공급자별 전체 운영 검증과 구분한다.

1. `https://localhost:3000/login`에서 기존 본인 계정으로 다시 로그인한다. 비밀번호는 채팅에 보내지 않는다.
2. 복구가 필요하면 `/forgot-password`에서 요청하고 같은 브라우저의 최신 메일 링크로 변경한다. 메일 수신/SMTP·발송 제한은 아직 실제 검증하지 않았다.
3. 소셜은 사용자 개발자 앱/키/콜백/Supabase 설정을 마친 뒤 공급자별 성공·취소·갱신·로그아웃·기존 가입 경로를 검증한다. 현재 기본 비활성을 유지했다.

로컬 웹 3000과 API 3001은 모두 loopback에서 실행 중이다. 기존 계정/금융 데이터 삭제, 실제 비밀번호 변경, 운영 배포·은행 호출·유료 설정 변경은 하지 않았다.
