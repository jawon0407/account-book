# A2.2 다음 작업 사전 점검 — 은행 연결 상태 처리

기준: 2026-09-29, A2.1 PR #18 병합 커밋 `b7ecd830c3aefd9b225b100b1087d78d39e2ddc1`.
현재 단계는 **사전 범위 정리**다. A2.2 상세 함수 설계·테스트·제품 코드는 아직 작성하지 않았다. 이 문서를 실행 완료나 상세 구현 계획으로 취급하지 않는다.

## 사용자가 겪을 문제와 목표

두 탭에서 동시에 은행 연결을 완료하거나 같은 Callback이 다시 도착해도 하나의 요청만 처리해야 한다. 다른 사용자·로그인 세션의 요청을 가져올 수 없어야 하고, 유효 시간이 지난 인증 코드는 즉시 거부해야 한다.

A2.1은 자료를 담는 테이블과 저장 규칙이다. A2.2는 그 자료를 안전한 순서로 바꾸는 처리다. 외부 은행 호출 자체는 A3에서 연결하며, 이번에 운영 DB나 실계좌를 사용하지 않는다.

## 검토할 처리 흐름

1. 시작: 같은 사용자·세션의 이전 미완료 요청을 취소하고 새 요청을 만든다. 이미 코드 교환 중이면 충돌로 거부한다.
2. Callback: state 지문으로 요청을 확인하고 유효 시간 안의 인가 코드만 암호화해 잠시 저장한다. 중복 Callback은 기존 자료를 덮어쓰지 않는다.
3. 완료 권한 획득: 사용자·세션·proof·기한을 확인한 한 요청만 `exchanging`으로 바꾼다. 임시 코드는 DB에서 제거하며 API의 한 번뿐인 교환에 사용한다.
4. 성공/실패: 성공한 연결과 암호화 자격정보를 함께 저장하거나 실패 상태를 기록한다. 요청이 불명확하게 끝났다면 같은 코드를 자동 재전송하지 않는다.
5. 취소/만료: 종료된 요청에 임시 코드를 남기지 않는다. 청소 작업을 기다리지 않고 사용 순간 기한을 검사한다.

## 접근법과 유지보수 영향

| 접근법 | 장점 | 부담과 결정 |
| --- | --- | --- |
| API에서 일반 SQL을 조합 | TypeScript 개발 흐름이 단순함 | 여러 경로의 조건 누락과 런타임 직접 쓰기 권한 확대를 검토해야 하므로 기존 최소 권한 설계와 맞지 않음 |
| 작은 DB 원자 함수 + 최소 실행 권한 | 서버가 여러 개여도 같은 전이·동시성 규칙 적용 | 함수 소유자·RLS·잠금·실행 권한 테스트가 필요함. 승인된 A2 설계에 따라 이 방향을 상세화 |
| 별도 Redis/작업 엔진 | 별도 분산 조정 도구 활용 가능 | 새 서비스·비용·운영 복잡도가 늘어 이번 범위에서 제외 |

함수 소유자 역할, 고정 검색 경로, PUBLIC 실행 철회, 본인 문맥 검증은 상세 설계의 필수 점검 대상이다. 새 권한을 미리 부여하지 않는다.

## 예상 변경 파일

아래는 사전 파일 지도이며 최종 함수 서명·migration 이름은 상세 설계와 실행 계획에서 고정한다.

- `supabase/migrations/`: 함수 전용 역할/정책, 시작/Callback, 교환 권한/완료, 취소/만료를 역할별 새 migration으로 분리한다.
- `tests/database/`: 시작·Callback·완료·종료·실제 동시 요청·권한 거부를 작은 테스트 파일로 분리한다.
- `tests/database/support/bank-database.ts`: 추가 migration과 독립 DB 연결의 안전한 생성·정리를 지원한다. 기존 DB 삭제 금지는 유지한다.
- `tests/database/support/bank-fixtures.ts`: 상태 전이 테스트용 합성 자료를 추가한다. 실제 사용자나 은행 자료는 사용하지 않는다.
- `docs/superpowers/specs/`, `docs/superpowers/plans/`: 함수의 입력·반환·오류·잠금 순서·검증 절차를 먼저 확정한다.
- `docs/database/bank-connections.ko.md`, 진행 기록과 Notion A2: 초급 개발자 설명과 기능별 체크를 갱신한다.

예상: 코드/테스트 10~14파일, 약 700~1,200줄 + 문서 3~4파일. 상세 함수 수와 동시성 시험에서 달라질 수 있으며, 변경 전에 실제 파일 지도를 다시 기록한다. BFF·웹 화면·모바일·공급자 HTTP 어댑터는 이번 범위 밖이다.

## 검증 순서와 중단 기준

- 상세 설계 → 파일별 실행 계획 → 실제 PostgreSQL RED → 최소 구현 → GREEN → 전체 회귀 → 독립 리뷰 → 정상 PR/main 검사.
- 동시성은 같은 연결을 재사용한 순차 mock이 아니라 별도 DB 연결의 경쟁 요청으로 검증한다.
- 유효 시간 경계, 다른 사용자/세션/proof, 잘못된 상태, 중복 Callback, 취소·교환 경쟁, 종료 후 암호문 제거를 각각 검사한다.
- BFF·공개 역할·직접 DML·함수 역할로의 권한 상승은 계속 거부해야 한다.
- 외부 은행 HTTP 호출을 DB transaction/잠금 안에서 실행하지 않는다.
- 운영 권한·실제 비밀값·비용·보안 완화가 필요해지면 해당 부분을 멈추고 사용자에게 알린다. 일반 개발은 반복 승인 없이 진행한다.

공유 요청 제한·오래된 요청 정리는 A2.3, API 연결은 A3, 웹 은행 연결 UI는 A4다. 실제 잔액·거래 자동 수집과 별도 모바일 앱은 여전히 후속 작업이다.
