# Android 화면의 서버 동의·철회 연결

확인일: 2026-10-21. 기준 커밋: `94f19be`. 이 문서는 앞선 로컬 동의 실기기 시험과 새 서버 연결 시험을 구분한다.

## 이번 변경과 사용 흐름

‘수집 설정’의 동의 화면을 기존 서버 API에 연결했다. 화면 진입 → 서버 상태 조회 → 고지 확인 → 동의 또는 철회 → 서버 응답 확인 순서다. 저장하기 전부터 완료로 보이지 않으며, 동의 저장과 Android 알림 접근은 각각 별도다. **실제 알림 본문 읽기·자동 거래 저장은 아직 없다.**

이전 SecureStore의 로컬 동의는 읽거나 서버로 자동 전송하지 않는다. 과거 기록도 이번에 지우지 않는다. 서버에 동의가 없으면 사용자가 고지를 다시 확인해야 한다. 거절해도 기존 수기 장부는 사용할 수 있다.

## 파일과 역할

수정 전 [설계](../superpowers/specs/2026-10-21-mobile-server-consent-design.md)·[계획](../superpowers/plans/2026-10-21-mobile-server-consent.md)을 작성하고 Notion 07번에 기록했다. 최종16파일(제품·시험·설정11, 문서5)로, 예상10~14파일보다 테스트 타입 검사 목록과 실기기 안내가 추가됐다. 새 의존성은 없다.

| 파일 | 초급 개발자용 설명 |
| --- | --- |

통신 흐름: 화면 → 동의 모델 → SessionManager → NativeCollectorClient → HTTPS BFF → NestJS → 기존 PostgreSQL 제한 함수. 계정/설치 ID·서버 시각은 요청 본문으로 받지 않는다. 이번 제품 변경에 새 DB 테이블이나 의존성은 없다.

## 실패와 보안 처리

- `not_granted`/`granted`/`withdrawn`/`outdated`를 구분한다. 오래된 고지는 재동의 또는 철회할 수 있다.
- 통신 실패·버전 충돌·잘못된 응답이면 동의 상태를 미확정으로 바꾸며 성공을 표시하지 않는다. 변경 요청은 자동 재전송하지 않는다.
- 재조회는 GET만 한다. 철회 실패 후 동의가 남아 있으면 다시 철회해야 한다고 안내한다. 응답만 유실되고 실제 철회된 경우에는 GET 결과로 확인한다.
- 서버 오류 중에도 실제 OS 접근이 켜져 있으면 해제용 설정으로 이동할 수 있다. 반대로 OS 조회가 실패해도 서버 철회는 가능하다.
- 로그아웃·계정 재로그인·화면 이탈·앱 복귀 재검증 뒤 늦은 응답을 거부한다. 중복 클릭은 한 요청만 보낸다.
- 앱 권한을 강제로 변경하지 않았으며 HTTPS 검증을 끄지 않았다. 원시 서버 오류·토큰을 화면에 표시하지 않는다.
- 동의 기록은 현재 상태이며, 법적 증빙 전체나 불변 감사 이력이 완성됐다는 뜻은 아니다. 오프라인 철회 큐도 이 단계에는 없다.

## 검증 결과

- RED→GREEN: HTTP/세션16개, 모델/표시31개. 신규 기능이 없는 상태의 실패를 확인한 뒤 통과했다.
- 전체 모바일223개(213 + 도구10), 전체 프로젝트2,285개(기존 도구208 + 계약186 + DB 모델19 + API333 + 웹1,225 + 모바일223 + E2E 사전검사91) 통과.
- 전체 린트·타입 검사, Android JavaScript/Hermes 번들 생성, NestJS TypeScript 빌드 통과. Android 번들은 APK 제작/실기기 검증과 다르다.
- 실제 로컬 HTTPS 왕복: 모바일의 실제 API/세션/동의 모델을 사용하여 미동의 → 동의v1 → 철회v2 → GET 확인 → 재동의v3 → 정리 철회v4를 확인했다. 같은 사용자의 다른 설치는 미동의였고, 오래된 버전은409, 로그아웃 뒤 조회는 차단됐다. 기존 수기 거래2건 유지, 신규 금융 거래 작성0건.
- 위 왕복은 Node의 네이티브형 HTTPS 전송과 OS 상태 대역을 사용했다. 앱의 실제 Android 전송/화면 터치는 아니며, 로컬 CA를 추가 신뢰하되 인증서 검증은 유지했다. 첫 Node fetch 시험은 브라우저형 `Sec-Fetch-Mode` 때문에 서버에서 거부됐고 서버 보호를 완화하지 않고 시험 전송기를 수정했다.
- PC Playwright: 서버 최종 재시작 후 기존 합성 입출금2건 조회, 새로고침 후2건, 로그아웃 뒤0건, 페이지 오류0 확인. 로그인 이동 주소를 `/app/accounts`로 예상한 첫 대기는 실패했으며 실제 `/app` 화면을 관찰해 검사했다. 별도 테스트 브라우저 문맥만 개발 인증서 예외를 사용했다. 일반 브라우저나 앱의 TLS 정책은 바꾸지 않았다. 증거: `output/mobile-consent-pc-records.png`.
- 독립 코드 리뷰: Critical0 / Important0 / Minor0. 현재 변경과 신규 파일, 공통 계약 및 상위 화면의 background 해제/복귀 흐름을 검토했다. 리뷰어의 시험 재실행은 기본 Node/pnpm 버전 불일치로 실행 전 차단됐으므로 위 시험 통과는 구현 담당자가 고정된22.15.1/11.9.0 환경에서 직접 실행한 결과다. 별도의 미해결 코드 지적은 없다.
- 마지막 완료 기록용 재검사에서 Git Bash가 Git 실행 파일 탐색 순서를 바꿔 기존 훅 시험 1개가 셸을 찾지 못했다. 같은 단일 시험은 정상 PowerShell에서 통과했다. 중간의 구형 PowerShell 실행도 고정 런타임 선택에 실패했으므로 PowerShell 7·고정 Node/pnpm·Windows용 Git/cmd 경로로 실행 환경을 통일했다. 제품이나 보안 게이트를 수정하거나 시험을 제외하지 않고 전체 2,285개를 다시 실행해 모두 통과했다. 최종 로그는 `.superpowers/sdd/2026-10-21-mobile-server-consent/task-3-tests.log`다.

## 로컬 실행 환경

실행 중이던 합성 화면 DB에는 동의 테이블이 아직 없어, 앞선 `20261021050645_notification_consent.sql`만 단일 transaction으로 적용했다. 대상이 loopback의 `account_book_core_test`인지 확인하고 거래2건 및 BFF/API 역할 속성이 전후 동일함을 확인했다. 동의 테이블 RLS/FORCE RLS도 확인했다. 전체 DB 초기화/삭제는 하지 않았다.

기존 합성 실행기로 API/웹/테스트 인증 서버를 재시작했다. HTTPS3000·API4511·인증4510·Metro8081 구성이다. 세션 암호 키가 바뀌므로 이전 테스트 세션은 다시 로그인할 수 있다. 운영 Supabase 프로젝트는 읽거나 수정하지 않았다.

## 미완료와 다음 단계

1. USB 연결 기기0대여서 새 동의 화면의 Android 실제 터치/OS 왕복은 미검증이다. 기존 권한 모듈 포함 개발 APK와 최신 Metro로 확인하면 되며 새 네이티브 변경은 없다.
2. 선택 출처와 수집 시작/중지 상태를 설계에 맞춰 연결한다.
3. 합성 금융 알림 한 지원 형식의 판독 → 미분류 거래 → PC 조회를 구현한다.
4. 실제 알림·운영 DB·스토어/독립 APK·원격 CI/배포·전체 DB 시험·전체 취약점 재감사는 이번 결과에 포함하지 않는다. 기존 기본 브랜치 의존성 경고25건도 별도 미해결이다.

관련 없는 `apps/web/next-env.d.ts` 변경은 보존한다. 변경한 제품 파일에 비밀값이나 실제 금융 알림은 추가하지 않았다.

## 진행 판단과 보존 상태

기존 연속 진행 지시에 따라 승인 질문을 반복하지 않고 승인된 연결 범위만 구현했다. 범위를 새로 바꾸는 제품 결정은 하지 않았다. 이번 후속에는 별도 커밋/푸시 요청이 없어 로컬 변경으로 보존하며, GitHub 반영은 다음 작업이다. 앞선 서버 기반까지의 푸시와 혼동하지 않는다.

리뷰에서 판단을 보류한 범위도 명시한다. Android 렌더링·터치·접근성·OS 왕복은 기기 연결 후 추가 확인이 필요하므로 단말 특유 문제가 남을 수 있다. 운영 배포/hosted DB/전체 의존성 보안/법적 동의 적정성은 출시 검증이 따로 필요하다. 실제 알림 수집·자동 저장·오프라인 철회 큐는 이번 구현에서 제외되어 아직 자동 기록을 사용할 수 없다. 미해결 사소한 코드 지적은 없다.
