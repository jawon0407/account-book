# Android 장부 연결·PC 편집 권한 구현 기록

## 현재 어디까지 됐나요?

Android 앱이 사용할 인증 경로에 이어 **프로필·계좌·카테고리·거래 API 14개 작업**을 연결했다. Android용 HTTP 경로에서 만든 거래를 같은 계정의 PC 웹에서 조회·수정·삭제할 수 있다. PC에서는 신규 거래 작성을 막고 계좌·카테고리 관리는 유지한다.

이것은 **서버 연결 단계의 로컬 구현**이다. `apps/mobile`·APK·알림 접근/판독/자동 기록·실기기 시험은 아직 없다. Android 우선, iOS는 Android 승인 범위와 실기기 검증 뒤에 진행한다. 앱이 없는 현재의 PC 작성 제한 상태는 사용자에게 배포하지 않는다. 실제 Supabase 이관·배포·커밋/푸시는 하지 않았고 기존 혼합 미커밋 작업은 보존했다.

## 초급 개발자를 위한 요청 흐름

1. Android 앱은 기존 이메일 로그인 경로에서 앱 세션 자격 증명을 받는다. 공급자 토큰·DB 비밀번호는 받지 않는다.
2. 앱이 `Authorization: Bearer ...`로 장부 경로를 호출하면 BFF가 HTTPS·주소·헤더·입력 크기와 세션을 검사한다.
3. BFF는 서버 세션의 사용자·설치 ID·채널이 맞는지 확인한다. `x-client-channel: android` 같은 외부 헤더만 보내도 Android 권한을 얻는 구조가 아니다.
4. 검증된 채널을 `chn`이라는 JWT 항목에 서명한다. 기존 30초 유효 기간·요청 내용 결합·재사용 방어를 유지한다. 값이 없거나 잘못되면 기본값으로 추측하지 않고 거절한다.
5. NestJS는 서명과 권한을 다시 검증한다. 새 거래 생성은 Android 채널만 허용하며, 타인 계좌/카테고리를 사용하거나 수정 버전이 어긋나는 요청은 기존 저장소 경계에서 거절한다.
6. PC도 같은 사용자·같은 원장을 조회한다. 별도 모바일 DB에 복제하지 않으므로 거래 ID·금액·수정 버전을 공유한다.

채널은 **서버 인증 경로의 구분**이다. 정식 APK나 Android 하드웨어를 증명하지 않으며 유효한 자격 증명을 가진 다른 HTTP 프로그램까지 차단한다는 뜻도 아니다. 수기 기록과 계정당 자동 수집 기기 1대 정책은 별개다.

## 작업별 권한

| 작업 | PC 웹 | Android HTTP |
| --- | --- | --- |
| 프로필·계좌·카테고리 조회/관리 | 허용 | 허용 |
| 거래 조회·수정·삭제 | 허용 | 허용 |
| 새 수기 거래 작성 | 403 거절 | 허용 |
| 알림 자동 기록 | 없음 | 후속 구현 |

PC 화면에서 생성 버튼과 폼 연결을 제거했다. 빈 목록에서도 PC 작성을 권하지 않고, Android 설치 파일이 아직 없다는 안내를 표시한다. 이번 화면 검증은 기존 PC 디자인의 기능 회귀 확인이며 새 모바일 Figma 디자인 구현 완료가 아니다.

## 파일과 역할

이번 단위의 제품·테스트·설정 변경 목록은 **52파일**이다. 최초 예상 40~55파일 범위이며 이전 은행/인증/원장 작업 전체의 Git diff와 구분한다. 작은 라우트 9개와 인증 fixture·부정 테스트가 포함되어 파일 수에 비해 핵심 로직은 작다. 신규 패키지·DB 테이블·역할 권한·migration은 추가하지 않았다.

| 파일/묶음 | 역할 |
| --- | --- |
| `packages/contracts/src/internal-api.ts`, `errors.ts` | 필수 채널 타입과 고정된 403 오류 |
| API의 `principal.ts`, `jwt-verifier.ts`, `delegated-scope.ts`, `auth.guard.ts` | 서명된 채널을 검증된 사용자 정보로 전달하고 경로 권한 검사 |
| `transactions.controller.ts`, `core-error.ts` | Android 전용 거래 생성과 안전한 오류 상태 |
| 웹 `security/delegated-jwt-signer.ts`, `http/delegated-api-client.ts` | 서버 채널을 요청에 묶어 서명·전달 |
| `security/native-request.ts` | HTTPS/canonical origin, Bearer, 브라우저 헤더 혼용 검사 |
| `core/channel-auth.ts` | 웹 쿠키/CSRF와 Android 세션·기기·갱신 시각·제한을 분리 |
| `core/core-controller.ts`, `operations.ts`, `http-boundary.ts`, `route-adapter.ts` | 기존 14작업과 요청/응답 검증 재사용 |
| `native-auth`의 boundary/types/limiter, `container.ts` | 공통 경계 추출, 읽기/쓰기 제한, 요청별 서비스 조립 |
| `app/api/native`의 장부 라우트 9개 | 고정 경로·메서드만 해당 작업에 연결 |
| 기존 auth/bank 호출자와 테스트 fixture | 새 필수 채널을 서버 세션에서 명시적으로 전달 |
| `transaction-page.tsx`, 단위·API·DB·E2E 테스트, Vitest 설정 | PC 생성 연결 제거와 인증/권한·실제 저장·PC 회귀 검증 |

함수 주석에는 입력의 신뢰 여부·매개변수·역할·실패 조건을 적었다. `coreRequestSelector`는 HTTP 자격 증명을 검사하고, `coreSession`은 그 자격 증명이 가리키는 서버 세션을 검사한다. 인증과 거래 업무 처리를 한 함수에 합치지 않았다.

## 제한과 실패 처리

- 새 native 경로는 Node.js 런타임, 캐시 금지, 고정 작업만 사용한다. 쿠키·Origin·Sec-Fetch가 섞인 요청은 거절한다.
- JSON 본문 16KiB/3초, 상위 응답 1MiB 제한을 재사용한다. 리다이렉트와 자동 변경 재전송을 하지 않는다.
- 서버 접근 토큰 만료까지 60초 이하이면 명시적 갱신을 요구한다. 계정 전환 전 사용자의 요청은 새로운 계정에 쓰지 않는다.
- 읽기 제한은 전역 분당 1,200/사용자+설치 60, 쓰기는 전역 600/사용자+설치 30이다. 로그인/갱신 제한과 별도 HMAC 작업 구분을 사용한다. 한도 초과 429, 제한 DB 장애 503으로 실패한다.
- 멱등성 키가 같은 Android 생성 요청은 같은 거래를 반환한다. 잘못된 사용자 계좌는 존재 여부를 드러내지 않는 404를 유지한다.

## 검증과 발견한 문제

1. 실제 JWT 서명/검증 RED 각각 10건, native 경계 RED 32/109, API RED 1/35를 확인하고 구현했다. PC 생성 버튼 제거도 RED 1건 이후 GREEN을 확인했다.
2. 첫 PC E2E는 16/17이었다. 타인 계좌의 생성 요청이 409여야 한다는 테스트 기대가 틀렸고 실제 404가 기존 개인정보 경계에 맞았다. 테스트를 404와 `LEDGER_NOT_FOUND` 확인으로 수정했다. 제품 권한은 완화하지 않았다.
3. 파일 추출 후 기존 커버리지 목록에서 `native-request.ts`가 빠지는 문제를 발견했다. 기존 24파일을 빼지 않고 추출 helper·새 채널 인증·JWT 서명기를 더해 27파일로 확대했다. 첫 결과 99.63%의 미검사 분기 4개는 누락 쿠키, GET 본문, GET 출처, 잘못된 세션 만료 시각이었다. 기존 거절 동작에 대한 6개 회귀 테스트를 추가했으며 기준을 낮추지 않았다.
4. 독립 읽기 전용 코드·보안 리뷰: Critical 0, Important 0, 별도 수정이 필요한 Minor 0. 현재 파일의 이번 변경 범위만 검토했다. 전체 PR·이전 혼합 변경·실기기·운영 침투검사 승인으로 확대하지 않는다.

### 확인된 결과

- 실제 로컬 PostgreSQL 통합: **336개 / 28파일 통과**, 종료 0.
- core Playwright: **17개 통과 / 37.2초**, 종료 0. 실제 Next/NestJS/폐기용 DB와 합성 인증 공급자로 Android HTTP 생성→PC 조회/편집/삭제·합계, 중복 생성 방지, PC 생성 403, 다른 계정 격리, 충돌·응답 유실·세션 만료를 검증했다. Android 실기기 시험은 아니다.
- 웹 coverage: **1,192개 / 69파일 통과**, 선택한 인증/보안 27파일 분기 **1,098/1,098(100%)**, 문장 99.73%, 함수 99.56%, 줄 99.77%. 전체 프로젝트 100%가 아니다.
- 운영 및 전체 의존성 감사: 알려진 취약점 보고 0건. 공개 권고 검사 결과이며 취약점 부재의 보증은 아니다.
- 최종 `pnpm verify`: 종료 0. 린트·6개 workspace 타입 검사·전체 테스트·API/웹 production build 통과. 테스트 구성은 legacy/security 208, contracts 98, database 단위 19, API 296, web 1,192, preflight 86으로 총 **1,899개**다.
- 문서를 포함한 Git 추적/비무시 **772파일**의 등록된 비밀 패턴 검사: 0건, 종료 0. 무시된 실제 환경변수는 읽지 않았으며 모든 비밀 형식을 탐지하는 검사는 아니다. `git diff --check`는 종료 0이며 CRLF→LF 정규화 안내만 있었다.
- 검증용 로컬 PostgreSQL은 마지막 상태 확인에서 실행 중이 아니었다. 실제 서비스 DB/서버에는 손대지 않았다. E2E의 Next 타입 참조 자동 변경은 기존 production 경로로 복원했다.

## 적용 순서와 다음 개발

현재 변경은 로컬 검증만 했다. 운영에는 선행 세션 채널·요청 제한 migration을 승인된 주체가 적용하고, 새 BFF/API 조합을 함께 검증해야 한다. **구 BFF가 새 API에 `chn` 없이 요청하면 401**이다. 무중단 혼합 배포를 보장하지 않으므로 호환 전환 또는 점검 창·함께 되돌리기 계획이 필요하다. 이번 작업은 배포하지 않는다.

1. 계정당 활성 자동 수집 기기 1대: 교체·철회와 진행 중/늦게 도착한 쓰기를 서버에서 차단하는 계약·DB/API를 구현한다.
2. Android 기본 앱: 안전 저장소, 로그인/갱신 직렬화, 계좌·카테고리·수기 기록·조회/편집을 연결한다. 가입·복구/소셜 복귀 계약은 별도로 완성한다.
3. 검증한 금융 알림 형식부터 수집→미분류 거래→사용자 분류→PC 동기화를 실제 기기에서 검증한다. 모든 은행/문자/카카오톡 형식을 한 번에 지원한다고 표시하지 않는다.
4. 정밀 시각/시간대, 복수 필터, 선택형 규칙, 환불·30일 복구·집계, 시작 잔액의 승인 범위를 순차 완성한다. 시작 잔액은 구현 전 별도 공수 보고 조건을 유지한다.

현재 사용자에게 새 키나 실제 금융 데이터를 요청할 필요는 없다. Android SDK·Java·adb 환경 및 기기 설치/권한 승인이 필요한 시점에 안내한다. Autoplan 필수 참조 경로 누락은 직접 설계·TDD·독립 리뷰로 보완했으며 전체 자동 파이프라인 실행으로 표시하지 않는다.
