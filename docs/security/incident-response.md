# 보안 사고 대응 절차

## 1. 목표와 원칙

사고 대응의 우선순위는 추가 피해 차단, 증거 보존, 안전한 복구, 사용자 보호, 재발 방지다. 기능 가용성을 유지하려고 데이터 유출이나 무단 변경 가능성을 방치하지 않는다.

팀이 구성되기 전 사고 지휘자와 보안 책임자는 저장소 소유자다. 데이터베이스·인증·배포 공급자와의 연락, 사용자 공지, 복구 승인을 한곳에서 조정한다. 사고와 관련된 토큰, 개인정보, 공격 페이로드는 일반 채팅이나 공개 Issue에 공유하지 않는다.

## 2. 심각도

| 등급 | 기준 | 초기 목표 |
|---|---|---|
| SEV-1 치명적 | 사용자 간 재무 데이터 노출·변조, 운영 secret 또는 관리자 계정 탈취, 광범위 계정 탈취, 복구 불가능한 데이터 손상 | 즉시 배포·관련 기능 중단, 세션·키 폐기, 1시간 이내 범위 파악 시작 |
| SEV-2 높음 | 제한된 사용자 데이터 노출, 악용 가능한 인증·권한 우회, 배포 공급망 손상 가능성 | 4시간 이내 완화 또는 기능 차단, 당일 원인 분석 시작 |
| SEV-3 중간 | 직접 악용 조건이 제한된 취약점, 민감하지 않은 로그 노출, 보완 통제가 있는 설정 오류 | 1영업일 이내 책임자·수정 계획 확정 |
| SEV-4 낮음 | 악용 가능성이 낮고 사용자 영향이 작은 방어 강화 항목 | 정상 유지보수 일정에서 추적 |

심각도가 불확실하면 한 단계 높게 시작하고 증거가 생기면 낮춘다.

## 3. 공통 대응 흐름

### 3.1 탐지와 등록

1. UTC 기준 사고 시작 시각과 최초 관찰 시각을 기록한다.
2. 관련 request ID, 배포 commit, 계정·서비스 내부 ID, 경보를 수집한다.
3. 실제 비밀값과 개인정보는 복사하지 않고 해시·마스킹된 식별자를 사용한다.
4. 추정이 아니라 확인된 사실, 가설, 미확인 범위를 구분한다.

### 3.2 봉쇄

1. 영향을 받는 엔드포인트, OAuth 공급자, 파일 처리, 배포를 기능 플래그·라우팅·권한으로 차단한다.
2. 관련 access·refresh token, API key, DB 자격 증명, 배포 자격 증명을 폐기한다.
3. 공격자가 제어할 가능성이 있는 CI와 관리자 세션을 종료한다.
4. 증거를 보존한 뒤 로그·DB·아티팩트에 대한 쓰기 범위를 최소화한다.

### 3.3 제거와 수정

1. 최초 침투 경로와 권한 상승·지속성 경로를 확인한다.
2. 같은 패턴을 전체 코드, 설정, 로그, Git 기록, 의존성에서 검색한다.
3. 최소 수정이 아니라 공격 경로 전체를 차단하는 회귀 테스트를 먼저 추가한다.
4. secret은 회전하고, 손상된 아티팩트와 세션을 신뢰하지 않는다.

### 3.4 복구

1. 격리 환경에서 수정본, 마이그레이션, RLS, 백업 복구를 검증한다.
2. 치명적·높음 취약점이 0건인지 독립된 검토 증거로 확인한다.
3. 제한된 트래픽부터 재개하고 인증 실패, 권한 거부, 오류율, 데이터 정합성을 감시한다.
4. 재개 후에도 의심스러운 세션과 비정상 내보내기를 집중 감시한다.

### 3.5 사후 분석

사고 종료 후 5영업일 안에 타임라인, 근본 원인, 영향 데이터, 탐지 지연, 잘 작동한 통제, 실패한 통제, 재발 방지 작업을 기록한다. 개인 비난 대신 시스템과 승인 과정의 결함을 수정한다. 위협 모델, 체크리스트, 테스트, 운영 문서를 같은 변경에 갱신한다.

## 4. 시나리오별 플레이북

### 4.1 Git·로그·CI에서 secret 발견

1. 해당 자격 증명을 즉시 폐기한다.
2. 최소 권한의 새 자격 증명을 생성하고 안전한 저장소에 배포한다.
3. 노출 시각부터 폐기 시각까지 공급자 감사 로그에서 사용 흔적을 확인한다.
4. 관련 세션과 파생 토큰을 함께 폐기한다.
5. Git 기록 또는 로그의 노출본을 접근 제한·보존 요구와 조정해 제거한다.
6. secret scanner 규칙과 회귀 테스트를 추가한다.
7. Git 기록 재작성은 협업 브랜치와 태그 영향을 검토하고 명시적 승인 후 수행한다.

### 4.2 access·refresh token 또는 사용자 세션 탈취

1. 사용자와 토큰 계열을 식별해 서버에서 폐기한다.
2. 비밀번호 로그인 계정은 비밀번호 재설정과 다른 세션 종료를 요구한다.
3. OAuth 공급자 연결과 최근 로그인·내보내기·삭제 활동을 확인한다.
4. 사용자 데이터 변경은 감사 로그와 동기화 operation을 대조해 되돌릴 범위를 정한다.
5. 사용자에게 발생한 행동, 폐기 완료, 필요한 재로그인을 알린다.

### 4.3 사용자 간 데이터 접근 또는 RLS 실패

1. 관련 읽기·쓰기 엔드포인트와 내보내기를 즉시 차단한다.
2. service-role 사용 경로, RLS 정책, 앱 쿼리의 `user_id`, 연관 FK를 함께 검토한다.
3. 읽기 노출과 쓰기 변조 범위를 사용자·테이블·시간대별로 계산한다.
4. 변조 데이터는 백업과 감사 로그를 이용해 복구하되 증거를 먼저 보존한다.
5. 모든 사용자 소유 테이블에 같은 패턴이 없는지 변형 분석을 수행한다.
6. 사용자 A/B 음성 테스트와 마이그레이션 정책 테스트를 필수 게이트에 추가한다.

### 4.4 악성 또는 손상된 의존성·GitHub Action

1. 배포와 패키지 설치를 중지하고 손상 의심 버전과 실행 시각을 고정한다.
2. CI·개발·운영에서 해당 코드가 접근할 수 있었던 secret을 회전한다.
3. lockfile, 설치 스크립트, 빌드 로그, 배포 아티팩트, 네트워크 접근을 보존한다.
4. 신뢰 가능한 이전 버전이나 검증된 대체 패키지로 재빌드한다.
5. 깨끗한 runner에서 SBOM과 아티팩트를 새로 생성하고 재배포한다.
6. 의존성 승인, Action SHA 고정, 네트워크·secret 권한을 보강한다.

### 4.5 데이터베이스 노출 또는 무단 변경

1. 외부 네트워크 접근과 손상 계정을 차단하고 자격 증명을 회전한다.
2. DB 감사 로그, 쿼리 로그, 백업, 복제 상태를 보존한다.
3. 읽기 노출과 쓰기 변조를 분리해 평가한다.
4. 깨끗한 시점의 백업을 격리 환경에 복원하고 이후 정상 변경만 재적용한다.
5. 운영 재개 전 RLS, 역할, 함수 권한, Storage 정책, API 권한 테스트를 실행한다.

### 4.6 OAuth 공급자 또는 콜백 이상

1. 해당 공급자 로그인을 일시 중지하되 다른 안전한 로그인 수단은 유지한다.
2. redirect URI, client secret, PKCE, `state`, `nonce`, issuer·audience 검증을 확인한다.
3. 영향받는 공급자 세션과 연결 토큰을 폐기한다.
4. 자동 계정 병합이나 잘못된 provider subject 연결이 있었는지 검토한다.
5. 공급자 상태·보안 공지를 확인하고 검증 후 단계적으로 재개한다.

## 5. 사용자와 외부 커뮤니케이션

- 확인되지 않은 원인이나 피해 규모를 사실처럼 말하지 않는다.
- 사용자 공지에는 발생한 일, 영향받을 수 있는 데이터, 이미 취한 조치, 사용자가 해야 할 일, 다음 업데이트 시점을 포함한다.
- 토큰, 내부 IP, 상세 공격 페이로드처럼 추가 악용을 돕는 정보는 공개 공지에서 제외한다.
- 법적·규제 신고 의무가 생길 수 있는 범위라면 공개 전 전문 법률 검토를 받는다.
- 공급자 문의와 사용자 공지는 UTC 타임라인에 연결한다.

## 6. 증거 보존

- 원본 로그와 스냅샷은 읽기 전용 또는 변경 탐지가 가능한 저장소에 보관한다.
- 수집자, 수집 시각, 원본 위치, 해시, 사본 위치를 기록한다.
- 조사용 사본에서 분석하고 원본을 수정하지 않는다.
- 불필요한 개인정보를 새 조사 문서에 복제하지 않는다.
- 보존 기간은 사고 영향과 법적 요구를 검토해 정하고 종료 후 안전하게 삭제한다.

## 7. 복구 연습

분기마다 최소 한 가지 플레이북을 표본 연습한다. 연습은 토큰 폐기, 기능 차단, 백업 복원, RLS·정합성 테스트, 사용자 공지 초안까지 포함한다. 실제 운영 secret을 노출하거나 운영 데이터를 테스트 환경으로 복사하지 않는다.

이 절차와 자동 검사는 전문 보안 감사와 사고 대응 업체를 대체하지 않는다. 실제 재무 데이터 또는 개인정보 침해 가능성이 있으면 자격을 갖춘 보안·법률 전문가의 도움을 받는다.
