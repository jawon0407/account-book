## 3. 시스템과 신뢰 경계

코드는 Next.js 웹/BFF → NestJS/Fastify API → PostgreSQL 형태다. 로그인 공급자와 금융기관 연동은 서버 경계 밖에 있다. 이번 감사 대상은 실제 금융 DB가 아니라 **그 시스템의 소스·이력·개발 기록이 GitHub 공개로 노출되는 경계**다.

브라우저/앱에 자격증명을 보내지 않는 설계와, 개발자가 이를 Git에 올리지 않는 통제는 서로 다른 문제다. 공개 전환으로 운영 DB 자체가 공개되지는 않지만 소스·문서·커밋에 들어 있는 값은 별도로 노출될 수 있다.

기존 로컬 secret scanner는 AWS/GitHub 토큰/개인키 표식 중심이다. 이번 일회성 검사에서는 JWT, 인증정보 포함 URL, 인용/비인용 secret 할당, secret 문맥의 UUID, 한국 전화·주민등록번호 형태, 계좌번호 문맥까지 보완했다. 금융결제원처럼 UUID 형태의 키는 일반 토큰 접두사 검사만으로 충분하지 않다. 제품 scanner를 수정한 것은 아니다.

## 6. 공개 전에 남은 조건

### G1. Git 작성자 개인정보 공개 결정 — 확인 필요

원격 커밋의 author/committer 메타데이터에 개인 메일 서비스 주소 1종과 비-noreply 로컬 식별자 1종이 있다. 주소 원문은 기록하지 않는다. 공동 작성자 문구 등 커밋 본문에도 별도 식별자가 있을 수 있다.

공개되면 누구나 Git 이력을 복제해 해당 주소를 수집할 수 있다. 이는 비밀번호 탈취가 확인됐다는 뜻은 아니지만 스팸·표적 피싱·계정 연계에 활용될 수 있다. 사용자가 공개를 허용할지 먼저 결정한다.

- 그대로 공개 수용: 이력 변경이 없으나 기존 주소는 공개된다. 이후 새 커밋부터 noreply를 써도 과거 주소는 남는다.
- 과거 주소 비공개 요구: 새 커밋의 Git 설정만으로 해결되지 않는다. 이력 재작성·PR 참조/캐시 대응을 별도 계획·승인해야 한다. 이번에 강제 push하지 않았다.

### G2. 외부 복사본의 라이선스·출처 — 로컬 보완, 원격 미반영

최초 T5 감사 시점에는 원격 main과 작업 트리에 `.agents/skills/impeccable/` 복사본 및 `scripts/modern-screenshot.umd.js` 번들이 포함돼 있었으나, 전체 원격 이력 경로 검색에서 LICENSE/NOTICE 파일을 찾지 못했고 번들에도 해당 고지를 확인하지 못했다.

공식 Impeccable은 Apache-2.0과 제3자 NOTICE를 제공하며, modern-screenshot은 MIT 고지를 제공한다. 단, 현재 공식 main의 라이선스만으로 우리 복사본의 정확한 버전·출처·수정 여부까지 확정할 수는 없다. 공개 전 원본 버전과 배포 조건을 대조해 해당 LICENSE/NOTICE·출처·수정 고지를 보존해야 한다.

근거: [Impeccable LICENSE](https://github.com/pbakaus/impeccable/blob/main/LICENSE), [Impeccable NOTICE](https://github.com/pbakaus/impeccable/blob/main/NOTICE.md), [modern-screenshot LICENSE](https://github.com/qq15725/modern-screenshot/blob/main/LICENSE).

이는 앱 전체에 Apache/MIT 라이선스를 임의 부여하라는 뜻이 아니다. 우리 코드의 라이선스 선택과 외부 코드의 기존 조건 준수는 별개다. 초기 감사에서는 법적 위반을 확정하지 않고 **출처·재배포 고지 검증 미완료**로 기록했다. 아래 후속 작업과 구분하며, 외부 도구는 실행하지 않았다.

G2 후속 반영(2026-09-28): 사용자가 상세 파일 지도를 승인하여 [외부 코드 고지](../../THIRD_PARTY_NOTICES.md)와 원문 4개를 로컬에 추가했다. 설치된 105개 파일은 공식 스냅샷 `da99645a58400ed7acb201e6904f9413efd89c6e`와 모두 일치한다. 표시 3.9.1과 같은 릴리스 태그는 아니며, modern-screenshot 번들은 공식 npm 4.7.0과 일치한다. 원본 NOTICE에 명시된 Platform Design Skills MIT 원문도 보존했다.

- 원문 4개의 SHA-256이 고정 출처와 일치하고 기존 외부 코드 105개는 HEAD와 일치한다. 고지 원문과 경로 매핑은 [상세 계획·검증 기록](../superpowers/plans/2026-09-28-third-party-license-notices.md)에 남겼다.
- **로컬 고지 반영과 공개 준비 완료는 다르다.** 커밋·push하지 않아 원격 고지 누락은 아직 해소되지 않았다. 공개 직전 실제 배포할 커밋에 고지가 포함됐는지 확인해야 한다.
- 앱 전체 라이선스·외부 도구 실행 허용·기존 보안 문제는 변경하지 않았다. G1 개인정보, G3 권리·최종 목록, P1 원격 보호는 계속 미종결이다.

### G3. 자료 소유권과 최종 노출 목록 — 확인 필요

원격 텍스트 이력에서 raon/라온/Notion 링크 관련 자료는 발견하지 못했다. 현재 미푸시 기획 문서에는 raon-app의 향후 연동 역할만 있다. 그렇더라도 제3자 계약 자료·고객 자료가 없다는 소유자의 확인을 검사기가 대신할 수 없다.

원격 이력에는 이번 분류에 해당하는 .env/덤프/백업/스크린샷/문서 바이너리 경로가 없었다. 로컬 합집합의 DOCX와 패키지 캐시 DB 2개는 원격 refs에서 도달 불가능했다. 압축 문서 내부·DB 레코드는 검사하지 않았으며, 향후 이 객체가 포함되는 브랜치를 push하려면 별도 검토해야 한다.

공개 직전에 refs, PR/댓글, runs/attempts/artifacts, 라이선스 파일, 최종 미커밋 변경을 다시 대조한다. 차이가 있으면 감사와 승인 범위를 갱신한다. PC 전체·채팅 첨부·Notion 전체를 이번 승인으로 읽거나 공개하지 않는다.

## 7. CI·원격 보안 설정의 현재 관측

| 항목 | 읽기 조회 결과 | 해석 |
| --- | --- | --- |
| 원격 브랜치의 workflow | 10개 브랜치 중 9개에 각 1개, maintenance에는 없음 | 현재 tip의 구성 점검 |
| workflow의 외부 실행 경계 | 검사한 모두 pull_request_target/self-hosted/secrets 참조 없음 | 과거 모든 코드의 취약점 부재 보증은 아님 |
| Actions 버전·checkout | 사용 Action SHA 고정, contents read, persist-credentials false | 실제 CI 결과의 합격을 뜻하지 않음 |
| 저장소 Actions 설정 | enabled=true, allowed_actions=all, sha_pinning_required=false | 개별 파일은 pin됐지만 저장소가 미래 변경에도 강제하지는 않음 |
| 기본 token 권한 | read, PR 승인 권한 false | 현재 관측값 |
| self-hosted runner | 0 | 별도 실행 장비 없음 |
| environment/deployment | 각각 0 | 외부 PaaS 자체의 배포/로그 상태는 미검증 |
| fork PR 승인 정책 | HTTP 422: 비공개 저장소에서는 지원되지 않는 조회 | 공개 전환 절차에서 즉시 확인·설정하고 미확인이면 병합/실행 승인 중단 |
| 비공개 취약점 신고 | HTTP 404 | 활성이라고 안내할 근거 없음; 공개 후 실제 신고 경로 확인 필요 |
| GitHub Pages | HTTP 404 | 없음/접근 불가를 이 응답만으로 단정하지 않음 |
| secret 보호 | repository 응답 security_and_analysis=null | 비활성이라고도, 활성이라고도 확정하지 않음 |

`.env`, `.env.local`, `apps/web/.env.production`은 실제 `git check-ignore`에서 제외됐으며 추적 env 파일은 0개다. `.env.example`은 허용 예외이므로 나중에 생성하면 내용 검사가 필요하다. 현재 제외 규칙만으로 과거 유출이 없어졌다고 판단하지 않는다.

main의 기존 간접 병합 P1은 이번 노출 감사로 닫지 않는다. 실제 서버 보호 적용·read-back·정상/거부 흐름·독립 검토가 후속 승인 범위다. 앱 auth의 기존 검증 결과를 원격 보호 증거로 바꾸어 적지 않는다.

## 8. 검증과 증거 파일

- 임시 scanner 10종은 각각 합성 양성 입력으로 일치 여부를 검사했다: 10/10, exit 0. 검사기의 포괄성이나 탐지율을 증명하는 테스트는 아니다.
- Git 스캔·원격 목록·GitHub 메타데이터·122개 실행 로그 조회는 종료 0. 재실행 차수 2개도 별도 조회 성공. API에서 조회 불가였던 항목은 위 표에 유지한다.
- 로그 조회 3개 일치는 컨테이너 ID로 문맥 확인했다. PR/댓글에서는 당시 적용한 규칙의 일치가 없었다.
- 자체 scanner 사용이며 상용 secret 탐지기나 Gitleaks 정식 전수 검사를 실행했다고 주장하지 않는다. 이번에 도구 설치·패키지 레지스트리 전송을 하지 않았다.
- 문서 변경이므로 앱 전체 verify·coverage·DB·브라우저 E2E는 재실행하지 않았다. 1,149개/185개 등 이전 수치는 이전 구현 검증이다.
- 최종 대조: 문서 4개의 로컬 링크 36개 존재 확인, diff 공백 검사 통과. 124개 로그 합계 24,965,567바이트를 검사했고 감사 시작/종료의 원격 refs는 같았다. 이는 최종 공개 시점의 동결·재검사를 대신하지 않는다.

로컬 증거: `remote-refs.json`, `git-scan.json`, `triage.json`, `inventory.json`, `github-scan.json`, `runs.json`, `artifacts.json`, `logs-scan.json`, `followup.json`, `checks.json`. 값 지문과 경로도 내부 감사 자료이므로 기본 Git 제외를 유지한다. 별도의 원시 로그 파일은 만들지 않았다.

## 9. 다음 작업 제안과 승인 경계

1. **라이선스 출처 조사·고지는 로컬 반영했다.** 별도 승인한 커밋·push 단계에서 실제 원격 반영을 확인한다. 앱 코드 변경이나 새 전체 앱 라이선스 부여는 하지 않는다.
2. 사용자는 Git 이력의 개인 이메일 공개 허용 여부와 자료 공개 권리를 결정한다. 비공개를 원하면 이력 정리의 영향과 대안을 먼저 설명한다.
3. 최종 공개 자료 목록을 동결하고 변경분을 재검사한다. 공개 자체, 보호 적용, 외부 PR 실행 정책, 신고 채널, secret 보호는 단계별 성공 조건을 가진 별도 원격 실행 계획으로 승인받는다.
4. 원격 보호와 승인된 PR 검증 후 10-A2 은행 연결 DB·최소 권한 개발로 돌아간다. 모바일·실은행 API가 이번에 완성된 것은 아니다.

이번 승인으로 이력 삭제·강제 push·공개 전환·외부 요금제 변경을 하지 않았다. 실제 secret이 새로 발견되면 폐기/교체가 우선이며, 공급자 감사 로그 확인과 이력 정리는 각각 별도 승인·권한으로 진행한다.

## 10. 한계와 책임

이 보고서는 `cso` 절차를 적용한 **AI 보조 공개 노출 감사**다. 전문 보안 감사나 침투 테스트를 대체하지 않으며, 모든 취약점·개인정보·인코딩/압축된 secret을 탐지했다는 보증이 아니다. 금융정보를 다루는 운영 출시 전에는 별도 전문 검토가 필요하다. “확정 유출 0건”과 “공개 승인 가능”을 혼동하지 않는다.
