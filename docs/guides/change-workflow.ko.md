# 작업 사전 계획·승인·검증·기록 절차

적용일: 2026-09-09. 사용자 요청에 따라 모든 후속 작업에 적용한다.

## 1. 기본 원칙

**현황 확인 → 작업 내역·대안 정리 → 파일 지도·규모·검증 계획 기록 → 사용자 승인 → 구현 → 검증 → 결과 기록** 순서로 진행한다.

- 질문·검토 요청만으로 제품 코드, 의존성, DB, 배포 설정을 수정하지 않는다.
- 승인 전에는 관련 파일 읽기, 비파괴 진단, 요청받은 계획 문서 작성만 한다. 외부 전송·비용·secret 접근은 허용된 범위를 별도로 확인한다.
- 사용자가 승인한 작업 단위 안에서는 계획된 세부 단계를 진행한다. 범위가 달라지면 다시 설명하고 승인받는다.
- “앞으로 진행”이라는 장기 의향과 특정 수정안의 승인을 구분한다. 감사 데이터 전송 승인을 패키지 설치·업데이트·배포 승인으로 해석하지 않는다.
- 기존 미커밋 변경은 소유권을 추정하지 않고 보존한다. 무관한 파일을 일괄 stage하거나 되돌리지 않는다.

## 2. 수정 전에 전달할 내용

| 항목 | 반드시 설명할 내용 |
| --- | --- |
| 목적 | 어떤 사용자 문제·보안 위험을 해결하는지 |
| 현재 근거 | 기준 브랜치/SHA, 확인한 코드, 재현 결과와 미확인 사항 |
| 포함/제외 | 이번에 할 일과 별도 작업으로 남길 일 |
| 대안 | 실제로 타당한 접근별 장점·단점·보안·유지보수 영향과 추천 이유 |
| 파일 지도 | 수정/추가/삭제/읽기 전용 파일의 정확한 경로 및 역할 |
| 규모 | 파일 수, 직접 코드와 자동 생성 diff를 구분한 예상 변경량, 불확실성 |
| 진행 순서 | 단계별 실행 방법과 완료 조건 |
| 검증 | 사용할 테스트·빌드·브라우저 확인, 실제 서비스 검증의 한계 |
| 위험·중단 조건 | 보안 완화·추가 의존성·대규모 수정·운영 데이터 접근이 필요해지는 경우 |
| Git/배포 | 브랜치·커밋·푸시·PR·병합·배포 중 승인받은 범위 |

선택의 여지가 없는 단순 수정에 억지 대안을 만들지는 않는다. 이 경우 대안이 실질적으로 없는 이유와 영향을 짧게 설명한다.

## 3. 작업 종류에 맞는 검증

- 단순 CSS·배치: 새 테스트 코드를 기본으로 만들지 않는다. 영향 화면과 경계 폭을 브라우저에서 확인하고 수정량을 먼저 안내한다.
- 기능·인증·보안·데이터 변경: 실패 조건을 재현하는 테스트를 먼저 작성하거나 기존 테스트를 보강한다. 실패 원인과 수정 후 통과를 구분해 기록한다.
- 의존성 업데이트: 버전 정책·회귀 테스트·타입 검사·빌드·audit을 수행한다. 실제 DB/E2E는 폐기 가능한 환경에서만 실행한다.
- 문서: 경로·명령·코드와의 일치, 링크 유효성, 구현 완료/계획/미검증 구분을 확인한다.
- 실행하지 않은 검사를 통과로 적지 않는다. 과거 결과에는 날짜와 SHA를 남긴다.

## 4. 기록 위치와 상태

- 상세 실행 계획: `docs/superpowers/plans/YYYY-MM-DD-주제.md`.
- 장기 진행 지도: `docs/status/2026-08-24-development-progress.ko.md`.
- 보안 검증 기록: `docs/guides/security-auth-testing.md`.
- 비공개 로컬 캡처·원시 결과: Git 제외 `output/`. 공유가 필요한 핵심 결론은 비밀값을 제거하여 추적 가능한 문서에 옮긴다.
- 계획 상태는 `승인 대기 → 승인됨 → 진행 중 → 검증 중 → 완료`로 구분한다. 미해결은 `차단/추가 승인 필요`로 기록한다.
- 완료 기록에는 실제 수정 파일, 테스트 명령/종료 코드/개수, 미실행 검사, 남은 위험, 커밋/PR 상태를 적는다.
- 결과에 secret·cookie·토큰·DB 연결 문자열·실제 금융내역을 넣지 않는다.

## 5. 범위 재승인이 필요한 때

예상하지 못한 DB migration, 인증 방식 변경, 패키지 메이저 업그레이드, 빌드 스크립트 허용 확대, 보안 검사 완화, 운영 데이터 접근, 새 외부 서비스 도입, 파일 수나 변경량의 큰 증가가 발견되면 중단하고 변경 계획을 제시한다.

실패한 업데이트를 취약 버전으로 되돌려 로컬 비교할 수는 있어도 그 상태를 배포 승인으로 취급하지 않는다. 릴리스는 안전한 수정안이 검증될 때까지 보류한다.
